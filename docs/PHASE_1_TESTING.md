# Phase 1 테스트 설계와 완료 증빙

기준일: 2026-11-20

상태: Docker 개발환경·Makefile·`tests/environment`의 도구 체인 검사를 작성했다.
`tests/test_http.c`에 요청 라인·헤더 구문, `tests/test_body.c`에 본문 디코더,
`tests/test_webserver.c`에 서버 연결 C 단위 테스트를 둔다.
파서 구현은 `http.c` 하나를 링크하며, 단계별 테스트 파일 구분은 유지한다.
`tests/test_server.py`는 실제 소켓의 요청 수신·오류·본문·100·후속 요청을 검사한다.
Host·지원 버전·URI 구문의 단위/수신 연결 사례를 추가했다.
고정 index/echo Router의 단위와 실제 소켓 테스트를 추가했다.
일반 파일 경로 정책·시간 제한·요구사항 전체 테스트·성능 측정은 아직 구현하지 않았다.
기본 블로킹 수신·고정 200 응답 예제는 일회성 소켓/curl 검사와 부분 송신·실패 주입 검사로 확인했다.
이 결과를 아래 HTTP 파서·보안·메모리 테스트 전체의 통과로 계산하지 않는다.
구현된 환경 검사와 아래 후속 타깃 제안을 구분하며 실제 실행 결과는 진행 원장에 기록한다.
요구사항의 단일 기준은 `PHASE_1_REQUIREMENTS.md`, 진행 원장은 `../AGENTS.md`다.

## 1. 검증 원칙

- C: 파서·청크·URI·MIME·정책·마감 계산의 단위 검증.
- Python 표준 라이브러리: 실제 서버 프로세스와 소켓 통합 검증.
- curl·브라우저: 실제 클라이언트 동작 확인. 자동 보안 테스트를 대체하지 않는다.
- sanitizer·누수 검사·FD 관찰: 정상과 실패 경로의 자원 검증.
- 별도 부하 도구: 성능 기준선. 테스트 하네스의 속도를 서버 성능으로 오인하지 않는다.
- 서버의 HTTP 파서를 응답 검증기에 재사용하지 않는다.
- 고정 sleep·준비 상태 폴링·실패 후 재시도로 통과시키지 않는다.
- pure prose 문구를 테스트로 고정하지 않는다. 실제 응답 바이트·파싱 필드·로그 스키마는 검증한다.
- 미실행·차단·도구 미지원은 PASS가 아니다. 기존 실패를 삭제·skip·완화하지 않는다.

## 2. 권장 실행 표면

구현된 개발환경 명령은 다음과 같다. 호스트 Make 설치는 필요하지 않다.

```sh
sh dev.sh build
sh dev.sh check
sh dev.sh shell
```

`check`는 비특권 사용자·Linux/amd64·작업 디렉터리 쓰기를 확인한 뒤
C17·POSIX 프로그램을 일반 빌드와 ASan/UBSan/누수 검사 설정으로 실행하고
일반 빌드를 Valgrind로 검사한다. 전체 검사에는 120초 제한과 5초 강제 종료 유예를 둔다.
GDB·strace는 설치 여부만 확인하며 실제 디버깅 동작은 검증하지 않는다.
이 검사는 서버의 T-01~T-32 통과로 계산하지 않는다.

컨테이너에서 `make test-unit`은 요청 라인 파서·서버 연결 단위 테스트를 엄격한 경고 옵션으로
빌드·실행하고 임시 실행 파일을 제거한다. CFLAGS를 바꿔 sanitizer 검사도 실행할 수 있다.
`make test-integration`은 서버를 빌드한 뒤 Python 소켓 테스트를 실행한다.
현재 테스트는 고정 포트 8080을 쓰므로 개발 서버와 충돌하지 않는 별도 컨테이너에서 실행한다.
테스트는 stdout 준비 이벤트를 받고 출력 파이프를 계속 비우며, 종료 시 자식 프로세스를 회수한다.
다음은 아직 구현되지 않은 서버용 Makefile 타깃 제안이다.

```sh
make test-security
make test
make sanitize
make benchmark
make clean
```

`test`는 단위·통합·필수 보안 테스트를 포함해야 한다.
`sanitize`는 sanitizer로 빌드한 서버와 단위 테스트에 정상·오류 시나리오를 실행한다.
`benchmark`는 최적화 빌드를 사용하고 sanitizer 결과와 혼합하지 않는다.
Python은 unittest·socket·subprocess·selectors·tempfile 등 표준 라이브러리를 우선한다.
pytest·외부 HTTP 라이브러리는 기본 의존성으로 추가하지 않는다.
컴파일러·C/Python 버전·검사 도구의 실제 지원 범위는 D-07·D-08에서 고정한다.
빌드·서버 실행·자동 검증·성능 기준선은 Linux Docker 컨테이너를 기준으로 한다.
컨테이너 생성·도구 체인 검사 명령은 `dev.sh`에 구현했다. 포트 공개와 HTTP 테스트 실행 명령은 해당 서버 기능 구현 시 추가한다.
WSL에서는 `docker.exe`와 Windows 형식의 소스 경로를 사용하며, 일반 Linux 호스트에서는
`docker`를 사용한다. 현재 WSL/Windows 드라이브 환경의 실제 결과는 진행 원장에 있다.

### 첫 구현 단위의 확인

아키텍처 A-10의 첫 단위는 컨테이너·도구 체인 검증이며 HTTP 기능 검증이 아니다.
Docker CLI뿐 아니라 데몬 연결 성공을 확인한 뒤 지정 이미지에서 빌드한다.
컴파일러·Make·Python·검사 도구의 버전과 실제 컴파일·실행의 종료 코드를 기록한다.
이미지를 빌드한 것만으로 서버 동작·보안·메모리 검사 통과를 선언하지 않는다.

Docker 데몬에 접근할 수 없으면 컨테이너 검증은 BLOCKED, 실행하지 않은
빌드·서버·테스트는 NOT_RUN이다. 호스트 네이티브 실행으로 대체하지 않는다.
현재 접근 상태와 재개 조건은 `../AGENTS.md`의 증빙 원장을 따른다.

## 3. 결정적 동기화

### 서버 준비와 종료

서버 준비·테스트 자식 프로세스 회수는 Phase 1에도 필요하다.
SIGINT/SIGTERM의 애플리케이션 정상 종료 검증은 T-27과 함께 Phase 2 시작에 진행한다.

준비 완료 통지용 테스트 파이프를 서버 실행 전에 연결한다.
listen과 필수 초기화가 성공한 뒤의 READY 이벤트를 제한 시간 안에 받는다.
접속을 반복하거나 고정 시간 기다린 뒤 준비됐다고 추측하지 않는다.
종료는 프로세스 종료 이벤트·exit code·출력 수집으로 확인한다.
테스트 실패의 finally 경로에서도 자식 프로세스와 임시 자원을 정리한다.
테스트 전용 제어 통로를 생산용 HTTP 관리 경로로 노출하지 않는다.

### 분할 수신·부분 송신

- C 단위 테스트는 고정 입력의 모든 단일 분할점과 고정 seed의 다중 분할을 적용한다.
- 바이트마다 한 번씩 넣어 CR/LF, 숫자, `%HH`, trailer 경계 상태를 확인한다.
- Python에서 send를 여러 번 했다는 것만으로 recv도 나뉘었다고 주장하지 않는다.
- 특정 단계에서 끊어야 하는 경우 테스트 빌드의 소비/단계 이벤트를 먼저 구독한다.
- 부분 송신은 I/O 단위 테스트의 정해진 짧은 write/EAGAIN/EINTR 결과와
  실제 소켓 backpressure 테스트를 함께 사용한다.
- 클라이언트 측 수신 이벤트를 등록한 뒤 전송·닫기를 발생시킨다. 종료 시그널 사례는 Phase 2 시작의 T-27에 적용한다.

### 시간 제한

마감 계산은 C에서 주입한 단조 시각으로
deadline 직전·동일·직후 및 진행 후 재계산을 검사한다.
통합 테스트는 제어 가능한 테스트 시계/단계 통지 또는
문서화된 짧은 테스트 전용 제한으로 실제 I/O와 마감 연결을 검사한다.
생산 기본값 10·30·60초의 설정값 검증은 별도로 유지한다.
시간 자체가 대상인 검증에서도 고정 sleep으로 상태를 추정하지 않고
만료 이벤트·EOF·프로세스 종료를 bounded wait로 기다린다.
가상 시계로 검사한 결과를 실제 소켓 대기 검증으로 포장하지 않는다.

### 링크 교체·파일 변경·통제된 실패

검사 직후/열기 직전 같은 정확한 테스트 단계에 barrier를 둔다.
외부 파일을 식별 가능한 canary로 만들고 단계 통지 뒤 링크/경로를 교체한다.
무작위 경쟁 반복에서 우연히 외부 파일이 안 보였다는 결과만으로 합격시키지 않는다.
그 단계가 실제 생산 접근 경로를 대표하는지도 아키텍처 불변 조건으로 검토한다.
할당·파일 읽기·로그 쓰기 실패는 테스트 전용 오류 주입으로 재현한다.
정상 제어 흐름을 대체하는 과도한 mock 때문에 경계 검증이 사라지지 않게 한다.

## 5. 필수 시나리오

각 그룹의 사례는 C 또는 Python 테스트로 구현하며, 필요한 자원 검사를 함께 수행한다.
T-27은 Phase 2 시작에 구현·실행하고 나머지는 Phase 1 범위를 따른다.
D 항목이 열려 있어 예상 결과를 정할 수 없으면 BLOCKED로 기록하고 통과로 계산하지 않는다.

### T-01 의존성

서버 소스·include·링크 명령·실행 의존성을 확인한다.
외부 HTTP/이벤트 루프가 없고 Python/부하 도구가 서버 실행 의존성이 아닌지 검사한다.

### T-02 지원 환경

Linux Docker 컨테이너 안에서 빌드·실행하고 실제 기능·보안 경계 동작을 확인한다.
호스트 OS·실제 Linux 커널·CPU 아키텍처·Docker 버전·이미지 식별자와 도구 버전을 기록한다.
호스트의 macOS 네이티브 실행·검증은 필수 범위가 아니다.
이미지·최소 커널·도구·마운트·포트와 개발 컨테이너의 중지 유예 설정은 D-02·D-07·D-08에서 정한 계약대로 확인한다.
서버 SIGINT/SIGTERM 전달·정상 종료 유예 검증은 Phase 2 시작의 T-27에서 수행한다.

### T-03 빌드와 CLI

깨끗한 빌드·재빌드·정리, 다른 포트·루트 실행을 검증한다.
잘못된 숫자·누락/중복/알 수 없는 인자·없는 루트·읽기 불가 루트·이미 사용 중인 포트를 검사한다.
실패 시 비정상 종료·진단·FD 회수를 확인한다.
실행 이름 `webserver`, 필수 `--port`/`--root`, 포트 1~65535와 잘못된 입력의 비정상 종료는 확정 계약이다.
청취 주소·동적 포트·중복 인자 등의 미정 사례와 지원 도구 버전은 D-07의 관련 하위 결정을 먼저 닫는다.

### T-04 연결 하나의 수명

새 연결로 연속 요청하면 서버는 계속 응답한다.
한 연결에서는 최종 응답 하나와 Connection: close 뒤 종료한다.
keep-alive 요청이나 두 요청을 이어 보낸 입력에도 두 번째 요청이 실행되지 않는다.
두 번째 연결이 첫 연결과 동시에 서비스되는 것을 Phase 1 합격 조건으로 삼지 않는다.

### T-05 파서와 헤더

서버 연결 하위 범위는 `tests/test_webserver.c`에서 실제 `handle_client`의 recv/send만
제어해 CR/LF 분할·반복 수신·완성 전 앱 호출 금지·소비 길이·400/414·EOF·EINTR를 검사한다.
`tests/test_server.py`는 실제 앱과 서버의 정상/미구현 메서드 200, 잘못된 라인 400,
정확한 길이 한도 200·초과 414·미완성/빈 EOF 400과 후속 정상 요청을 검사한다.
소켓 테스트의 send 호출 횟수를 recv 분할의 증거로 사용하지 않는다.

현재 구현 범위는 `tests/test_http.c`의 요청 라인·헤더 구문 테스트다.
`test_request_line`은 필드·원본 참조·소비 길이, `test_fragmented_line`은 모든 단일
분할점과 바이트별 누적 입력, `test_invalid_lines`는 구분자·CRLF·버전 문법과
NUL을 포함한 제어문자, `test_syntax_is_not_routing`은 구문 분리와 지원 판정의 분리를 검사한다.
`test_headers`는 원본 참조·이름 대소문자·중복/순서 보존·OWS 제거·빈 값·
값의 0x80/0xff 보존·본문 비소비를 검사한다. `test_fragmented_headers`는
모든 누적 길이의 미완성 상태와 분할 후 완료를 검사한다.

### T-15 echo 보안

### T-16 정적 파일과 특수 파일

### T-18 링크와 경계 보안

상대·절대·중첩·중간 디렉터리 링크를 각각 검사한다.

검사/열기 단계 barrier에서 외부 canary로 링크를 바꿔도 내용이 노출되지 않아야 한다.

### T-19 URL 디코딩

인코딩된 숨김·상위 이동·중첩 경로는 공개 정책을 우회하지 못한다.
`%252e`를 다시 `%2e` 또는 `.`으로 재해석하지 않는다.
인코딩된 구분자·Unicode 정규화·비정상 UTF-8·중복 slash의 기대값은 D-01을 먼저 닫는다.

### T-20 쿼리 분리

정적 경로에 query가 없거나 달라도 같은 파일을 제공한다.
query가 파일명·경계 검사·접근 로그에 섞이지 않는다.
`%3F`를 디코딩 뒤 query 구분자로 잘못 분리하지 않는다.
redirect와 `/echo?x=1`의 처리도 D-01 판정표에 맞춘다.

### T-21 MIME와 허용 목록

확정한 각 확장자의 MIME, 미등록·무확장자 403, 미정인 대소문자 정책을 검사한다.
링크의 URL 이름과 실제 대상 이름이 다른 경우에도 공개 정책이 우회되지 않는다.
허용 확장자가 루트 경계·권한 검사를 생략시키지 않는다.
같은 바이트가 echo에서는 허용돼도 정적 파일 허용 목록과 충돌하지 않는다.
정확한 목록·검사 기준은 D-01 결정 전 BLOCKED다.

### T-22 403/404와 존재 노출

숨김·없는 경로·index 없는 디렉터리는 같은 404 본문·정책 헤더를 사용한다.
루트 이탈·OS 권한 거부는 403이며 실제 경로·errno를 노출하지 않는다.
Date 같은 동적 필드는 정규화해 비교한다. 응답 시간의 완전 동일성은 요구하지 않는다.
권한 fixture는 실제 비특권 계정에서 검증한다.
컨테이너의 root 실행이나 호스트 공유 마운트 권한 때문에 재현하지 못하면 사유를 기록하고 PASS로 처리하지 않는다.

### T-23 오류 응답

각 확정 상태 코드, fixed text/plain 본문, Content-Length와 close를 확인한다.
통제된 내부 할당/읽기 실패로 500을 재현한다.
예외·실제 경로·원문·인증정보가 응답에 섞이지 않는다.
이미 최종 응답을 보낸 뒤의 오류는 두 번째 응답을 만들지 않는다.

### T-24 Expect

클라이언트가 헤더만 보낸 상태에서 본문 전에 100을 받는다.
헤더 오류·크기 초과에서는 100 없이 최종 오류를 받는다.
본문이 이미 도착했거나 동시에 도착해도 교착·중복 최종 응답이 없다.
미지원 expectation은 417, 문법 오류는 400이다.
빈 본문·Expect 반복·중간 응답 부분 송신과 마감은 D-04·D-05의 판정대로 검사한다.

### T-25 HEAD

GET과 HEAD의 성공 표현 메타데이터를 비교한다.
200·3xx·400·403·404·405·413 등 HEAD로 판별 가능한 응답은 실제 본문 0바이트다.
Content-Length가 GET의 본문 길이를 나타내도 본문을 기다리지 않는 검증기를 사용한다.
HEAD echo는 Allow: POST가 있는 405이며 본문이 없다.
HEAD 때문에 파일 전체를 읽거나 불필요하게 스트리밍하지 않는다.

### T-26 자원과 연결 실패

recv EOF, 송신 half-close, RST, 읽기/쓰기 실패, 짧은 I/O, EINTR·EAGAIN을 구분한다.
완성 요청 후 송신 half-close에는 응답을 시도하고 미완성 요청은 성공시키지 않는다.
응답 중 RST 뒤에도 서버가 다음 연결을 처리해 SIGPIPE 정책을 검증한다.
정상·오류·중단 사이클 뒤 FD·메모리가 지속적으로 증가하지 않아야 한다.
부분 초기화·파일 탐색 실패에도 이중 close/free·미해제가 없어야 한다.

### T-27 정상 종료

**Phase 2 시작으로 이관. 아래 사례를 Phase 1 필수 게이트에 포함하지 않는다.**
Phase 1 테스트 하네스의 자식 프로세스 강제 회수는 정상 종료 기능의 통과가 아니다.

accept 대기·헤더 수신·본문 수신·응답 송신 단계 이벤트를 받은 뒤 SIGINT/TERM을 보낸다.
새 연결 수락 중단, 완료 가능한 현재 요청, 최대 30초 유예를 검사한다.
기존 더 이른 타임아웃과 반복 시그널이 마감을 연장하지 않는다.
종료 통지가 check-then-wait 틈에서 유실되지 않음을 제어된 이벤트로 검사한다.
모든 서버·파일·연결·테스트 자원을 회수하고 종료 코드/진단을 기록한다.
컨테이너 종료 경로에서도 서버가 SIGTERM을 전달받고 기존 30초 유예를 검증할 수 있는지 확인한다.
Docker의 중지 유예·강제 종료 설정은 D-07에서 서버의 종료 계약과 맞춘다.

### T-28 JSONL과 내부 로그

각 기록을 독립 JSON으로 파싱하고 필수 필드·타입·단위를 검사한다.
query·본문·Authorization·Cookie·실제 파일 경로 canary가 접근 로그에 없는지 검사한다.
따옴표·개행·제어문자·비정상 바이트로 위조된 로그 줄을 만들 수 없어야 한다.
HEAD·100·부분 송신·파싱 실패·RST에서 상태와 송신량이 정확해야 한다.
로그 출력 실패·출력 backpressure에서도 무한 대기·무한 버퍼링이 없어야 한다.
정확한 스키마·출력 실패 정책은 D-06을 닫은 뒤 고정한다.
최종 200 헤더를 보낸 뒤 본문이 잘린 경우를
최종 상태가 없었던 연결과 구분하고 완전 송신 여부가 드러나는 계약으로 검증한다.
원래 합의는 로그 항목의 의미이지 특정 JSON 키 이름이나 body-only 바이트 단위가 아니다.
진단 로그에도 민감 본문·인증정보가 새지 않는지 검사하고 필요한 내부 진단까지 일괄 금지하지 않는다.

### T-29 메모리와 필수 게이트

단위·통합·보안 스위트와 sanitizer 경로를 연결한다.
정상뿐 아니라 파서 오류·크기 초과·링크 실패·RST의 정리도 검사한다.
시그널 정상 종료의 정리 검증은 Phase 2 시작의 T-27과 결합한다.
ASan/누수 검사 도구의 실제 지원을 컨테이너의 이미지·아키텍처·컴파일러별로 확인한다.
미지원이면 사용 가능한 대체 도구와 증거를 정하거나 BLOCKED로 남긴다.
검사 옵션을 붙여 빌드한 것만으로 누수 검사가 실행됐다고 하지 않는다.

### T-30 성능 기준선

6절 프로토콜로 정적 GET과 echo를 분리 측정한다.
처리량·지연·오류·메모리·FD와 실제 실행 명령을 저장한다.
Phase 1에서 동시성·keep-alive를 구현했다고 주장하지 않는다.
비교할 수 없는 설정의 결과는 별도 실험으로 구분한다.

### T-31 환경별 재현성

호스트 OS·실제 Linux 커널·CPU 아키텍처·Docker 버전·이미지 식별자·컴파일러·Python·빌드 옵션을 기록한다.
마운트의 종류·파일 시스템·권한, 포트·네트워크 구성, CPU·메모리·FD 제한과 실제 명령·exit code·결과 파일을 보관한다.
권한·링크 fixture는 실제 제공 경로의 마운트 조건에서 수행하고 제약을 명시한다.
미검증 이미지·커널·마운트 조건을 검증한 것으로 표시하지 않는다.

### T-32 추적과 누락 검토

P1-01~P1-32 각각에 아키텍처 위치·테스트 그룹·실제 구현/결과가 연결돼야 한다.
요구사항 제목의 P1 ID 32개와 이 문서의 추적표·진행 원장의 행이 일치하는지 확인한다.
D-01~D-08과 AGENTS 진행표의 상태가 증빙과 일치하는지 검토한다.
나열된 시나리오가 모두 구현됐는지 확인하고 문서의 제목 존재만으로 PASS 처리하지 않는다.
전체 과제의 Phase 2·3 항목이 구현 완료로 오인되지 않아야 한다.
P1-27/T-27의 Phase 2 이관을 누락·PASS로 오인하지 않고 Phase 1 게이트에서만 제외했는지도 확인한다.

## 6. 성능 측정 프로토콜 초안 D-08

아래 수치·도구 선택은 인터뷰 확정이 아닌 초기 제안이다.
처음 측정 전에 고정하고 후속 비교에서도 같은 프로파일을 사용한다.

- 최적화 빌드와 검사 빌드를 분리하고 컴파일 명령·버전을 기록한다.
- 정적 GET: 작은 파일, 중간 파일, 1 MiB 초과 큰 파일을 구분한다.
- echo: 0·1 KiB·64 KiB·1 MiB를 구분한다.
- echo CL과 chunked는 독립 측정한다.
- Phase 1의 기본 프로파일은 동시 활성 클라이언트 1, 매 요청 새 연결이다.
- 단계별 비교용 반복 수·워밍업·측정 기간·seed를 측정 전에 정한다.
- 처리량은 성공 요청/초, 실패 수·원인·타임아웃도 별도로 남긴다.
- 지연은 클라이언트 관측 완료 기준의 p50·p95·p99와 표본 수를 기록한다.
- 메모리는 측정 도구·단위와 함께 안정 상태/최고치를 기록한다.
- FD는 기준·실행 중·종료/정리 후를 관찰하고 지속 증가 여부를 검사한다.
- 로그 켜짐 여부·목적지, warm/cold 파일 캐시 조건, 부하 발생기의 CPU 포화를 기록한다.
- 도구가 현재의 Connection: close·바이너리·chunked 사례를 실제 생성하는지 확인한다.
  불가능한 workload를 지원하는 것처럼 보고하지 않는다.
- Phase 2에서는 같은 close 프로파일의 N 확장과 별도 keep-alive 프로파일을 나눈다.
- 기준선의 Linux 컨테이너 환경·호스트·이미지·마운트·네트워크·자원 제한을 D-08에서 고정한다.
  다른 환경에서 측정하면 결과를 분리하고 같은 환경의 후속 결과와 비교한다.
- 동적 포트/포트 예약·READY 메시지의 실제 포트 전달 방식과
  생산 설정과 테스트 전용 시계/제한의 차이를 D-07·D-08에서 고정한다.

특정 RPS·C10K·고정 지연을 Phase 1의 임의 합격선으로 추가하지 않는다.
다만 바이트 오류·예상 밖 상태·자원 누수·무한 대기를 좋은 RPS로 덮지 않는다.

## 7. 증빙 저장과 완료 판정

[Phase 1 마무리 계획](PHASE_1_FINISH_PLAN.md)에 D-01/D-02/D-04의
디렉터리·링크·MIME·경로·응답 순서 예상값을 기록했다. 결정은 실행 증빙과 구분한다.

구현 단계에서 `artifacts/phase1/<환경>/<실행ID>/` 같은 결과 위치를 정한다.
현재 이 경로나 결과 파일은 생성되지 않았다.
원문 본문·인증정보·민감한 파일 내용을 결과에 무조건 덤프하지 않는다.

각 실행에는 다음이 필요하다.

| 항목 | 내용 |
| --- | --- |
| 식별 | 날짜, 플랫폼, 소스 상태/변경 식별자 |
| 명령 | 실제 작업 디렉터리·명령·옵션·도구 버전 |
| 결과 | exit code, PASS/FAIL/NOT_RUN/BLOCKED, 실패 사례 |
| 근거 | 원시 결과/요약 경로, 해당 P1·T ID |
| 제약 | 검사기 지원·권한·파일 시스템·플랫폼 미접근 |

AGENTS에는 요약과 경로를 남기고 대용량 로그를 붙이지 않는다.
설계됨·코드 구현됨·실행 통과·플랫폼 검증됨은 서로 다른 상태다.
Phase 1 범위의 필수 보안 실패, D 결정 차단, 플랫폼 증빙 누락이 있으면 Phase 1 완료가 아니다.
Phase 2 시작으로 이관한 P1-27/T-27의 미실행은 Phase 1 완료 차단 사유가 아니다.
