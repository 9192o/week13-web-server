# 1. 목적과 문서 범위

> **표준 C 라이브러리와 POSIX API를 사용하여 HTTP 웹서버를 직접 구현한다.** 구현 범위는 정적 파일 제공, 동적 요청 처리, 동시 요청 처리와 함께 Forward Proxy 또는 Reverse Proxy 중 하나 이상을 구현한다.

## 요구 수준

| 구분     | 의미                              |
| ------ | ------------------------------- |
| 필수     | 모든 구현에서 충족해야 한다.                |
| 조건부 필수 | 해당 구현 방식을 선택했을 때 충족해야 한다.       |
| 권장     | 원문에서 권장하거나 가능하면 구현하도록 제시한 항목이다. |
| 선택     | 기본 범위 외 확장 기능이다.                |
| 결정 필요  | 구현 전에 정책을 정하고 문서화해야 하는 항목이다.    |

## 2. 기술 제약 및 실행 환경

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| ENV-01 | 필수 | 서버 구현 언어는 C로 한다. | 서버 소스와 빌드 구성을 확인한다. |
| ENV-02 | 필수 | 네트워크와 요청 처리는 표준 C 라이브러리 및 POSIX API로 직접 구현한다. | 소켓 처리, HTTP 파싱, 응답 생성 및 프록시 중계 코드를 확인한다. |
| ENV-03 | 필수 | 완성된 HTTP 서버·프레임워크·이벤트 루프 라이브러리를 사용하지 않는다. 금지 예시는 libevent, libuv, nginx, Apache, mongoose다. | 의존성과 링크 옵션에 금지 라이브러리가 없고, 해당 기능을 외부 서버에 위임하지 않는다. |
| ENV-04 | 필수 | Makefile 또는 CMakeLists.txt를 제공한다. | 문서화된 빌드 명령으로 실행 파일을 생성한다. |
| ENV-05 | 필수 | 웹서버는 Linux Docker 컨테이너 안에서 실행한다. 이는 과제의 POSIX 실행 환경 선택을 구체화한 사용자 확정 정책이다. 호스트 OS의 네이티브 실행은 필수 지원 범위가 아니다. | 컨테이너 안에서 빌드·실행·검증하고 호스트·커널·이미지·도구 정보를 기록한다. |
| ENV-06 | 필수 | 여러 OS를 대상으로 할 때 POSIX 표준 범위를 사용하거나 OS별 차이를 조건부 컴파일로 분리한다. | 지원 OS와 제한을 명시하고, 지원한다고 명시한 환경의 빌드·실행 결과를 기록한다. |
| ENV-07 | 필수 | 포트와 정적 파일 루트를 CLI 인자 또는 설정 파일로 받는다. | 소스 수정 없이 포트와 루트를 변경하여 실행한다. |
| ENV-08 | 조건부 필수 | Reverse Proxy를 선택하면 라우팅 규칙도 CLI 인자 또는 설정 파일로 받는다. | 소스 수정 없이 라우팅 대상을 변경한다. |

부하 테스트에 Apache Bench를 사용하는 것은 서버 구현에 Apache를 사용하는 것과 구분한다.
검증 도구와 서버의 런타임 의존성은 별도로 기록한다.

## 3. 공통 기능 요구사항

### 3.1 TCP 서버와 입출력

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| TCP-01 | 필수 | `socket()` → `bind()` → `listen()` → `accept()` 흐름을 직접 구현한다. | 지정 포트에 리슨하고 실제 클라이언트 연결을 수락한다. |
| TCP-02 | 필수 | 연결된 클라이언트의 요청을 수신하고 응답을 송신한다. | 실제 HTTP 클라이언트로 요청과 응답을 주고받는다. |
| TCP-03 | 필수 | 한 번의 수신·송신으로 전체 메시지를 처리할 수 있다고 가정하지 않는다. | 요청을 여러 조각으로 보내도 파싱하며, 부분 송신 시 남은 데이터를 처리한다. |
| TCP-04 | 필수 | 바인드 실패, 입출력 실패, 연결 종료 시 오류를 처리하고 자원을 회수한다. | 사용 중인 포트, 클라이언트 연결 해제 등의 상황에서 원인을 확인할 수 있고 서버가 비정상 종료하지 않는다. |
| TCP-05 | 결정 필요 | 블로킹·논블로킹 모드와 `SO_REUSEADDR` 적용 정책을 정한다. | 선택 이유, `accept()`의 대기 동작, 서버 재시작 시 동작을 설명하고 확인한다. |

### 3.2 HTTP 요청 파싱

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| REQ-01 | 필수 | 요청 라인에서 메서드, URI, HTTP 버전을 분리한다. | 정상 요청과 형식이 잘못된 요청을 단위 테스트로 구분한다. |
| REQ-02 | 필수 | 최소 GET과 POST를 지원한다. | GET 응답과 POST 본문 처리를 실제 요청으로 확인한다. |
| REQ-03 | 필수 | 헤더를 파싱하고 `Host`, `Content-Length`, `Connection`을 처리한다. | 헤더 이름의 대소문자 차이와 정상 헤더 값을 처리한다. |
| REQ-04 | 필수 | 요청 라인, 헤더, 본문의 경계를 식별한다. | 헤더 종료 구분자가 수신 경계에 걸쳐 있어도 처리하고, 미완성 헤더를 완성된 요청으로 취급하지 않는다. |
| REQ-05 | 필수 | `Content-Length`에 따라 POST 본문의 바이트 수를 처리한다. | 본문이 분할 수신되거나 헤더와 함께 수신되어도 지정 길이만큼 처리한다. |
| REQ-06 | 필수 | 잘못된 요청, 비정상 메서드, 잘못된 버전을 안전하게 처리한다. | 정의한 오류 정책대로 응답하거나 연결을 정리하며, 충돌·버퍼 초과가 발생하지 않는다. |
| REQ-07 | 필수 | 매우 긴 URI, 큰 본문, 불완전한 요청에 대한 제한과 처리 정책을 둔다. | 경계값과 초과값을 검증하고, 무제한 메모리 사용이나 무기한 자원 점유를 방지한다. |
| REQ-08 | 결정 필요 | 지원 HTTP 버전과 요청 프레이밍 범위를 정한다. 잘못되거나 중복된 `Content-Length`, 지원하지 않는 전송 방식의 처리도 명시한다. | 지원 범위 밖 요청을 정상 요청으로 오해하지 않고 일관되게 거부·종료한다. |
| REQ-09 | 결정 필요 | `Connection: keep-alive`의 연결 재사용 정책을 정한다. | 재사용 지원 시 같은 연결의 후속 요청을 처리한다. 미지원 시 `Connection: close`를 알리고 응답 후 닫는다. |

HTTP 명세의 학습 범위는 과제에서 제시한 RFC 7230~7235를 바탕으로 한다.
전체 HTTP 규격 구현을 완료 조건으로 삼지는 않는다.
keep-alive 연결 재사용, chunked 전송, 파이프라이닝의 구현을 자동으로 필수 범위에 포함하지 않는다.
다만 지원하지 않는 입력을 어떻게 처리하는지는 명시해야 한다.

### 3.3 HTTP 응답 생성

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| RES-01 | 필수 | HTTP 버전, 상태 코드, 사유 구문을 포함한 상태 라인을 생성한다. | `HTTP/1.1 200 OK` 등 유효한 상태 라인을 클라이언트가 해석한다. |
| RES-02 | 필수 | `Content-Type`, `Content-Length`, `Connection` 등 응답에 필요한 표준 헤더를 생성한다. | 본문 타입, 바이트 길이, 실제 연결 동작과 헤더 값이 일치한다. |
| RES-03 | 필수 | 헤더와 본문을 구분하여 전송하고, 텍스트 및 바이너리 본문을 처리한다. | 이미지에 널 바이트가 포함되어도 원본 바이트가 보존된다. |
| RES-04 | 필수 | 기본 오류 응답인 404, 403, 500을 제공한다. | 파일 없음, 접근 금지, 통제된 내부 오류 상황에서 대응 상태와 응답을 확인한다. |

서버가 직접 생성하는 응답과 프록시로 중계하는 응답의 처리를 구분한다.
프록시 응답은 원 서버의 상태와 본문을 보존하되, 중계에 필요한 헤더 처리는 프록시 정책으로 정한다.

### 3.4 정적 파일 제공

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| STATIC-01 | 필수 | 지정된 정적 파일 루트에서 요청 파일을 읽어 응답한다. | 서로 다른 루트로 실행했을 때 각 루트의 파일을 제공한다. |
| STATIC-02 | 필수 | HTML, CSS, JS, PNG, JPG 등의 확장자를 MIME 타입에 매핑한다. | 매핑 단위 테스트와 실제 응답의 `Content-Type`을 확인한다. |
| STATIC-03 | 필수 | 파일 없음, 접근 거부, 파일 처리 중 내부 오류를 구분한다. | 각 상황에서 404, 403, 500 정책을 검증한다. |
| STATIC-04 | 필수 | 지정 루트 밖 파일에 접근하지 못하도록 경로를 처리한다. | 상위 경로 이동 등 루트 이탈 요청으로 외부 파일이 노출되지 않는다. |
| STATIC-05 | 결정 필요 | `/`의 기본 문서, 디렉터리 요청, 심볼릭 링크, 알 수 없는 확장자 정책을 정한다. | 선택한 정책과 실제 응답이 일치한다. |

### 3.5 동적 요청과 동시성

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| DYN-01 | 필수 | 요청에 따라 애플리케이션 로직의 응답을 제공한다. CGI 실행 또는 백엔드 전달 등의 방식 중 하나를 선택할 수 있다. | 입력이 다른 동적 요청에 대해 의도한 응답을 확인한다. |
| DYN-02 | 조건부 필수 | 백엔드 전달을 동적 처리 방식으로 선택하면 메서드, 대상 경로, 필요한 헤더와 POST 본문을 전달한다. | 백엔드에서 수신한 요청과 클라이언트 입력을 비교한다. |
| CON-01 | 필수 | `fork()`, `pthread`, I/O 멀티플렉싱 중 하나 이상으로 동시 요청을 처리한다. | 여러 클라이언트가 동시에 접속하여 정상 응답을 받는다. |
| CON-02 | 조건부 필수 | I/O 멀티플렉싱 선택 시 `select()` / `poll()` / `epoll()` / `kqueue()` 등을 사용한 이벤트 루프로 여러 연결을 관리한다. | 여러 연결의 수신·송신과 종료가 이벤트 루프에서 처리된다. |
| CON-03 | 권장 | 멀티스레드 선택 시 요청 처리 스레드 풀을 고려한다. | 채택 여부와 자원 사용 측면의 이유를 기록한다. |
| CON-04 | 필수 | 선택한 모델에 맞게 연결과 공유 자원의 수명을 관리한다. | 요청 간 데이터가 섞이지 않고, 종료된 연결의 FD·메모리 및 해당되는 자식 프로세스·스레드 자원이 회수된다. |

CGI와 백엔드 전달을 모두 구현할 필요는 없다.
프록시 경로에서 동적 백엔드 응답을 제공하면 동적 요청 요구사항을 함께 충족할 수 있다.

## 4. 프록시 요구사항

### 4.1 공통

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| PROXY-01 | 필수 | Forward Proxy 또는 Reverse Proxy 중 하나 이상을 구현한다. | 선택한 방식의 전체 요청·응답 흐름을 실제 클라이언트와 원 서버로 확인한다. |
| PROXY-02 | 필수 | 목적지에 TCP 연결을 만들고 요청을 전달한 뒤 응답을 클라이언트로 중계한다. | 원 서버의 상태 코드와 본문이 보존된다. |
| PROXY-03 | 필수 | 중계 과정에서도 부분 수신·송신과 클라이언트 연결 종료를 처리한다. | 큰 응답과 전송 중 연결 해제 시 충돌하거나 자원이 누적되지 않는다. |
| PROXY-04 | 결정 필요 | 요청 대상 형식, `Host`, 연결별 헤더 처리 및 응답 종료 판단 기준을 정한다. | 백엔드가 해석 가능한 요청을 받고, 응답 경계를 넘겨 읽거나 응답을 조기에 자르지 않는다. |

### 4.2 Forward Proxy 선택 시

흐름: `클라이언트 → Forward Proxy → 원 서버`.
클라이언트를 대신하여 외부 서버에 접근한다.

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| FWD-01 | 조건부 필수 | 요청 URL에서 목적지 호스트와 필요한 포트·경로를 파악한다. | 서로 다른 목적지 URL에 대해 올바른 원 서버로 연결한다. |
| FWD-02 | 조건부 필수 | 원 서버로 HTTP 요청을 전달하고 응답을 중계한다. | 프록시를 명시한 실제 클라이언트 요청으로 GET 및 본문이 있는 POST를 검증한다. |
| FWD-03 | 선택 | 응답 캐싱 기능을 구현한다. | 구현 시 캐시 대상, 만료·무효화 정책과 적중·미적중 동작을 검증한다. |

HTTPS 터널링을 위한 CONNECT는 원문에 명시된 필수 기능이 아니다.

### 4.3 Reverse Proxy 선택 시

흐름: `클라이언트 → Reverse Proxy → 내부 백엔드 1..N`.
백엔드 서버를 대신하여 외부 요청을 받는다.

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| REV-01 | 조건부 필수 | 여러 내부 백엔드로 요청을 라우팅할 수 있다. | 구분 가능한 두 개 이상의 백엔드를 사용해 목적지 선택을 검증한다. |
| REV-02 | 조건부 필수 | 경로 또는 `Host` 헤더 기반 라우팅 규칙을 설계한다. | 예를 들어 `/api/*`, `/static/*` 또는 호스트별 요청이 설정한 대상으로 전달된다. |
| REV-03 | 조건부 필수 | 백엔드 무응답과 타임아웃을 처리한다. | 연결 실패 및 응답 지연 시 정의한 시간 제한·오류 정책에 따라 요청을 종료하고 자원을 회수한다. |
| REV-04 | 결정 필요 | 정적 파일을 프록시가 직접 제공할지, 백엔드로 전달할지 정한다. | 선택한 경로에서 정적 파일 제공 요구사항과 MIME·오류 응답을 충족한다. |
| REV-05 | 결정 필요 | 규칙 우선순위, 일치하지 않는 경로, 전달 경로 보존·변경 정책을 정한다. | 겹치는 규칙과 미일치 요청의 목적지 또는 오류 응답이 일관된다. |
| REV-06 | 권장 | 가능하면 Round-Robin 등 단순 로드 밸런싱을 구현한다. | 구현 시 반복 요청이 선택한 정책대로 여러 백엔드에 분배된다. |

두 프록시 방식의 동시 구현, 캐싱, 로드 밸런싱은 기본 필수 완료 조건과 분리한다.

## 5. 안정성 및 자원 관리

| ID | 수준 | 요구사항 | 검증 기준 |
| --- | --- | --- | --- |
| SAFE-01 | 필수 | 동적 메모리 할당과 해제를 대응시키고 버퍼 경계를 검사한다. | 정상·오류·연결 중단 경로에서 메모리 누수와 잘못된 접근이 검출되지 않는다. |
| SAFE-02 | 필수 | 파일, 소켓 등 획득한 자원을 성공·실패 경로 모두에서 회수한다. | 반복 요청과 연결 중단 후 열린 자원이 지속적으로 증가하지 않는다. |
| SAFE-03 | 필수 | `SIGINT`, `SIGTERM`에 안전하게 종료한다. | 연결 처리 중에도 선택한 종료 정책에 따라 프로세스와 자원이 정리된다. |
| SAFE-04 | 필수 | `SIGPIPE`를 무시하여 연결이 끊긴 클라이언트에 쓰더라도 서버 전체가 종료되지 않게 한다. | 응답 전송 중 연결을 끊은 뒤에도 다른 요청을 처리한다. |
| SAFE-05 | 결정 필요 | 요청 크기, URI·헤더·본문 길이, 동시 연결 수, 타임아웃, 종료 유예 정책을 정한다. | 값과 초과 시 동작이 문서화되어 있고 경계 테스트로 확인된다. |

제한값, 타임아웃 초, 목표 처리량 등 구체적인 수치는 원문에서 지정하지 않았다.
환경과 구현 모델에 맞게 정하되 임의의 수치를 과제 원문의 합격 기준으로 간주하지 않는다.

## 6. 품질 및 검증 요구사항

| ID | 수준 | 검증 영역 | 완료 기준 |
| --- | --- | --- | --- |
| QA-01 | 필수 | 단위 테스트 | HTTP 파서, MIME 매핑, 선택한 라우팅·프록시 전달 로직의 정상 및 오류 입력을 검증한다. |
| QA-02 | 필수 | 실제 클라이언트 기능 테스트 | curl, 브라우저 등으로 정적 파일, GET, POST, 동적 응답, 선택한 프록시 흐름을 검증한다. |
| QA-03 | 필수 | 동시 접속 테스트 | 여러 클라이언트가 동시에 정적·동적·프록시 요청을 보내 정상 응답과 요청 간 격리를 확인한다. |
| QA-04 | 필수 | 부하 테스트 | ab, wrk, hey 등으로 동시 요청 수를 바꾸어 처리량을 측정하고 명령, 환경, 결과를 기록한다. |
| QA-05 | 필수 | 메모리 검사 | Valgrind 또는 AddressSanitizer·LeakSanitizer 등으로 잘못된 접근과 누수를 검사하고 결과를 기록한다. |
| QA-06 | 필수 | 실패·경계 테스트 | 아래 시나리오를 실행하고 예상 결과와 실제 결과를 비교한다. |

### 필수 실패·경계 시나리오

- 잘못된 요청 라인, 비정상 메서드, 지원하지 않는 HTTP 버전.
- 불완전한 헤더, 헤더·본문의 분할 수신, 명시된 본문 길이보다 적게 보내고 연결 종료.
- 매우 긴 URI, 큰 요청 본문, 설정한 입력 제한의 경계값과 초과값.
- 없는 파일, 접근이 금지된 파일·경로, 통제된 내부 오류.
- 클라이언트의 갑작스러운 연결 종료 및 응답 중 연결 해제.
- Reverse Proxy 선택 시 백엔드 연결 실패, 응답 없음, 타임아웃.
- 동시 요청 중 다른 요청의 지연·실패가 발생하는 경우의 자원 회수.
- 요청 처리 중 `SIGINT`, `SIGTERM` 수신과 서버 종료.

부하 테스트는 측정 가능한 결과를 남기는 것이 필수다.
C10K 달성이나 특정 RPS 수치는 원문에 정해진 합격 기준이 아니다.

## 8. 설명해야 할 설계 근거

코드 동작과 함께 다음 내용을 설명할 수 있어야 한다.

- TCP 3-way handshake와 서버 소켓 생성·연결 수락 흐름의 관계.
- `SO_REUSEADDR`, bind 실패 원인, `accept()` 블로킹, 블로킹·논블로킹 차이.
- HTTP 요청 경계, `Content-Length` 기반 본문 처리, keep-alive의 의미와 선택한 처리 정책.
- 프로세스·스레드 풀·이벤트 루프의 트레이드오프와 C10K 관점의 자원 사용.
- Forward Proxy와 Reverse Proxy가 각각 누구를 대신하는지, 보안·로드 밸런싱·캐싱 측면의 용도.
- 메모리·FD 소유권, 오류·연결 중단 시 회수 방식, 시그널과 종료 정책.
- Linux 컨테이너에서 사용하는 POSIX·Linux 전용 API의 차이, 최소 커널·마운트 제약과 이식성 범위.

## 9. 최종 완료 조건 및 증빙

- 모든 공통 필수 요구사항을 구현하고 검증한다.
- 프록시 방식 하나 이상과 동시성 방식 하나 이상을 선택하여 해당 조건부 필수 요구사항을 충족한다.
- 결정 필요 항목의 정책을 확정하고 문서화한다.
- 빌드 및 실행 방법과 포트·루트·라우팅 설정 예시를 제공한다.
- 단위·기능·동시 접속 테스트 결과, 부하 측정 결과, 메모리 검사 결과를 남긴다.
- 실제 지원 범위와 알려진 제약을 명시하고, 권장·선택 기능의 미구현을 필수 기능 완료와 혼동하지 않는다.
- 이력서·포트폴리오에서 구현 범위, 설계 선택, 검증 결과와 성능 측정 조건을 재현 가능한 근거로 제시한다.
