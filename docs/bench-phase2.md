# Phase 2 기준선 부하 테스트

phase2(스레드 풀 + keep-alive)의 처리량과 지연을 재고, 순차 처리였던 phase1 과 비교한다.
phase3(프록시) 전에 스레드 풀 모델로 계속 갈지, 이벤트 루프로 바꿀지 판단할 근거를 남기는 것이 목적이다.

## 환경과 방법

| 항목 | 값 |
|---|---|
| 머신 | WSL2 (커널 6.6.87.2), Intel i7-1165G7 × 8 스레드, 메모리 7.6GB |
| 도구 | wrk 4.1.0, `-t 4 -d 10s --latency` (스레드 4개는 클라이언트, 나머지 코어는 서버 몫) |
| 대상 | 정적 파일 `index.html` (130 바이트) |
| 서버 | 일반 빌드 (`-O2`), 접근 로그는 `/dev/null` (로그 비용은 따로 한 조합) |
| 반복 | 조합마다 3번, 2xx 처리량이 중앙값인 회차를 표에 씀 |
| 커밋 | phase2 `9905f64` + TCP_NODELAY 수정, phase1 `cc05337` |

- 재현: `bench/run.sh` (결과는 `bench/results/phase2-baseline/`: `env.txt`, `runs.csv` 전 회차, `summary.csv` 중앙값,
  `logcost-summary.txt`. wrk 원본 출력 `raw/` 는 실행한 곳에만 남고 레포에는 올리지 않는다)
- keep-alive 없음은 wrk 에 `-H "Connection: close"` 를 줘서 잰다.
- **처리량은 2xx 기준**이다. wrk 는 503 도 요청으로 세므로, 전체 처리량과 503 수를 따로 적었다.
- 문서 루트는 `www/` 를 `/tmp` 로 복사해서 쓴다. 레포가 있는 `/mnt/d`(Windows 드라이브)는 파일 접근이
  요청마다 ms 단위라서, 그대로 쓰면 서버와 상관없이 약 3,000 req/s 에서 막힌다.
- 클라이언트와 서버가 같은 머신이라 CPU 를 나눠 쓴다. 높은 숫자(10만 이상)는 wrk 쪽 한계도 섞여 있다.
- 모든 조합에서 소켓 오류(connect/read/write/timeout)는 0 이었다 (`tcp_tw_reuse=2` 라 포트 고갈 없음).

## 측정 전에 고친 것: Nagle + 지연 ACK

스모크 측정에서 keep-alive 처리량이 비정상적으로 낮았다. 응답 헤더와 본문을 `send` 두 번으로 나눠 보내서
두 번째 조각이 클라이언트의 지연 ACK(~40ms)를 기다리고 있었다. 연결을 바로 닫으면 드러나지 않는다.
accept 한 소켓에 `TCP_NODELAY` 를 켜서 고쳤다 (워커 8, 동시 10, 5초).

| | keep-alive | Connection: close |
|---|---|---|
| 수정 전 | 184 req/s, p50 44ms | 37,965 req/s, p50 0.12ms |
| 수정 후 | **77,626 req/s**, p50 0.08ms | 38,333 req/s, p50 0.13ms |

기능 테스트에 "keep-alive 20개를 한 연결로 400ms 안에" 검사를 넣었다 (수정 전 1,048ms, 수정 후 121ms).

## 결과

### 1. 순차(phase1) vs 스레드 풀(phase2), keep-alive 없음

| 동시 | phase1 순차 | phase2 워커 8 | phase2 워커 64 |
|---:|---|---|---|
| 10 | 26,939 req/s · p50 0.26 · p99 0.48 | 38,187 · 0.13 · 0.39 | 37,648 · 0.13 · 0.37 |
| 100 | 27,430 · 3.35 · 12.74 | **64,634** · 0.94 · 3.23 | 53,701 · 0.80 · 5.13 |
| 1000 | 24,964 · 38.42 · 69.87 | **69,816** · 10.27 · 18.85 | 54,194 · 11.06 · 23.25 |

(처리량은 2xx req/s, 지연은 ms)

- 동시 1000 에서 처리량 2.8배, p50 지연 38ms → 10ms.
- 응답이 아주 작아서(130 바이트) 순차 처리도 2.5만 req/s 가 나온다. 차이는 처리량보다 **동시 연결이 늘 때 지연**에서 크다.
- 503 은 워커 8: 동시 100 에서 1,903건, 동시 1000 에서 11,321건. 워커 64: 7건, 10,771건.
  짧은 연결이 한꺼번에 몰리면 큐(64칸)가 순간적으로 찬다.

### 2. keep-alive 와 워커 수 (큐 64)

| 동시 | 워커 | keep-alive | 2xx req/s | 전체 req/s | 503 | p50 | p99 |
|---:|---:|---|---:|---:|---:|---:|---:|
| 10 | 8 | 있음 | 79,403 | 79,403 | 0 | 0.08 | 0.26 |
| 10 | 64 | 있음 | 74,802 | 74,802 | 0 | 0.09 | 0.43 |
| 100 | 8 | 있음 | 68,334 | 75,556 | 72,939 (9.6%) | 0.22 | **97.65** |
| 100 | 64 | 있음 | **145,420** | 145,420 | 0 | 0.31 | 26.03 |
| 1000 | 8 | 있음 | 65,571 | 72,576 | 70,468 (9.7%) | 15.26 | **196.22** |
| 1000 | 64 | 있음 | 125,428 | 131,306 | 59,074 (4.5%) | 0.99 | **161.88** |
| 100 | 8 | 없음 | 64,634 | 64,824 | 1,903 | 0.94 | 3.23 |
| 100 | 64 | 없음 | 53,701 | 53,701 | 7 | 0.80 | 5.13 |

- keep-alive 는 연결 수가 워커 수 이하일 때 효과가 크다: 워커 64 · 동시 100 에서 53,701 → 145,420 (2.7배).
- 연결 수가 워커 수를 넘으면 **워커 수가 곧 동시에 처리할 수 있는 연결 수**가 된다. 워커 8 은 동시 100 이든 1000 이든 약 6.5~8만에서 멈추고, 나머지 연결은 큐에서 기다리다 503 을 받는다.
- keep-alive 가 없을 때는 워커 8 이 64 보다 빠르다 (8코어에서 스레드 64개의 문맥 전환과 잠금 경쟁).

### 3. 큐를 키우면 (동시 1000, 큐 1024)

| 워커 | keep-alive | 2xx req/s | 503 | p50 | p99 |
|---:|---|---:|---:|---:|---:|
| 8 | 있음 | 75,009 | 0 | 0.17 | **1,290** |
| 64 | 있음 | 122,870 | 0 | 0.81 | **755** |
| 8 | 없음 | 63,344 | 0 | 10.34 | 20.08 |
| 64 | 없음 | 59,118 | 0 | 8.19 | 18.88 |

- 큐가 1000 연결을 다 받아 주니 503 은 사라진다. 대신 keep-alive 에서 **p99 가 0.2초 → 1.3초**로 늘어난다.
- 큐에서 기다리는 연결은 워커를 잡은 연결이 100번째 요청을 채우고 닫힐 때(`KEEPALIVE_MAX_REQUESTS`)까지 차례가 오지 않는다.
  즉 503 은 큐 크기 문제가 아니라 **워커 점유** 문제이고, 큐를 키우면 거절이 대기로 바뀔 뿐이다.

### 4. 로그 비용 (워커 8, 동시 100, keep-alive)

| 접근 로그 | 2xx req/s | p99 |
|---|---:|---:|
| `/dev/null` | 68,334 | 97.65 |
| 파일 | 64,228 | 108.72 |

- 파일 로그는 약 6% 느리다 (10초에 약 3,600만 바이트, 72만 줄).
- 이 조합의 keep-alive 닫힘 로그: 회차마다 `max` 약 6,500건, `eof` 약 20건, `idle` 0건.
  클라이언트가 쉬지 않으니 idle 로 닫히는 일은 없고, 연결은 100요청마다 강제로 교대된다.
  그 교대가 큐에서 기다리던 연결이 워커를 얻는 유일한 기회다.

## 정리

- 스레드 풀은 순차 처리보다 처리량 약 2.8배, 높은 동시성에서 지연 약 1/4.
- keep-alive 는 연결 수 ≤ 워커 수에서 처리량을 2.7배까지 올린다.
- 연결 수 > 워커 수이면서 keep-alive 이면 README "알려진 한계"의 워커 점유가 그대로 숫자로 나온다:
  큐 64 에서는 요청의 약 10% 가 503, 큐 1024 에서는 503 대신 p99 1.3초.
- phase3 참고: 프록시는 백엔드 응답을 기다리는 동안에도 워커를 붙잡는다. 이 측정에서 요청 하나를 처리하는 시간은
  0.1ms 안팎이지만, 백엔드가 수 ms~수십 ms 걸리면 같은 워커 수로 처리할 수 있는 양이 그만큼 줄어든다.
  phase3 뒤 같은 스크립트로 다시 재서 비교한다.
