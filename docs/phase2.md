## Phase 2: 동시성 (스레드 풀 + keep-alive)

phase 1 은 `accept → 읽기 → 처리 → 쓰기 → close` 를 연결 하나씩 순차로 돌렸다. 클라이언트 A 가 느리게 보내거나 큰 파일을 받는 동안
B, C 는 accept 조차 못 받고 줄을 선다. 이 문제를 **스레드 풀**로 풀고, 동시성이 생긴 뒤에야 안전해지는 **keep-alive** 와 **정상 종료**까지 붙였다.
외부 라이브러리 없이 pthread 와 POSIX 소켓 API 만 쓴다.

```
메인 스레드                                  워커 스레드 x N (기본 8)
accept → TCP_NODELAY → 큐에 push --> [연결 큐 64칸] --> pop → server_handle (keep-alive 루프)
              └ 큐가 가득 차면 기다리지 않고 503 후 close
```

- 유저 시나리오 5개(S1~S5)를 먼저 쓰고, 한 단위씩 "결정 → 구현 → 테스트" 순서로 만들었다. 시나리오가 그대로 기능 테스트가 된다.
- 연결 큐(`src/queue.c`)와 워커 풀(`src/pool.c`)을 나눠서, 큐는 소켓 없이 단위 테스트한다. `server_run` 은 accept 한 연결을 큐에 넣는 일만 한다.
- 처리 로직(파서, 정적 파일, CGI)은 phase 1 의 블로킹 코드를 그대로 재사용했다. 고친 것은 스레드 간에 공유되던 자원 두 군데(정적 파일 버퍼, CGI 의 fd 상속)와,
  keep-alive 를 위해 `server_handle` 을 요청을 반복하는 루프로 바꾼 것이다.
- **하지 않은 것:** `fork` 방식, `epoll` 이벤트 루프, TSan 검사 (맨 아래 "추후 작업").

| 과제 요구 | 선택 | 구현·검증 |

### 사용법

```sh
./server -p 8080 -r ./www -w 8 -q 64    # 워커 8개, 큐 64칸 (모두 기본값)
./server -w 2 -q 2                      # S3 시나리오: 워커 2, 큐 2
```

- `-w` 워커 수 1~256 (기본 8), `-q` 연결 대기 큐 칸 수 1~4096 (기본 64). 범위를 벗어나면 사용법을 출력하고 종료한다.
- 시간 제한은 빌드할 때 `-D` 로 바꿀 수 있다 (`make ftest` 가 짧은 값으로 빌드해서 시간 제한 시나리오를 몇 초 안에 돌린다).

| 상수 | 기본 | 기다리는 것 | 넘기면 |
| --- | --- | --- | --- |
| `HEADER_TIMEOUT_MS` | 5초 | 요청 라인 + 헤더 **전체** | 한 바이트도 없었으면 응답 없이 close, 일부라도 왔으면 **408** |
| `KEEPALIVE_TIMEOUT_MS` | 5초 | 응답 뒤 다음 요청의 **첫 바이트** | 응답 없이 close (408 아님) |
| `BODY_TIMEOUT_MS` | 10초 | POST 본문 전체 | **408** |
| `SEND_TIMEOUT_MS` | 30초 | 응답 하나(헤더 + 본문) 전체 | 그냥 close |
| `SHUTDOWN_TIMEOUT_MS` | 10초 | 종료 신호 뒤 처리 중인 연결 | 강제로 끊고 종료 (exit 2) |

접근 로그는 phase 1 형식에 몇 줄이 더 생겼다.

```
127.0.0.1:50210 "GET /index.html HTTP/1.1" 200 130
127.0.0.1:50311 "-" 503 176 (queue full)                         # 큐가 가득 차서 즉시 거절
127.0.0.1:50210 (keep-alive closed: idle, 3 requests, 6.2s)      # 이유: idle / eof / max / shutdown
shutting down: waiting for 1 connection(s) (up to 10s)           # 종료 신호 뒤 처리 중인 연결이 있을 때
forced close of 1 connection(s)                                  # 시간 초과나 두 번째 신호로 강제로 끊음
```

### 설계 결정과 이유

#### 동시성 모델

| 결정 | 선택 | 이유 | 대안 |
| --- | --- | --- | --- |
| 모델 | **스레드 풀**: 메인은 accept 만, 워커 N 개가 큐에서 연결을 꺼내 처리 | phase 1 의 블로킹 파서·정적 파일·CGI 코드를 그대로 쓴다. 스레드 수에 상한이 있고, 매뉴얼이 권장한다 | `fork`: 단순하고 격리되지만 연결마다 프로세스 비용이 들고 좀비 회수(`SIGCHLD`)가 필요하며, phase 3 의 라운드로빈 카운터 같은 공유 상태를 두기 어렵다. `epoll`: C10K 에 강하지만 읽기·쓰기·CGI 를 전부 논블로킹 상태 머신으로 다시 짜야 한다 |
| 워커 수·큐 | `-w` / `-q` CLI 옵션, 기본 **8 / 64**, 상한 256 / 4096 | 매뉴얼의 "CLI 인자로 받기". 테스트가 `-w 2 -q 2` 로 가득 찬 상황을 쉽게 만든다 | `#define` 만 (테스트용 빌드를 따로 만들어야 함) |
| 모듈 | `queue.c`(연결 큐) / `pool.c`(워커 생성·종료·join) 분리 | 큐 동기화를 소켓 없이 단위 테스트할 수 있다 | `server.c` 안에 함께 |
| 약점 | 느린 연결이 워커를 붙잡는다 (slow client → 워커 고갈, 이를 노린 공격이 slowloris) | 시간 제한으로 점유 시간에 상한을 두고, 큐까지 차면 503 으로 거절한다. **근본 해결은 아니다**: 시간 제한 전까지는 워커를 점유한다 | 이벤트 루프 (아래 "알려진 한계") |

#### 큐 동기화 (생산자-소비자)

메인(생산자)이 넣고 워커(소비자)가 꺼내는 고정 크기 원형 버퍼다. 세 도구가 각자 다른 문제를 막는다.

| 도구 | 막는 문제 |
| --- | --- |
| mutex | 여러 워커가 동시에 꺼내거나, 메인과 워커가 동시에 만져서 섞이는 것 (경쟁 조건) |
| `cond_wait` (`not_empty`) | 빈 큐를 "비었나?" 하고 계속 확인하는 **바쁜 대기** (CPU 100%, 잠금 방해) |
| `cond_signal` | 넣었는데 잠든 워커가 모르는 것. 넣을 때 한 명을 깨운다 |
| `cond_broadcast` | 종료할 때 잠든 워커를 전부 깨운다 (`queue_close`) |

- 닫힌 큐에서는 남은 항목이 있어도 `pop` 이 닫힘을 돌려준다. 남은 연결은 처리하지 않고 `queue_drain` 이 응답 없이 닫는다.
- 큐에 넣는 `push` 는 기다리지 않는다 (S3 에서 정한 대로 가득 차면 503). 기다리는 쪽은 `pop` 뿐이다.
- `cond_timedwait` 의 기준 시계는 `CLOCK_REALTIME` 이다. macOS 에는 `pthread_condattr_setclock` 이 없어서 단조 시계로 기다릴 수 없고, 이식성을 택했다.

#### 신호: 메인 스레드만 받는다

- 프로세스 대상 신호(Ctrl-C, `kill`)는 막지 않은 스레드 **아무나** 받는다. 워커가 받으면 메인의 `accept` 가 `EINTR` 로 깨어나지 않아서, 다음 클라이언트가 올 때까지 종료가 시작되지 않는다.
- 그래서 워커를 만들기 직전에 `pthread_sigmask` 로 `SIGINT`/`SIGTERM` 을 막고, 만든 직후 메인의 마스크를 복구한다. 새 스레드는 만든 스레드의 마스크를 물려받으므로, 워커는 막힌 채로 시작하고 메인만 신호를 받는다.
- 워커가 신호를 안 받으면 파일 전송이나 CGI 도중 `EINTR` 로 끊길 걱정도 사라진다.
- `main.c` 는 `SA_RESTART` 없이 핸들러를 등록한다. 핸들러는 플래그만 세운다 (`volatile sig_atomic_t`, 첫 신호 1, 두 번째 신호부터 2).

#### 느린 클라이언트 (S2)

| 결정 | 선택 | 이유 | 대안 |
| --- | --- | --- | --- |
| 시간 제한 방식 | `poll` 로 **헤더 전체**에 데드라인 | `SO_RCVTIMEO` 는 `read` 한 번 단위라서, 4초마다 1바이트씩 보내는 클라이언트(slowloris)가 워커를 영원히 붙잡는다. 전체 기준이면 5초에 끊긴다 | `SO_RCVTIMEO` (구현이 단순하지만 위 약점) |
| 아무것도 안 보낸 연결 | 응답 없이 close | 브라우저가 미리 열어 두는 연결(preconnect)에 408 을 보내지 않는다 | 408 응답 |
| 일부만 보낸 연결 | **408** | 요청을 시작했는데 제때 끝내지 못한 것이므로 이유를 알려 준다 | |

- **408 과 503 의 차이:** 408 은 클라이언트가 늦은 것이고, 503 은 서버가 꽉 찬 것이다.
- slowloris 는 기능 테스트로 확인한다. 헤더를 시간 제한의 1/10 간격으로 한 바이트씩 계속 보내도 제한 시간에 408 로 끊긴다.

#### 워커와 큐가 가득 찼을 때 (S3)

큐가 가득 찬 상황에서 accept 스레드가 기다리면 새 연결을 하나도 못 받고 listen backlog 만 쌓인다. 그래서 **큐에 넣지 않고 바로 503** 을 보내고 닫는다.
문제는 503 을 어떻게 보내고 닫느냐다. 요청 바이트를 읽지 않은 채 `close` 하면 커널이 FIN 대신 **RST** 를 보내고, 클라이언트는 이미 받은 503 을 버리고 `connection reset` 만 볼 수 있다.

| | ① 논블로킹 1회 + 도착분만 비우고 close (선택) | ② 기존 에러 경로에 짧은 제한 | ③ 503 없이 바로 close |
| --- | --- | --- | --- |
| 503 전송 | `MSG_DONTWAIT` 로 한 번 (수백 바이트라 새 소켓 버퍼에 다 들어감) | `send_all` 로 최대 약 100ms | 보내지 않음 |
| accept 가 멈추는 시간 | **0** | 503 하나당 최대 약 200ms (과부하일수록 악화) | 0 |
| 클라이언트가 503 을 볼 가능성 | 높음. 요청이 `close` 뒤에 도착하면 RST 가능 | 가장 높음 | 없음 (S3 기대와 다름) |

- 선택한 방식의 절차: 503 한 번 `send` → `shutdown(SHUT_WR)` → 이미 도착한 요청 바이트만 `recv(MSG_DONTWAIT)` 로 비움 → `close`. 어느 단계도 기다리지 않는다.
- 남는 약점: 클라이언트가 연결하자마자 요청을 보내도 서버가 그 바이트보다 먼저 accept 하면 비울 것이 없고, 그 뒤 도착한 요청 때문에 RST 가 나갈 수 있다. 로컬 `curl` 에서는 드러나지 않았다.
- `Retry-After` 는 넣지 않았다. 다른 에러 응답과 같은 형식이고, 언제 자리가 날지 서버도 모른다.
- 로그 한 줄(`(queue full)`)로 거절된 연결을 구분한다.

#### keep-alive (S4)

phase 1 은 응답이 항상 `Connection: close` 였다. 순차 처리에서는 keep-alive 연결 하나가 서버를 독점하기 때문이다. 동시성이 생긴 뒤에야 지원할 수 있다.
keep-alive 의 전제는 **양쪽이 서로의 경계를 정확히 아는 것**이다. 응답의 끝은 `Content-Length` 로 클라이언트가 알고, 요청의 끝은 서버가 이번 요청을 끝까지 읽었을 때만 안다.

| 결정 | 선택 | 이유 |
| --- | --- | --- |
| 유지 조건 | HTTP/1.1 이고 `Connection` 에 `close` 토큰이 없을 때. HTTP/1.0 은 항상 close | 1.0 의 keep-alive 는 오래된 확장이라 범위 밖. `Connection` 헤더는 여러 줄·쉼표 목록·대소문자를 모두 검사한다 (`http_wants_close`) |
| 유지하는 응답 | 200, 301, 403, 404, 405 와 정상 실행된 CGI 응답 | 요청을 정상적으로 다 읽었다 |
| 닫는 응답 | 400, 408, 411, 413, 414, 431, 501, 505, 500, 전송 실패, 읽지 않은 본문이 있는 요청 | 요청이 깨졌거나 본문이 남아 있으면 다음 요청이 어디서 시작하는지 모른다 (남은 본문이 다음 요청으로 해석된다). 500 은 서버 상태가 의심스럽다 |
| idle 제한 | 다음 요청의 첫 바이트까지 5초, 그 뒤 헤더 5초 | idle 초과는 "다음 요청이 오는가"라서 응답 없이 닫고, 헤더 초과는 "온 요청이 제때 다 오는가"라서 408 이다 |
| 연결당 최대 요청 | 100개. 100번째 응답에 `Connection: close` | 한 클라이언트가 워커를 무한정 붙잡지 못하게 한다 |
| 응답 헤더 | 유지할 때는 `Connection` 헤더를 생략, 닫을 때만 `Connection: close` | HTTP/1.1 의 기본값이 유지다 |
| 닫힘 로그 | idle / eof / max / shutdown 일 때 연결당 한 줄 (요청 수, 유지 시간) | 부하 테스트에서 연결이 워커를 얼마나 붙잡았는지 볼 단서다 |

**pipelining.** 클라이언트가 응답을 기다리지 않고 요청을 연달아 보내면, 한 번의 `read` 에 다음 요청 일부가 같이 들어온다.

```
buf: [ 요청1 헤더 | 요청1 본문 | 요청2 시작... ]
     └──── consumed ────────┘└─ have ─┘
```

- 이번 요청이 쓴 바이트(`consumed` = 헤더 + 본문)만 소비하고, 나머지는 `memmove` 로 버퍼 앞으로 옮겨 다음 요청의 시작(`have`)으로 넘긴다. phase 1 은 연결을 닫았으니 남은 바이트를 버려도 됐지만, keep-alive 에서는 버리면 다음 요청이 사라진다.
- `have > 0` 이면 소켓에서 기다리지 않는다. 그 요청은 이미 버퍼에 있어서 소켓에는 더 올 데이터가 없고, 기다리면 idle 제한까지 멈춘 뒤 연결을 닫아 버린다. **기다릴지는 소켓이 아니라 버퍼에 남은 바이트로 먼저 정한다.**
- POST 본문 뒤에 붙어 온 다음 요청도 같은 방식으로 이어진다 (`read_cgi_body` 의 `consumed`).

**idle 의 대가.** 응답 뒤 기다리는 동안 워커 하나가 통째로 묶인다. 워커 8개에 가만히 있는 브라우저 8개면 새 연결은 큐에서 기다리고, 큐까지 차면 503 이다.
idle 시간은 "keep-alive 효과 ↔ 워커 점유 비용"의 손잡이다 (연결마다 스레드를 쓰는 Apache 는 기본 5초, 이벤트 루프인 nginx 는 75초).
종료 신호를 받으면 워커는 신호를 막아 두었으므로 `poll` 이 깨지 않는다. 그래서 idle 대기를 200ms 로 쪼개 종료 플래그를 확인하고, 켜져 있으면 쉬는 연결을 바로 닫는다. 종료 중에 나가는 응답에는 `Connection: close` 를 붙인다.

#### 정상 종료 (S5)

```
SIGINT  → 핸들러: server_stop = 1 (두 번째부터 2)
        → 메인 스레드의 accept 가 EINTR 로 깨어나 accept 루프를 빠져나옴
server_run
  1. close(listen_fd)           새 연결은 바로 Connection refused
  2. queue_close + queue_drain  큐에서 기다리던 연결은 응답 없이 닫음
  3. 처리 중인 연결이 있으면 "waiting for N connection(s)" 로그
  4. pool_stop(10초, &server_stop): 200ms 마다 워커가 다 끝났나 / 시간이 지났나 / server_stop >= 2 인가
       다 끝남                    → join → exit 0
       시간 초과 또는 두 번째 신호 → 처리 중인 연결을 shutdown(SHUT_RDWR) → join → exit 2
```

| 결정 | 선택 | 이유 | 대안 |
| --- | --- | --- | --- |
| listen 소켓 | accept 루프를 나오자마자 닫는다 | 커널은 handshake 를 끝낸 연결을 accept 전에도 받아 준다. listen 을 join 뒤에 닫으면 그 사이 들어온 연결은 refused 가 아니라 대기하다 끊긴다. 닫으면 backlog 에 남은 연결은 RST | 워커 join 뒤에 닫기 |
| 강제 종료 | 처리 중인 연결 **소켓을 `shutdown`** 한 뒤 join | 워커의 `send`/`poll` 이 곧바로 실패해서 빠져나온다. 자원이 정리되므로 ASan/valgrind 가 깨끗하다 | 프로세스 즉시 종료 (빠르지만 워커의 메모리·fd 가 정리되지 않은 채 끝남) |
| 종료 코드 | 정상 0, 시작 실패 1, **강제 종료 2** | 스크립트가 "강제로 끊었다"와 "아예 못 떴다"를 구분할 수 있다 | |
| 두 번째 신호 | 남은 대기를 건너뛰고 바로 강제 종료 | 10초를 기다리기 싫을 때 한 번 더 누르면 된다 | 무시 |
| 대기 방식 | `nanosleep` 으로 200ms 마다 확인 | `cond_timedwait` 는 macOS 에서 단조 시계를 쓸 수 없고, 200ms 지연은 종료에서 문제가 되지 않는다 | `cond_timedwait`, self-pipe |

**fd 번호 재사용 경쟁.** 강제 종료는 워커별로 기록해 둔 "처리 중인 fd"에 `shutdown` 을 건다. 워커가 `close` 를 먼저 하고 기록을 나중에 지우면, 그 사이에 같은 번호가 다른 워커의 CGI 파이프나 파일로 재사용되어 엉뚱한 fd 를 끊을 수 있다.
그래서 워커는 처리를 마치면 **mutex 안에서 기록을 먼저 지우고, 푼 뒤에 `close`** 한다. 강제 종료 쪽도 같은 mutex 를 잡은 채 `shutdown` 한다. 이 때문에 연결 fd 를 닫는 일은 처리 함수가 아니라 풀 한 곳에서만 한다.

#### 멀티스레드가 되면서 고친 공유 자원

| 문제 | 증상 | 고친 방법 |
| --- | --- | --- |
| 정적 파일 전송 버퍼가 `static char chunk[64KB]` (phase 1 은 순차라 공유 가능했음) | 워커 여러 개가 동시에 보내면 서로의 데이터를 덮어써서 응답 본문이 섞인다 | 함수 지역 배열(스레드 스택)로 바꿨다. 64KB 는 스레드 기본 스택(Linux 8MB, macOS 512KB)에 들어간다 |
| CGI 자식이 다른 워커의 fd 를 물려받음. fd 를 만들고 `FD_CLOEXEC` 를 거는 사이(accept 직후, `pipe` 직후)에 다른 워커가 `fork` 하면 그 fd 가 자식으로 넘어간다 | 다른 CGI 의 stdout 파이프 쓰기 끝이 남아 그쪽 응답에 EOF 가 오지 않고 시간 제한까지 멈춘다 | 자식이 `exec` 직전에 3번 이상 fd 를 모두 닫는다. `accept4`/`pipe2` 의 `O_CLOEXEC` 는 Linux 전용이라 쓰지 않았고, 모든 틈을 막는다 |

### 과제 중점 포인트와 이 구현

**소켓 프로그래밍의 기본 흐름**

- `socket → SO_REUSEADDR → bind → listen → accept` 는 phase 1 구현 그대로다. `SO_REUSEADDR` 는 재시작 직후 `TIME_WAIT` 이 남아 있어도 같은 포트에 `bind` 하게 한다.
- `accept` 는 블로킹이고 메인 스레드가 전담한다. 종료할 때는 `SA_RESTART` 없이 등록한 핸들러 덕분에 `EINTR` 로 깨어난다. 워커가 아니라 메인만 신호를 받아야 이 설계가 성립한다.
- 3-way handshake 는 커널이 `accept` 전에 끝낸다. 그래서 큐가 가득 차도 클라이언트는 "연결됨"을 보고, 서버가 503 으로 거절해야 비로소 알린다. 종료 때 listen 소켓을 먼저 닫는 이유이기도 하다.
- 블로킹과 논블로킹: 클라이언트 소켓은 블로킹으로 쓰되 `poll` 로 남은 시간만큼만 기다리게 해서 시간 제한을 건다. 503 만 `MSG_DONTWAIT` 로 한 번에 보낸다.
- `TCP_NODELAY`: 응답 헤더와 본문을 `send` 두 번으로 보내면 Nagle 알고리즘이 두 번째 조각을 클라이언트의 지연 ACK(약 40ms)까지 붙잡는다. 연결을 바로 닫으면 드러나지 않지만 keep-alive 에서는 요청마다 40ms 씩 늦어진다.
  부하 테스트에서 발견해서 accept 한 소켓에 `TCP_NODELAY` 를 켰다 (`<netinet/tcp.h>`, macOS/Linux 공통).

**HTTP 명세: 경계를 어떻게 식별하나**

- 응답의 경계는 `Content-Length` 다 (정적 파일은 파일 크기, CGI 는 출력을 다 모은 뒤 길이를 붙인다). 길이가 정확해야 같은 연결의 다음 응답과 섞이지 않는다.
- 요청의 경계는 헤더의 `\r\n\r\n` 과 `Content-Length` 다. 이번 요청이 쓴 바이트만 소비하고 나머지는 다음 요청에 넘긴다 (pipelining).
- `Connection: keep-alive` 는 "이 TCP 연결을 계속 쓰자"는 뜻이다. HTTP/1.1 은 기본이 유지이고, `close` 토큰이나 HTTP/1.0 이면 응답 뒤에 닫는다.

**동시성 모델의 트레이드오프**

| | `fork` (연결마다 프로세스) | 스레드 풀 (선택) | `epoll` 이벤트 루프 |
| --- | --- | --- | --- |
| 구현 | 가장 단순 | 큐 동기화가 필요, 처리 코드는 재사용 | 논블로킹 + 상태 머신으로 전면 재작성 |
| 격리 | 프로세스가 분리되어 한 연결이 죽어도 안전 | 같은 메모리를 공유해서 경쟁 조건을 직접 관리 | 한 스레드라 경쟁은 적지만 한 연결의 블로킹이 전체를 막음 |
| 비용 | 연결마다 프로세스, 좀비 회수 | 스레드 수에 상한 | 연결이 fd 하나라서 가장 가벼움 |
| 느린 연결 | 프로세스 하나가 묶임 | **워커 하나가 시간 제한까지 묶임** | fd 하나일 뿐 |
| C10K | 약함 | 워커 수가 동시 처리 상한 | 강함 |

- 이번에는 스레드 풀을 골라서 직선적인 블로킹 코드를 유지했다. 치른 것은 "워커 수 = 동시에 처리할 수 있는 연결 수"라는 상한이다. 측정으로 확인한 결과는 아래 "부하 테스트"에 있다.

**메모리·자원 관리, 클라이언트 끊김**

- 연결 fd 는 워커 풀이 **한 곳에서** 닫는다 (처리 중 기록을 지운 뒤 `close`). 처리 함수들은 닫지 않으므로 이중 `close` 나 누락이 생기지 않는다.
- 큐에 남은 fd 는 `queue_drain` 이 닫고, 워커·큐·mutex 는 `join` 뒤 모두 해제한다. 워커 생성이 중간에 실패하면 이미 만든 워커를 정리하고 시작 실패로 끝낸다.
- 클라이언트가 끊으면: 요청 사이에는 EOF 로 읽혀 `(keep-alive closed: eof)` 로, 전송 중에는 `send` 가 `EPIPE` 로 돌아와 `(aborted)` 로 정리된다 (`SIGPIPE` 는 무시하고 `MSG_NOSIGNAL` 을 쓴다).
- 응답을 읽지 않는 클라이언트는 전송 전체 제한(30초)에 끊긴다.
- 기능 테스트가 서버 프로세스의 `/proc/<pid>/fd` 개수를 시작과 끝에서 비교한다. S3, S5 용으로 따로 띄운 서버에도 같은 검사와 sanitizer 보고 검사를 한다.

**시그널·종료**

- `SIGPIPE` 무시, `SIGINT`/`SIGTERM` 은 메인 스레드만 받고 플래그만 세운다. 종료 순서와 강제 종료 조건은 위 "정상 종료"에 있다.

**엣지 케이스**

| 케이스 | 결과 |
| --- | --- |
| 연결만 열고 아무것도 안 보냄 | 약 5초 뒤 응답 없이 close, 그동안 다른 클라이언트는 바로 200 |
| 헤더를 한 바이트씩 천천히 (slowloris) | 헤더 전체 기준이라 5초에 408 |
| 워커와 큐가 모두 참 | 새 연결은 즉시 503, 큐에서 기다리던 연결은 워커가 비면 처리 |
| keep-alive 로 요청 사이에 가만히 있음 | 약 5초 뒤 응답 없이 close (408 없음) |
| 요청 여러 개를 한 번에 (pipelining), POST 뒤에 GET | 응답이 순서대로 |
| `Connection: close`, HTTP/1.0 | 응답 뒤 바로 close |
| 본문이 있는 GET | 읽지 않으므로 `Connection: close` 로 응답하고 닫음 |

| 응답을 안 읽는 클라이언트가 있는데 Ctrl-C | 약 10초 뒤 강제로 끊고 exit 2, 두 번째 Ctrl-C 면 바로 |
| 매우 큰 요청 본문, 긴 URI, 잘못된 요청 | phase 1 파서가 413/414/400 등으로 거절 (keep-alive 는 닫음) |

| 같은 조건에서 큐를 1024 로 키움 | 503 은 0건, 대신 p99 **1.3초** |
| 접근 로그를 파일로 남김 | 약 6% 느림 |

- **503 은 큐 크기가 아니라 워커 점유 때문이다.** 큐를 키우면 거절이 대기로 바뀔 뿐이다. 큐에서 기다리는 연결은 워커를 잡은 연결이 100번째 요청으로 닫힐 때까지 차례가 오지 않는다. 로그 비용 조합에서 닫힘 이유는 `max` 가 회차마다 약 6,500건이었고 `idle` 은 0건이었다.
- **워커 수는 한쪽이 항상 좋지 않다.** keep-alive 가 있고 연결이 많으면 64개가 유리하지만(동시 100: 68k → 145k), keep-alive 가 없으면 8개가 64개보다 빠르다 (8코어에서 스레드 64개의 문맥 전환과 잠금 경쟁).
- **측정이 찾아 준 것:** keep-alive 처리량이 비정상으로 낮아서 원인을 찾다가 위의 Nagle 지연을 발견했다 (동시 10에서 184 → 77,626 req/s). 또 레포가 WSL 의 `/mnt/d` 에 있으면 파일 접근이 병목이 되어 서버와 상관없이 약 3,000 req/s 에서 막혀서, 문서 루트를 `/tmp` 로 복사해서 쟀다.

### 알려진 한계

- **idle keep-alive 연결이 워커를 붙잡는다.** 워커 수만큼의 클라이언트가 가만히 연결만 열어 둬도 새 연결은 큐에서 기다리고, 큐까지 차면 503 을 받는다. 이벤트 루프는 쉬는 연결이 fd 하나라서 이 문제가 없지만, 읽기·쓰기·CGI 를 전부 논블로킹 상태 머신으로 바꿔야 한다.
  연결이 닫힐 때 남기는 `(keep-alive closed: ...)` 로그로 연결이 워커를 얼마나 붙잡았는지 볼 수 있다.
- **강제 종료가 CGI 실행 중이면 늦어진다.** 소켓을 끊어도 CGI 파이프를 기다리는 워커는 깨어나지 않아 CGI 시간 제한(5초)까지 더 걸릴 수 있다 (최악 10 + 5초). CGI 자식의 pid 를 워커마다 기록해 kill 하면 없앨 수 있지만 구조가 커져서 감수했다.
- **503 은 RST 에 질 수 있다.** 요청이 서버의 `close` 뒤에 도착하면 클라이언트가 503 대신 `connection reset` 을 볼 수 있다.
- **그대로 둔 것:** CGI 자식(`fork` 뒤)에서 `snprintf` 를 쓰는데 엄밀히는 async-signal-safe 가 아니다 (`posix_spawn` 이 대안). 본문 `malloc` 실패 경로의 `strerror` 는 스레드 안전이 보장되지 않는다 (`strerror_r` 이 대안).
