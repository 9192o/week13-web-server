# 팀 최종 제출 후보 공통 테스트

목적은 세 후보를 동일한 과제 계약과 관측 기준으로 비교하는 것이다. 이 문서는 테스트 계획이며 실행 결과가 아니다. 과제 범위는 [요구사항](REQUIREMENTS.md)의 공통·조건부 항목과 `QA-01`~`QA-06`을 참고한다. 다른 Phase 문서의 구현별 정책을 공통 합격 기준으로 가져오지 않는다.

팀원 컴퓨터에서 환경·시험 입력·기동 명령을 재현하려면 [공통 테스트 재실행 가이드](TEAM_COMMON_TEST_RUNBOOK.md)를 사용한다. 판정 기준은 이 계획 문서를 따른다.

## 1. 비교 대상과 실행 설정

원격 브랜치를 확인한 스냅샷이다. 실행할 때는 아래 SHA를 사용하고, 갱신본을 평가한다면 새 SHA를 남긴 뒤 동일한 계획으로 다시 실행한다.

| 최종 후보 | 커밋 SHA | 실행 설정에서 확인한 차이 | 기존 검증 진입점 예시 |
| --- | --- | --- | --- |
| `origin/eun/phase3` | `f4f33c7b843c52e27b3115a1359f5ee40ee5b910` | 단일 `server`에 정적·CGI·Reverse Proxy 기능. `-p`, `-r`, 반복 `-R`로 설정. 워커 스레드 풀. | `make test`, `make ftest`, `make valgrind` |
| `origin/feat/phase3/woong` | `01a2e8580eef90d118745ddf7f22e9804396f777` | 정적·동적 `webserver`와 `reverse-proxy`를 별도 실행. `--port`, `--root`, 반복 `--route`로 설정. Linux 이벤트 루프. | `make test-unit test-proxy-unit`, `make test test-shutdown test-epoll test-keepalive test-proxy`, `sh tests/verify_phase3.sh` |
| `origin/ldc` | `11080e4abee013a71245a7de8168e9d47e89c45b` | `server`에 정적·CGI·Reverse Proxy 기능. `--config`로 라우팅 설정. 이벤트 루프와 CGI 작업 풀. | `make test`, `make integration integration-p3 shutdown-test`, `make sanitize fdtest`, `make load proxy-load` |

`origin/main`은 구현 소스가 없는 기준 브랜치다. `origin/eun/phase1`, `origin/eun/phase2`, `origin/feat/phase1/woong`, `origin/feat/phase2/woong`은 각 최종 후보의 선행 브랜치라 중복 평가하지 않는다. 표의 실행 정보는 소스 트리·README·Makefile을 읽어 확인한 것으로, 테스트 통과를 뜻하지 않는다.

후보별로 **빌드·기동 명령, 포트, 정적 루트, POST 검증 경로와 기대 결과, 두 프록시 규칙, 백엔드가 받을 경로, URI·헤더·본문 제한, 타임아웃과 종료 유예, 연결 재사용 정책**을 한 장에 기록한다. 이 설정만 후보별로 다르고 아래 케이스 ID와 판정 기준은 같다. CGI와 로컬 동적 핸들러, 백엔드 전달은 모두 허용한다. 로컬 POST 엔드포인트가 없어도 백엔드가 입력에 따라 결과를 내는 경로로 동적 처리와 POST를 검증할 수 있다.

## 2. 공통 실행 환경과 입력

- 같은 Linux/amd64 환경에서 한 후보씩 실행한다. 이미지 식별자, 커널·컴파일러·도구 버전, 빌드 옵션, CPU/메모리/FD 제한, 실행 계정을 기록한다. 파일 권한 검사는 비특권 계정에서 한다. 테스트 트래픽은 격리된 로컬 환경에만 보낸다.
- 평가자가 만든 정적 루트 두 개에 같은 이름이지만 바이트가 다른 HTML 파일을 둔다. 기본 루트에는 CSS·JS·PNG·JPG, 널 바이트를 포함하는 이미지, 전송 중 종료를 재현할 수 있는 약 8 MiB의 큰 이미지도 둔다. 원본 크기와 SHA-256을 미리 기록한다.
- 평가자가 제어하는 백엔드 A/B는 고유 식별자와 요청 기록을 남긴다. 정상 응답 외에 `404` 응답, 큰 고정 길이 응답, 응답 헤더 지연, 본문 전송 중 종료를 재현할 수 있게 준비한다. POST 본문은 서로 다른 두 입력으로 시험한다(예: 짧은 텍스트와 널 바이트가 포함된 데이터). 별도 프록시 프로세스가 필요한 후보도 동일한 A/B에 붙인다.
- 보통 요청의 클라이언트 제한은 로컬 기준 5초, 요청·응답 지연 및 종료 시험의 관측 제한은 후보가 공개한 해당 최대 시간에 공통 여유 2초를 더한 값으로 사전 기록한다. 별도의 실행기 상한을 넘겨 종료한 경우 서버가 정상적으로 타임아웃을 처리한 것으로 보지 않는다. 수치는 팀 실행 기본안이며 과제 원문의 합격선이 아니다. 기준 변경은 후보 결과를 보기 전에 모두에게 동일하게 적용한다.
- `curl`로 정상 동작을 확인하고, 분할 전송·같은 소켓 재사용·중도 종료는 소켓 테스트 클라이언트로 확인한다. 상태 코드, 의미상 필요한 헤더, 실제 본문 바이트를 비교한다. 헤더 순서·대소문자, 사유 구문, 오류 문구, 합법적인 응답 프레이밍 차이는 고정하지 않는다.

## 3. 단위 테스트 — QA-01

후보의 단위 테스트를 실제로 실행한 뒤 각 ID를 테스트 이름과 연결한다. 기존 단위 테스트에 없다면 `커버리지 없음`으로 기록한다. 함수 이름, 내부 구조체, 스레드 수, assertion 수가 같을 필요는 없다. 통합 테스트 결과를 단위 테스트 증빙으로 대신하지 않는다.

| ID | 입력 → 확인할 계약 |
| --- | --- |
| U01 요청 줄 | 정상 GET/POST → 메서드·대상·버전 분리. 불완전하거나 형식이 잘못된 줄 → 완료로 처리하지 않음. |
| U02 헤더·본문 경계 | 대소문자가 다른 헤더 이름, 비어 있는 줄, 헤더 다음에 붙은 본문 → 헤더 의미와 본문 시작 위치 보존. 미완성 헤더 → 완료로 처리하지 않음. |
| U03 본문 길이 | `Content-Length`가 0인 경우, 정확한 길이의 바이너리 본문, 분할 입력, 잘못된 길이 또는 조기 EOF → 지정 바이트 보존 또는 거부·미완료의 구분. |
| U04 응답 생성 | 텍스트·바이너리·오류 응답 → 상태와 헤더를 파싱할 수 있고, 본문 프레이밍과 실제 바이트가 일치함. |
| U05 MIME·파일 오류 | HTML·CSS·JS·PNG·JPG → 해당 형식의 MIME. 없는 파일·접근 거부·통제된 I/O 실패 → 각각의 오류 의미 구분. |
| U06 목적지·중계 | 선택한 트랙에서 서로 다른 목적지 입력과 잘못된 설정 → 올바른 대상 선택 또는 오류. `GET`/`POST` 중계 데이터 → 메서드, 설정상 대상, 본문 길이·바이트 보존. |

## 4. 기능과 경계 사례 — QA-02, QA-03, QA-06

각 실패·경계 사례 뒤에는 **새 연결로 정상 GET을 한 번 더 보내** 프로세스 생존이 아니라 서비스 회복을 확인한다. 종료 시험은 종료를 확인한 뒤 재기동해서 정상 GET을 확인한다.

| ID | 재현 절차 | 통과 기준 |
| --- | --- | --- |
| F01 빌드·직접 실행 | 깨끗한 소스에서 문서대로 빌드. 포트와 정적 루트를 두 조합으로 바꿔 각각 실행. | 소스 수정 없이 지정한 포트에서 해당 루트의 파일을 제공. C, 빌드 파일, 금지 의존성 미사용, 소켓 흐름 직접 구현은 소스·빌드 설정으로 확인. |
| F02 정적 GET | 공통 루트의 HTML·CSS·JS·PNG·JPG 요청. | `200`, 올바른 MIME, 파일 해시 일치. `Content-Length`가 있다면 실제 바이트 수와 일치. 연결 종료·재사용이 광고한 정책과 일치. |
| F03 POST·동적 응답 | 기록한 POST 경로에 두 입력 전송. 한 번은 헤더와 본문을 함께, 한 번은 구분자·본문을 여러 쓰기로 나눠 전송. | 같은 입력은 분할 여부와 무관하게 같은 결과. 서로 다른 입력은 문서화한 결과로 구분되며, 위임 시 백엔드 기록이 받은 본문과 일치. |
| F04 파일 오류 | 없는 파일, 접근이 금지된 시험 파일, 제어된 내부 I/O 오류를 각각 검사. | `404`, `403`, `500`에 대응. `500`을 기능 시험에서 안정적으로 유발할 수 없다면 U05의 제어된 실패 실행 증빙을 연결하고 기능 항목은 `미실행`으로 분리. |
| F05 동시 처리 | 16개 클라이언트가 서로 다른 식별자나 파일을 섞어 정적·동적·프록시 요청. 별도로 요청 하나를 미완성 상태로 유지하고 정상 요청을 보냄. | 정상 응답이 시간 안에 완료되고 데이터가 다른 연결과 섞이지 않음. 미완성 연결 하나가 정상 클라이언트 전체를 막지 않음. |
| F06 프록시 왕복 | **Reverse:** 사용하는 규칙 유형(경로 또는 호스트)으로 A/B 지정. **Forward:** 실제 프록시 클라이언트 설정으로 A/B의 HTTP URL 지정. 각각 GET·POST를 보내고, A/B가 서로 다른 본문 및 `200`/`404`를 돌려주도록 함. | 올바른 A/B의 수신 기록에 메서드·설정에 따른 경로·POST 본문이 남고, 클라이언트에 백엔드 상태와 본문이 보존됨. 세 후보는 Reverse 트랙 적용. |
| F07 연결 정책 | 재사용을 지원한다고 선언한 모드에서, 동일 소켓에 응답을 하나씩 기다리며 연속 요청. 닫는 모드에서는 종료까지 관측. | 재사용 모드는 두 응답 모두 정상. 닫는 모드는 종료 정책과 응답 프레이밍이 일치. 파이프라이닝은 강제하지 않음. |
| E01 요청 오류 | 잘못된 요청 줄, 지원하지 않는 메서드·버전, 형식이 잘못된 길이 값을 개별 요청으로 검사. | 정상 요청으로 처리하지 않음. 문서화된 오류 응답 또는 연결 종료. |
| E02 요청 미완성 | 헤더 종료 전 연결 종료 또는 대기, 선언된 길이보다 짧은 POST를 보낸 뒤 쓰기 방향 종료. | 정상 동적 결과로 처리하지 않고, 정책에 따라 종료·정리. 백엔드에 보내기를 시작한 구현은 불완전한 전달도 종료해야 함. |
| E03 입력 한도 | 후보가 문서화한 URI·헤더·본문 한도에 대해 각각 `한도-1`, `한도`, `한도+1`을 시험. 다른 항목은 정상 범위 유지. | 문서화한 포함·초과 규칙과 일치. 오류에 특정 숫자 코드를 추가로 강제하지 않음. 정책이 없거나 경계를 확인할 수 없으면 미검증으로 기록. |
| E04 느린 수신·연결 중단 | 큰 파일을 천천히 읽어 끝까지 받고 해시 확인. 별도 요청은 응답 중 클라이언트를 닫음. 프록시를 거치는 큰 응답에서도 반복. | 완료된 응답은 잘리지 않음. 중단된 연결과 해당 백엔드 작업은 정책에 따라 정리되며 서버가 `SIGPIPE` 등으로 종료되지 않음. |
| E05 포트 충돌·종료 | 같은 주소·포트를 이미 점유한 상태에서 기동. 별도로 정상 기동 후 요청 처리 중 `SIGINT`, `SIGTERM`을 각각 시험. | 충돌 시 기동 실패를 확인할 수 있음. 종료 시 새 연결 수락을 멈추고, 진행 중 요청은 문서화된 유예 정책에 따라 완료 또는 정리. 자식·스레드·리스너도 남지 않음. |
| E06 백엔드 장애 | Reverse 트랙에서 시험 경로에 백엔드 하나만 지정. 백엔드 미기동, 연결 후 응답 헤더 무응답, 본문 중도 종료를 각각 시험. 이후 같은 주소로 백엔드를 복구. | 실패를 유한 시간 안에 처리하고 잘린 응답을 완전한 성공으로 전달하지 않음. 중계 자원을 정리하고 이후 요청이 복구됨. 상태 코드·재시도 방식은 문서와 대조. |
| E07 정적 루트 경계 | 루트 바깥에 평가용 임시 파일을 만들고, 루트 안에서 그 파일을 가리키는 시험 링크를 요청. | 루트 밖 파일의 내용이 노출되지 않음. 루트 안 링크의 지원 여부는 후보 정책에 따름. |

캐싱, 라운드 로빈, `HEAD`, chunked, `100 Continue`, 파이프라이닝 등은 **선언한 경우에만** 선택 검증으로 기록한다. 예를 들어 라운드 로빈은 단일 규칙에 건강한 A/B를 함께 등록해 순차 요청 10건을 보내고, 선언한 분배 정책과 A/B 수신 기록을 비교한다. 이 결과를 필수 항목과 섞지 않는다.

## 5. 부하 테스트 — QA-04

| ID | 워크로드 | 통제할 조건 |
| --- | --- | --- |
| L01 직접 정적 GET | 같은 1 KiB 정적 파일 요청 | 같은 원본 파일·해시·MIME |
| L02 프록시 경유 GET | 고정 백엔드 하나가 제공하는 같은 1 KiB 응답 중계 | 같은 독립 백엔드·고정 길이 응답. 로드 밸런싱이나 장애 재시도를 섞지 않음. 같은 조건의 백엔드 직접 측정도 기록. |

1. 최적화 수준을 맞춘 일반 빌드를 사용한다(예: 모두 `-O2`). sanitizer·Valgrind를 사용한 측정은 분리한다. 요청마다 새 연결을 사용하는 것이 기본이며, 클라이언트 keep-alive 비교는 모두 지원하는 경우 별도로 실시한다. 백엔드 연결 풀 등은 각 후보의 정상 구성대로 두고 설정값을 남긴다.
2. 팀이 고른 동일 도구(`ab`, `wrk`, `hey` 등)와 버전을 사용한다. 기본안은 **동시성 1·8·32, 조합마다 워밍업 100건 후 측정 2,000건, 3회 반복**이다. 도구는 고정 요청 수와 지연 백분위수를 기록할 수 있는 것으로 고른다. 총 요청 예산, 타임아웃과 로깅 조건을 통일하고 후보 실행 순서를 회차마다 바꾼다. 후보별 자원 한도·워커 설정은 결과를 보기 전에 고정한다.
3. 회차별 명령·경과 시간·성공/전체 건수·성공 건수 ÷ 경과 시간·p50/p95·오류율을 남긴다. 연결 실패, 타임아웃, 비정상 상태, 응답 길이 불일치는 성공에서 제외한다. 도구가 성공 요청만의 백분위수를 제공하지 않으면 백분위수의 집계 범위를 명시한다. 본문 해시는 측정 전후 기능 요청으로 확인한다. 로그가 뒷받침하지 않는 검증을 부하 도구가 수행했다고 기록하지 않는다.
4. 워크로드와 동시성별로 회차 값과 중앙값을 함께 비교한다. 부하 생성기나 공통 백엔드가 병목인 회차는 표기하고 같은 조건으로 재측정한다. 팀 기본안의 동시성이나 특정 RPS는 과제 원문의 탈락 기준이 아니다.

## 6. 메모리·자원 검사 — QA-05

| ID | 재현 절차 | 통과 기준 |
| --- | --- | --- |
| M01 메모리 접근·누수 | 각 후보의 **웹 서버와 프록시 실행 프로세스**를 같은 검사 방식으로 계측한다. 기본안: ASan + 누수 검사가 활성화된 Linux 빌드. 대안: Valgrind Memcheck로 동등한 케이스를 수행하고 사용 이유를 기록. 단위 스위트와 F02·F03·F04·F06·E02·E04·E06을 재실행하고, 도구가 종료 보고서를 남기도록 정상 종료. | 잘못된 메모리 접근과 손실된 할당이 보고되지 않음. 정상 종료 로그·도구 종료 상태·자식 프로세스 검사 범위를 보관. 검사 시작 실패나 종료 보고서가 없는 강제 종료는 통과가 아님. |
| M02 FD·작업 자원 | 예열 후 프로세스 트리의 FD·자식 수를 기준으로 기록. 정상 요청과 중도 종료를 100건씩 한 묶음으로 3회 반복. 직접 서버와 프록시를 각각 관측하고, 프록시는 백엔드 장애·복구도 포함. 각 묶음 뒤 같은 조건에서 유휴 상태로 복귀한 수치와 종료 후 잔류 프로세스를 기록. | 반복할수록 자원이 누적되지 않음. 연결 풀처럼 의도된 보유 자원은 설정 상한 안에서 안정화되고 종료 시 정리됨. FD 추세와 RSS 참고값을 메모리 검사 보고서 대신 쓰지 않음. |

메모리 검사 도구 자체의 오버헤드로 실패한 경우 일반 빌드 결과와 분리하고, 조정 근거를 남겨 동일한 재검증 정책을 적용한다. 서버가 단일 프로그램이면 정적·중계 경로를 모두 검사한다. 여러 프로그램이면 각각의 로그를 보관한다.

1. **공통 필수 기능과 선택한 트랙의 조건부 필수 기능**을 먼저 판정한다. 해당하지 않는 선택 기능은 `해당 없음`, 아직 입증하지 못한 필수 항목은 `미실행`이다. 대체 증빙을 허용한 항목은 연결된 증빙으로 판정하되, 하지 않은 검증 자체를 통과로 기록하지 않는다.
2. 단위 커버리지 누락, 반복 실패, 크래시·멈춤, 검사에서 확인된 접근 오류·누수와 복구 실패를 먼저 비교한다. 필수 실패나 미검증을 처리량으로 상쇄하지 않는다.
3. 필수 항목과 안정성 검증을 통과한 후보끼리 동일 부하 조건에서 성공 처리량·p95·오류율을 함께 비교한다. 차이가 반복 변동 폭 안이면 실행 재현성과 문서화가 더 나은 후보를 고른다. 추가 기능은 별도 메모로 남긴다.
