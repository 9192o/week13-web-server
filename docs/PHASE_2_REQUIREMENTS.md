# Phase 2 요구사항

**명세 확정: 2026-11-23.** 실제 실행 판정은 [Phase 2 검증](PHASE_2_TESTING.md)에
따로 기록한다.

전체 범위는 [과제 요구사항](REQUIREMENTS.md)을 따른다. Phase 2는 정상 종료,
다중 연결 동시 처리, HTTP/1.1 keep-alive 순으로 다룬다. 과제 필수 프록시는 Phase 3 범위다.
아래의 확정은 설계 합의를 뜻하며 구현·검증 완료를 뜻하지 않는다.
현재 코드 흐름은 [HTTP 서버 코드 읽기](../public/http-server-guide.html), 실행 결과는 검증 문서를 따른다.

## P1-27 — 정상 종료 (Phase 2 시작)

2026-11-23 인터뷰 합의. [Phase 1에서 이관한 P1-27](PHASE_1_REQUIREMENTS.md#정상-종료-p1-27)의
‘현재 요청’ 범위를 다음과 같이 정한다.

- `SIGINT` 또는 `SIGTERM`을 받으면 새 연결 수락을 중단한다.
- 요청 헤더를 아직 다 받지 못했거나 검증이 끝나지 않은 연결에는 유예를 주지 않고 HTTP 응답 없이 닫는다.
- 헤더 검증을 마친 요청은 본문 수신 중인 `POST /echo`와 응답 송신 중인 요청을 포함해 계속 처리한다.
  기존 마감과 종료 신호 후 30초 중 먼저 도달하는 시점까지만 허용하며 기존 마감을 연장하지 않는다.
- 진행 중인 요청이 모두 끝나거나 허용된 마감에 도달하면 자원을 회수하고 종료한다.
  유휴 `accept()`나 I/O 대기 중에도 종료 요청을 놓치지 않는다.

**검증 기준(T-27):** 두 신호 각각에 대해 유휴 대기, 미완성 헤더,
검증된 헤더 뒤 본문 대기, 응답 송신 중에 종료를 요청한다. 미완성 헤더 연결에는
HTTP 응답을 보내지 않는지, 유예 대상은 기한 내에 마칠 수 있는지,
기한을 넘기면 종료하는지, 새 연결을 처리하지 않는지 확인한다.

## P2-01 — `epoll` 기반 동시 연결 처리

2026-11-23 인터뷰 합의. `epoll`의 동작 원리를 학습하기 위해 Linux Docker에서
외부 이벤트 루프 라이브러리 없이 `epoll`을 직접 사용하는 이벤트 루프로 여러 연결을 관리한다.
전체 과제의 CON-01·CON-02·CON-04와 연결한다.

- Phase 2 필수 범위는 단일 프로세스·단일 스레드의 이벤트 루프 하나다.
  멀티프로세스·멀티스레드와의 조합은 후속 확장으로 남긴다.
- 서버는 `epoll`의 LT(Level-Triggered) 모드를 사용한다. 서버 코드에는 ET 전환 옵션을 추가하지 않는다.
- ET(Edge-Triggered)는 서버와 분리된 작은 실습에서만 다룬다. 동일한 입력에서 일부만
  읽고, 새 입력 없이 다시 대기했을 때 LT와 ET의 알림 차이를 관찰한다.

**검증 기준(T2-01):** 클라이언트 A가 `POST /echo` 본문 일부만 보낸 채
연결을 유지하는 동안 클라이언트 B의 `GET /`이 완료되어야 한다. 이후 A가 나머지
본문을 보내면 A는 자기 본문 그대로 응답받아야 한다.

## P2-02 — 동시 연결 한도와 수락 재개

2026-11-23 인터뷰 합의. 서버가 관리하는 클라이언트 연결 수가 한도에 도달하면
리스닝 소켓의 `epoll` 감시를 일시 중단하고 새 연결을 수락하지 않는다. 기존 연결은
계속 처리하고, 관리 중인 연결이 닫혀 빈자리가 생기면 감시와 수락을 재개한다.
정상 종료가 시작된 뒤에는 수락을 재개하지 않는다.

동시 연결 한도의 기본값은 256개이며, 실행 시 선택 인자 `--max-connections`로
변경할 수 있다. 한도는 서버가 수락하여 관리 중인 클라이언트 연결에 적용하며,
커널에서 수락을 기다리는 연결은 포함하지 않는다.

수락을 미룬 연결은 커널의 유한한 대기열에 맡긴다. 애플리케이션 대기열을 추가하거나
한도에 도달했다는 이유로 새 연결을 수락한 뒤 닫지 않는다. 대기열에 들어가지 못한
접속에 대해 서버는 특정 HTTP 응답이나 연결 실패 방식을 보장하지 않는다.

**검증 기준(T2-02):** 옵션을 생략하면 기본값 256이 적용되는지 확인한다.
`--max-connections 2`로 실행하고 두 연결을 유지한 채 세 번째 클라이언트가 요청을
보낸다. 기존 연결은 계속 처리하고, 세 번째 연결은 수락하지 않다가 한 자리가 비면
수락해 처리해야 한다. 종료 신호가 먼저 처리되면 자리가 비어도 추가 연결을 수락하지
않아야 한다.

## P2-03 — keep-alive 유휴 시간

2026-11-23 인터뷰 합의. 연결을 재사용할 수 있는 최종 응답의 송신을 마쳤다면
같은 연결에서 다음 요청이 시작되기를 최대 5초 기다린다. 그 안에 다음 요청이
시작되지 않으면 HTTP 응답을 추가로 보내지 않고 연결을 닫는다. 다음 요청이 시작되면
5초 유휴 제한 대신 요청 수신 마감을 적용한다.

**검증 기준(T2-03):** 응답 송신 후 5초 안에 같은 연결로 다음 요청을
시작하면 처리되는지 확인한다. 별도 연결에서 다음 요청을 보내지 않으면 유휴 마감에
연결이 닫히는지 확인한다.

## P2-04 — HTTP/1.1 파이프라이닝의 순차 처리

2026-11-23 인터뷰 합의. 재사용 가능한 연결에서 다음 요청의 바이트가 현재 요청과
함께 수신되거나 현재 응답이 끝나기 전에 도착해도 버리지 않는다. 한 연결에서는
한 번에 요청 하나만 처리하며, 현재 최종 응답의 송신을 마친 뒤 다음 요청을 처리한다.
이미 다음 요청 바이트가 있으면 유휴 대기 상태에 들어가지 않는다.
연결을 닫기로 했거나 정상 종료가 시작된 뒤에는 대기 중인 후속 요청을 시작하지 않는다.
응답 순서는 RFC 9112 §9.3.2를 따르며, HTTP/2 스트림 멀티플렉싱은 범위 밖이다.

**검증 기준(T2-04):** 같은 TCP 연결에서 첫 응답을 읽기 전에 결과가
서로 다른 두 `GET`을 보내고, 두 최종 응답을 요청 순서대로 받는지 확인한다.
첫 요청 처리에 필요한 바이트 뒤에 이미 수신된 다음 요청의 바이트도 보존해야 한다.

## P2-05 — 연결당 요청 수 상한

2026-11-23 인터뷰 합의. 첫 요청을 포함해 TCP 연결 하나에서 최대 100개 요청을
처리한다. `100 Continue` 같은 중간 응답은 요청 수에 별도로 포함하지 않는다.
다른 종료 조건에 먼저 해당하지 않으면 100번째 요청의 최종 응답에 `Connection: close`를
넣고, 응답 송신을 마친 뒤 연결을 닫는다. 이미 도착한 101번째 요청도 처리하지 않는다.
100개는 이 서버에서 정한 상한이며 HTTP/1.1 자체의 요구값이 아니다.

**검증 기준(T2-05):** 재사용 가능한 정상 요청 99개가 같은 연결에서 완료된 뒤,
100번째와 101번째 요청을 함께 보낸다. 100번째 최종 응답에 `Connection: close`가 있고
응답이 끝난 뒤 연결이 닫히며, 101번째 요청은 처리되지 않아야 한다.

## P2-06 — 오류 응답 뒤 연결 재사용

2026-11-23 인터뷰 합의. 요청 헤더가 유효하고 요청 경계까지 정상적으로 소비했다면
파일이 없어서 반환한 `404` 같은 애플리케이션 오류만으로 연결을 닫지 않는다.
요청 경계를 확정할 수 없거나 본문을 끝까지 소비하지 않았다면, 오류 응답을 보낼 수
있을 때 `Connection: close`를 붙여 보낸 뒤 닫고 후속 요청을 처리하지 않는다.
재사용 여부는 응답 상태 코드만으로 판단하지 않으며, 다른 종료 조건이 우선한다.
오류가 판정된 뒤 연결을 재사용할 목적으로 본문을 추가 수신하지 않는다.

**검증 기준(T2-06):** 본문 없는 유효한 `GET`의 `404` 뒤에 같은 연결에서
다음 `GET`이 처리되어야 한다. 반대로 잘못된 프레이밍이나 본문을 다 읽기 전에
종료되는 요청은 오류 응답 뒤 재사용할 수 없어야 한다.

## P2-07 — 요청당 접근 로그

2026-11-23 인터뷰 합의. P1-28의 stdout JSONL 기록 단위를 연결당 한 건에서
요청당 한 건으로 바꾼다. 같은 연결에서 두 요청을 처리하면 각각 한 건씩 기록한다.
후속 요청 없이 keep-alive 유휴 시간이 끝나 연결이 닫히는 경우에는 접근 로그를
추가하지 않는다. 기존 필드, 민감정보 제외, 진단 로그 분리 및 출력 지연 처리 정책은
P1-28을 유지한다.

**검증 기준(T2-07):** 같은 연결에서 서로 다른 두 요청을 처리하고 유휴
만료로 닫는다. 출력이 밀리지 않는 조건에서 stdout의 접근 로그가 요청별 두 건이며,
유휴 만료에 따른 세 번째 로그가 없는지 확인한다.

## P2-08 — 성능 비교 및 증빙

2026-11-23 인터뷰 합의. 같은 Linux Docker 환경에서 다음 세 조건을 비교한다.

| 조건 | 서버 | 연결 방식 |
| --- | --- | --- |
| A | Phase 1 블로킹 순차 서버 | 요청마다 새 연결 |
| B | Phase 2 LT `epoll` 서버 | 요청마다 새 연결 |
| C | Phase 2 LT `epoll` 서버 | HTTP/1.1 keep-alive로 연결 재사용 |

각 조건에서 정적 `GET`과 `POST /echo`를 따로 측정한다. 부하 단계별 처리량과
지연시간, 실패 수 및 원인을 기록한다. A와 B는 연결 방식을 맞춰 서버의 동시 처리
변경 전후를, B와 C는 같은 Phase 2 빌드에서 연결 재사용 유무를 비교한다.
C는 연결당 100개 상한에 도달하면 새 연결을 사용하고, 실제 재사용 여부를 확인한다.

**완료 증빙(T2-08):** [Phase 1 성능 측정 프로토콜](PHASE_1_TESTING.md#6-성능-측정-프로토콜-d-08)을
기준으로 비교에 사용한 소스 버전, Docker 환경, 빌드, 입력 크기, 동시 클라이언트 수,
로그·캐시 조건, 실행 명령 및 반복 결과를 남긴다. 서로 다른 환경에서 얻은 값을
개선율 계산에 섞지 않는다. 특정 RPS나 개선율은 합격선으로 삼지 않으며, 성능
측정으로 기능·자원 검증을 대신하지 않는다.

## P2-09 — 연결 중단 격리와 자원 회수

2026-11-23 인터뷰 합의. 동시 처리 중 클라이언트 하나가 연결을 끊어도 다른 연결의
요청은 정상 완료해야 한다. 끊긴 연결의 소켓·파일 FD와 요청 메모리는 회수한다.

**검증 기준(T2-09):** 요청 본문 수신 중 또는 응답 송신 중에 일부 연결을
끊고, 동시에 유지한 연결의 상태 코드와 응답 바이트가 예상과 일치하는지 확인한다.
이 시나리오를 반복한 뒤 모든 클라이언트 연결이 정리되면, 열린 FD 수가 같은 서버
실행의 `READY` 직후 유휴 기준치로 돌아와야 한다. 메모리 검사 도구로 정상 종료 후
누수나 잘못된 메모리 접근이 보고되지 않는지 확인한다.

## Phase 2 완료 판정

- Phase 1에서 유지되는 요청·응답 계약의 회귀를 확인한다. Phase 2에서 명시적으로
  바뀐 연결 종료와 로그 동작은 이 문서의 기준으로 판정한다.
- 별도 LT/ET 비교 실습의 관찰 결과와 P2-08의 성능 비교 결과를 남긴다.
- 미실행·실패·환경 제약은 통과와 구분해 기록한다. 명세 확정은 Phase 2의
  구현 또는 검증 완료를 뜻하지 않는다.
