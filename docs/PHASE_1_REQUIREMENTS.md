# 요구사항

제목의 P1 ID는 아키텍처·테스트·진행표의 추적 기준이다.
사용자 합의와 구현자 세부 정책을 구분한다. CLI·일반 정적 파일·연결 마감·JSONL은 구현되어 있다.
실행 증빙과 남은 검증은 [테스트 결과](PHASE_1_TESTING.md#7-실행-결과와-완료-판정)를 따른다.

## 스펙

### 구현 언어와 의존성 (P1-01)

- **서버는 C로 작성한다. 표준 C·POSIX API와 필요한 OS API를 직접 사용한다.**
- HTTP 파싱·응답·소켓 I/O를 외부 HTTP 서버, 프레임워크, 이벤트 루프에 위임하지 않는다. libevent, libuv, nginx, Apache, mongoose 등을 런타임 구현에 사용하지 않는다.
- Python·curl·부하 도구·메모리 검사기는 검증 도구이며 서버 의존성과 구분한다.

### 지원 플랫폼 (P1-02)

- **웹서버는 Linux Docker 컨테이너 안에서 작동한다.** 빌드·기능·보안·자원 검사와 성능 기준선도 해당 환경에서 수행한다.
- 기존 Linux/WSL2·macOS 네이티브 양쪽 지원·검증 조건을 이 정책으로 대체한다. 호스트 OS와 서버의 실행 환경을 구분하며, macOS 네이티브 구현·검증은 필수 범위가 아니다.
- 개발·검증 기준은 비특권 Linux/amd64 Docker와 C17이다. 정적 루트에는 Linux `openat2`(커널 5.6 이상에서 제공되며 컨테이너 정책이 허용해야 함)와 정상적인 `/proc/self/fd`가 필요하다. 시작 시 루트의 `openat2` 검사가 실패하면 종료한다.
- 검증한 정적 루트는 대소문자를 구분하는 컨테이너 overlayfs다. Windows 공유와 네트워크 파일 시스템을 정적 루트로 쓰는 구성은 검증 범위 밖이다.

### 빌드와 실행 설정 (P1-03)

- **Makefile을 제공하고 포트/정적 루트는 CLI로 받는다**. 설정 파일은 이후로 미룬다. CLI 명령 예시는 다음과 같다.
    
    ```bash
    ./webserver --port 8080 --root ./www
    ```
    
- 실행 파일 이름은 `webserver`, 두 인자는 필수, 포트 범위는 1~65535, 잘못된 인자/루트/바인드 실패는 진단 후 비정상 종료로 한다.
- `--port`와 `--root`는 순서와 무관하게 각 한 번 필수다. 포트는 십진 숫자로 입력하고 기본값과 포트 0은 허용하지 않는다. `127.0.0.1`에만 바인드하며, listen 성공 뒤 stdout에 `READY <port>`를 한 줄 출력한다.
- `make`의 기본 타깃은 `webserver`다. `app.c`가 CLI를 검사하고 열린 루트 디렉터리 FD를 연결 처리에 전달한다.

## 서버 로직

### TCP와 순차 연결 수명 (P1-04)

- `socket()` → `bind()` → `listen()` → `accept()`를 직접 구현한다.
    - Phase 1에서는, **한 번에 한 연결의 요청 하나만 처리하고 다음 연결로 넘어간다**.
    - 완료 응답은 `Connection: close`를 알리고 연결을 종료한다.
    - 추가 바이트나 파이프라인 요청을 두 번째 요청으로 실행하지 않는다.
- 대기열에 연결이 존재하는 것과 여러 연결의 동시 처리는 구분한다.
- 리스너에 `SO_REUSEADDR`를 설정하며, 블로킹 수신·송신에 P1-12 마감을 적용한다.

### 점진적 HTTP 파싱 (P1-05)

- **HTTP/1.1 기반으로 요청 라인·헤더·본문 경계를 분리한다**.
- 결과는 추가 입력 필요·완료·오류를 구분한다.
- CRLF, 헤더 종료, 숫자, 청크 경계가 수신 경계에 걸쳐도 정확해야 한다.
- 헤더 이름은 대소문자를 구분하지 않는다.
- **HTTP/1.1의 `Host` 누락·중복·잘못된 값은 400이다**.
- 필드 이름 문법, 콜론 앞 공백, NUL·금지 제어문자, obs-fold를 엄격하게 검사한다.
- 관대한 줄바꿈 보정이나 문법 복구는 하지 않는다.
- 지원 버전과 요청 대상 형식은 아래 요청 head 의미 검증 계약을 따른다.

현재 구현은 요청 라인과 별도 헤더 구문 분리 함수로 나뉜다.
요청 라인·헤더·본문 함수는 `http.c` 하나에 처리 순서대로 배치하며 입력·결과 계약은 별개다.
`http_parse_request_line()`의 COMPLETE는 요청 라인 완료이며 전체 요청 완료가 아니다.
메서드는 token, 구분자는 정확히 한 SP, 버전 표기는 `HTTP/숫자.숫자`, 종료는 CRLF로 검사한다.
요청 대상은 공백·제어문자로부터 분리한 원문 바이트로 보존한다.
URI 형식·인코딩·지원 버전·메서드의 지원 여부를 승인하는 함수는 아니다.
따라서 `HTTP/2.0` 표기를 분리할 수 있어도 HTTP/2 지원을 뜻하지 않는다.
D-04의 버전·대상 구문·Host 하위 결정은 아래에서 확정했다.
D-01의 파일 경로 디코딩 이후 정책과 라우팅은 별개다.

`http_parse_headers(data, length, request_line_length)`는 요청 라인 직후부터의
누적 버퍼를 받는다. 마지막 인자는 요청 라인 파서가 COMPLETE에서 반환한 소비 길이다.
빈 줄까지 COMPLETE이면 이름·값의 원본 참조 목록과 헤더 시작 기준 소비 길이를 반환한다.
필드 이름의 원래 대소문자와 중복 필드의 순서를 보존하고 값 양끝의 SP/HTAB만 제거한다.
이름 비교는 후속 의미 검증에서 대소문자를 구분하지 않아야 한다.
빈 값·알 수 없는 이름·중복 필드의 구문 분리는 해당 요청의 의미적 승인이 아니다.
Host·CL·TE 등의 필드별 검증은 별도이며 P1-05·P1-07의 거부 정책을 대체하지 않는다.
NUL·금지 제어문자·잘못된 이름/콜론/CRLF·obs-fold는 400,
P1-10의 필드 줄·초기 헤더 총량·개수 제한은 431이다.
NEED_MORE/ERROR는 소비 0·빈 목록이며, COMPLETE여도 본문은 소비하지 않는다.
서버는 이 구문 함수를 호출한 뒤 별도의 본문 초기화에서 CL/TE·Expect를 해석한다.
Host·지원 버전·URI 구문은 헤더 완료 뒤 별도 함수에서 검증한다.

#### 요청 head 의미 검증 계약 (2026-11-20)

`http_validate_request_head()`는 정상 요청 라인·헤더를 입력받아 0/400/505를 반환한다.
검사 순서는 헤더 구문/한도 완료 → 버전 → 대상 구문 → Host → 기존 CL/TE·Expect 초기화다.
본문 추가 수신·할당과 100 Continue 전에 거부하며, 이미 같은 recv에 들어온 본문은
거부 시 처리하지 않는다. 서로 다른 오류가 있으면 이 단계 순서의 첫 오류를 반환한다.
헤더가 미완성일 때의 EOF·구문/한도 오류는 의미 검증보다 먼저 판정한다.

| 항목 | 계약 | 출처 |
| --- | --- | --- |
| 버전 | HTTP/1.1과 높은 1.x minor를 1.1 규칙으로 처리. 1.0·다른 major는 505 후 close. 잘못된 버전 표기는 기존 구문 파서의 400 | 사용자 확정; minor 의미는 RFC 9110 §2.5 |
| origin-form | `/`로 시작하는 path와 선택 query. 첫 원문 `?`로 분리하며 `%3F`는 구분자가 아님 | RFC 9112 §3.2.1 |
| absolute-form | 대소문자 무관 `http://`·`https://`, 비어 있지 않은 authority, 선택 path/query. 빈 path는 `/`. URI authority가 유효한 Host 값보다 우선 | RFC 9112 §3.2.2; 지원 scheme 범위는 구현자 결정 |
| authority-form | 대문자 CONNECT에만 host와 비어 있지 않은 숫자 port를 허용 | RFC 9112 §3.2.3 |
| asterisk-form | 정확한 `*`는 대문자 OPTIONS에만 허용 | RFC 9112 §3.2.4 |
| URI 문자 | RFC 3986의 unreserved/sub-delims 및 구성요소별 `: @ / ?` 허용. raw 비ASCII·역슬래시·fragment·잘못된 `%HH`는 400. path의 `%00`도 400 | RFC 3986 §2·3; NUL 거부는 P1-19 |
| Host | 이름 대소문자 무관 정확히 한 필드. 누락·중복·잘못된 값은 400. 값은 reg-name/IPv4 형태 또는 괄호 IPv6/IPvFuture, 선택 `:`와 숫자 port. userinfo·내부 공백·비숫자 port·괄호 오류는 거부 | RFC 9112 §3.2, RFC 9110 §7.2, RFC 3986 §3.2 |
| 빈 Host | absolute/authority-form의 자체 authority가 있으면 허용. 그 외는 기본 authority를 설정하지 않았으므로 400 | RFC 9112 §3.3의 선택지 중 구현자 결정 |
| port | 이 단계는 URI 구문만 검사하므로 선택 port의 빈 값과 임의 길이 숫자는 허용. CONNECT는 빈 port 불허. DNS 조회·TCP 목적지 선택은 하지 않음 | RFC 3986 port 문법; CONNECT 빈 port 거부 |

유효한 authority가 있어도 Host 필드의 누락·중복·비어 있지 않은 잘못된 값은 거부한다.
Host와 absolute URI의 authority가 다르면 유효한 URI authority를 사용하며 Host와 합치지 않는다.
IPv6 zone ID는 이 URI 문법에 포함하지 않는다. reg-name은 DNS 이름만으로 제한하지 않는다.
URI 결과는 원문 참조인 `http_target { form, authority, path, query }`다.
빈 absolute path의 `/`만 정적 저장소를 참조하며 나머지는 요청 head의 수명을 따른다.
입력은 수정하지 않고, 실패 시 출력은 빈 구조체다.

이 단계는 path/query를 디코딩하지 않는다. 라우터가 P1-19·P1-22의 경로 정책을 적용한다.
authority-form/asterisk-form의 **구문 수용은 CONNECT/OPTIONS 기능 지원이 아니다**.
메서드 지원, 자원 오류와 405의 우선순위는 P1-06을 따른다.

현재 서버는 head와 프레이밍을 검증한 뒤 Router를 판정한다.
정적 자원과 오류는 본문 전에 판정하고 echo 응답은 프레이밍된 본문 완료 뒤 준비한다.
구문·프레이밍 오류와 완성 전 EOF는 빈 입력도 400, 요청 라인 초과는 414,
헤더 초과는 431, 본문 초과는 413이다.

### 메서드와 자원 (P1-06)

- 정적 파일/디렉터리는 GET, HEAD, 예약 경로 `/echo`는 POST를 제공한다.
- **문법 오류는 400, 서버 미구현 메서드는 501**, 구현한 메서드가 자원에서 불허되면 405와 해당 `Allow`를 반환한다.
    
    
    |  | 자원 | 허용 메서드 |
    | --- | --- | --- |
    |  | 정적 자원 | GET, HEAD |
    |  | `/echo` | POST |
- 메서드는 대소문자를 구분한다. 정상 head와 프레이밍을 확인한 뒤 미구현 메서드는 501로 처리한다. 그 다음 자원과 공개 가능 여부를 판정한다. 제공 가능한 정적 자원에 POST를 보내면 `405`와 `Allow: GET, HEAD`, `/echo`에 GET/HEAD를 보내면 `405`와 `Allow: POST`다.
- 정적 경로의 403/404는 405보다 먼저 판정한다. 헤더 단계에서 확정한 오류나 디렉터리 308에는 추가 본문 수신이나 100을 하지 않는다. 상세 조합은 아래 판정표를 따른다.

### 요청 본문 프레이밍 (P1-07)

- `Content-Length`와 `Transfer-Encoding: chunked`를 **모두 지원**한다.
    - 동일 값이어도 중복 Content-Length, 쉼표로 합친 복수 길이, CL+TE는 400 후 종료한다.
    - 잘못된 숫자·부호·오버플로를 빈 본문이나 잘린 길이로 보정하지 않는다.
- 유효하지만 지원하지 않는 전송 코딩은 501이다.
- **chunked 반복이나 최종 코딩이 chunked가 아닌 요청은 400 후 종료한다**. 예를 들어 `gzip, chunked`는 프레이밍이 가능하지만 미지원 코딩이므로 501, `chunked, gzip`은 프레이밍 오류이므로 400이다.
- TE 토큰·순서·중복 검증을 미지원 코딩 판정보다 먼저 한다.

현재 `http_body_init()`는 대소문자를 구분하지 않는 CL/TE 이름과 전송 코딩을
해석한다. CL은 `size_t` 범위의 십진수로 검사한 뒤 본문 한도와 비교한다.
중복 CL·CL+TE를 먼저 거부하고, TE 문법·chunked 위치를 검사한 뒤 미지원 코딩을 판정한다.
CL·TE가 없으면 본문은 0바이트다. 받은 나머지를 임의로 본문으로 포함하지 않는다.
Content-Encoding은 해석하지 않는다. echo에는 전송 디코딩 후 바이트를 그대로 쓴다.

### 청크 디코딩 (P1-08)

- 16진수 크기, 데이터, 뒤따르는 CRLF, 종료 청크, trailer와 종료 빈 줄을 처리한다.
    - 숫자는 오버플로를 검사하고 청크 하나를 통째로 할당하지 않는다.
    - 알 수 없는 유효한 확장 의미는 무시하되 문법·길이 제한은 검사한다.
- 청크 개수 자체에는 별도 상한을 두지 않는다.
- 본문 한도·부가 정보·시간 제한은 계속 적용한다.
- trailer를 초기 헤더나 응답 헤더에 합치지 않는다.
- 구현자 결정: trailer의 Host·Content-Length·Transfer-Encoding·Connection·Trailer·
  TE·Upgrade·Expect·Content-Encoding·Content-Type·Authorization·Proxy-Authorization·Cookie는
  400으로 거부한다. 그 외 유효한 필드는 중복을 포함해 무시한다.
  이는 표준이 정한 고정 목록이 아니라 현재 서버의 프레이밍·라우팅·인증·처리 보호 정책이다.
  초기 헤더와 본문을 덮어쓰지 않으며 trailer 값을 앱에 전달하지 않는다.

### 요청 본문 크기 (P1-09)

- **디코딩 후 본문 최대 크기는 1 MiB = 1,048,576바이트다**.
    - 0바이트와 최대값은 허용하고 초과는 413 후 종료한다.
    - 선언 길이 또는 다음 청크 크기로 초과를 알 수 있으면 전체 수신·해당 크기 할당 전에 거부한다.
    - 문법적으로 유효한 큰 값의 용량 초과와 숫자 파싱 실패를 구분한다.
    - 1 MiB는 연결마다 미리 확보해야 할 버퍼 크기가 아니다.
- 정적 200의 GET/HEAD 본문은 수신·검증 후 버린다. 선언 길이의 초과는 자원 판정보다 먼저 판정한다.

### 요청 라인과 초기 헤더 제한 (P1-10)

- **해당 정책은 자체 자원 정책이며 표준의 고정값이 아니다.**
    
    
    |  | 대상 | 최대값 |
    | --- | --- | --- |
    |  | 요청 라인 전체, CRLF 포함 | 8,192바이트 |
    |  | 헤더 필드 한 줄, CRLF 포함 | 8,192바이트 |
    |  | 요청 라인부터 헤더 종료 빈 줄까지 | 32,768바이트 |
    |  | 초기 헤더 필드 수 | 100개 |
- 수신 바이트 수로 계산하고 최대값까지 허용한다.
- 연결 중 아직 끝나지 않은 줄도 제한 계산에서 제외하지 않는다.
- 본문과 trailer는 초기 헤더 총량에 포함하지 않는다.

### 청크 부가 정보 제한 (P1-11)

- **해당 정책은 자체 자원 정책이며 표준의 고정값이 아니다.**
    
    
    |  | 대상 | 최대값 |
    | --- | --- | --- |
    |  | 청크 크기 줄 전체, 확장 정보·CRLF 포함 | 8,192바이트 |
    |  | 모든 청크 확장 정보 누적 | 32,768바이트 |
    |  | trailer 영역, 종료 빈 줄 포함 | 32,768바이트 |
    |  | trailer 필드 한 줄, CRLF 포함 | 8,192바이트 |
    |  | trailer 필드 수 | 100개 |
- 확장 정보는 첫 `;`부터 해당 줄의 CRLF 직전까지 합산한다.
- 확장 정보 없는 줄은 확장 누적량을 늘리지 않는다.
- 종료 청크의 확장 정보도 같은 계산에 포함한다.
- 구현자 결정: 위 메타데이터 제한 초과는 431이다. 디코딩된 본문 한도 초과 413,
  숫자 오버플로·문법 오류 400과 구분한다. 종료 청크의 확장도 같은 제한을 적용한다.
- 레이아웃 정리 중 빠졌던 최대값 열은 기존 합의와 T-11의 수치로 복원했다. 새 한도나 표준 고정값을 추가한 것이 아니다.

### 시간 제한 (P1-12)

| 제한 | 값 | 시작·초기화 기준 |
| --- | --- | --- |
| 헤더 전체 수신 | 10초 | accept 성공부터, 연장 없음 |
| 본문 수신 무진행 | 30초 | 본문 수신 단계 진입, 실제 수신 시 초기화 |
| 전체 요청 수신 | 60초 | accept 성공부터, 연장 없음 |
| 응답 전체 송신 | 30초 | 응답 송신 시작부터 완료까지, 연장 없음 |
- **동시에 적용되는 마감 중 가장 이른 것을 따른다**. 버퍼 재파싱/루프 반복/무데이터 이벤트로 수신 타이머를 갱신하지 않는다.
- 수신 초과는 가능하면 408을 보내고 종료한다.
- 실패 연결에 오류 응답을 무기한 재시도하지 않는다.
- 단조 시계를 쓰며 진행과 만료가 같은 시각이면 만료가 우선한다. 본문 단계에서 실제로 받은 프레이밍 바이트도 무진행 마감을 갱신한다. 100 송신은 현재 본문 수신 마감 안에서 수행하며 그 마감을 연장하지 않는다.
- 최종 응답은 408을 포함해 송신 시작 시 독립 예산을 한 번 얻는다. 송신을 완료하면 쓰기 방향만 닫고 즉시 읽을 수 있는 바이트를 최대 32 KiB 폐기한 뒤 닫는다.
- 서버 정상 종료 유예 30초는 P1-27과 함께 Phase 2 시작으로 옮긴다.
  위 수신·송신 마감과 개별 연결의 정리 예산은 Phase 1에 유지한다.

### 응답 생성 (P1-13)

- **HTTP/1.1 상태 라인, 필요한 Content-Type, Content-Length, Connection을 생성한다**.
    - 문자열 길이가 아닌 실제 바이트 길이로 본문을 전송한다.
    - 부분 송신/중단/실패를 처리하고 상태 라인 전송 후 두 번째 최종 응답을 덧붙이지 않는다.
- 시계가 있는 서버의 2xx·3xx·4xx 응답에는 유효한 Date를 제공한다.
- 100 같은 중간 응답에는 본문/Content-Length를 보내지 않는다.

## 정적/동적 응답

### `/echo`의 의미 (P1-14)

- **POST 본문을 전송 디코딩한 후 바이트 그대로 응답한다**.
- 텍스트·NUL·비텍스트 바이트를 모두 허용한다.
- 입력의 Content-Type에 따라 내용을 해석하거나 변형하지 않는다.
- CL=0 또는 CL/TE 모두 없는 요청은 빈 본문, 최종 200/CL=0이다.
- 잘못된 프레이밍은 빈 본문으로 대체하지 않는다.
- 헤더 뒤에 추가 바이트가 와도 길이 없는 요청의 본문으로 포함하지 않는다.

### `/echo` 보안 (P1-15)

- **본문을 저장·실행하거나 정적 파일 조회에 사용하지 않는다**.
- 응답은 `application/octet-stream`, `X-Content-Type-Options: nosniff`, 직접 계산한 Content-Length, `Connection: close`를 사용한다.
- 요청 헤더·trailer·본문을 응답 헤더에 복사하지 않는다.
- HTML·스크립트·CRLF·가짜 응답 문자열도 본문 바이트로만 취급한다.
- 관련 보안 테스트는 필수이며 생략/실패 상태로 구현을 완료하지 않는다.

### 정적 파일의 범위와 전송 (P1-16)

- **확정. CLI로 지정한 정적 루트 안의 공개 허용 일반 파일만 제공한다.**
    - 파일 전체를 메모리에 적재하지 않고 고정 크기 버퍼로 전송한다.
    - 정적 파일 자체에는 1 MiB 제한이나 별도 크기 상한을 두지 않는다.
- 응답 송신 전체 30초 제한은 그대로 적용한다.
- FIFO·소켓·장치 등 특수 파일은 403이다.
- 연 뒤 fstat로 확인한 대상과 실제 읽는 대상이 일치해야 한다.
- 열린 파일의 크기 스냅샷까지만 보낸다. 증가분은 보내지 않으며 조기 EOF나 읽기 실패는 불완전 송신으로 처리한다.
- **크기 상한이 없다는 것은 전송 시간도 무제한이라는 뜻이 아니다.**
    - 최종 헤더 뒤 송신 마감이 오면 불완전 전송으로 종료하고 두 번째 오류 응답을 붙이지 않는다.
    - 이미 200을 보냈더라도 전송을 마치지 못하면 `complete: false`를 기록한다.

### 디렉터리와 기본 문서 (P1-17)

- **`/`와 하위 디렉터리는 해당 `index.html`을 제공한다.**
- 디렉터리 목록은 제공하지 않는다.
- 제공 가능한 기본 문서가 있는 디렉터리의 끝 `/`가 없으면 붙인 URL로 리다이렉트한다.
    - 숨김·없는 경로·기본 문서 없는 디렉터리는 리다이렉트하지 않고 404다.
- 제공 가능한 인덱스를 확인한 뒤에만 308을 보낸다. `Location`은 검증한 원문 URL 경로에 `/`를 붙인 값이며 authority와 query를 포함하지 않는다.

### 심볼릭 링크와 경계 (P1-18)

- **심볼릭 링크는 허용하되 실제 접근 대상도 정적 루트 내부여야 한다.**
    - 루트 이탈과 권한 거부는 403이다.
    - 끊어진 링크는 404, 순환 또는 해석 한도 초과는 403으로 종료하고 자원을 회수한다.
- **검사와 사용 사이에 링크가 바뀌어도 외부 파일을 노출하지 않아야 한다.**
    - 한 번의 realpath 검사 후 일반 open만 하는 방식은 이 요구의 검증 증거가 아니다.
- 상대·절대·중첩·중간 디렉터리 링크는 고정한 루트 내부의 공개 대상까지 해석할 수 있을 때 허용한다. 하위 마운트와 proc magic link는 허용하지 않는다. 루트 지정과 지원 조건은 아키텍처 A-06, 실행 범위는 테스트 T-16·T-18·T-22를 따른다.

### 경로 디코딩 (P1-19)

- **먼저 쿼리를 분리하고 경로를 정확히 한 번 퍼센트 디코딩한다.**
- 공백·한글 이름을 지원한다. 잘못된 `%`·불완전한 16진수·디코딩된 NUL은 400이다.
- 디코딩 결과에 숨김·루트 경계·파일 허용 정책을 적용한다.
- 중간 계층이 다시 디코딩하여 이중 인코딩이 정책을 우회해서는 안 된다.
- 인코딩된 `/`·역슬래시와 잘못된 UTF-8은 400이다. 반복 `/`와 `.`·`..` URL 구성요소는 경로를 정규화하지 않고 403으로 거부한다. `+`는 그대로, `%3F`는 파일명 문자로 처리한다.

### 쿼리와 파일 선택 (P1-20)

- **Phase 1의 정적 파일 선택에는 쿼리 값을 사용하지 않는다.**
    - `/index.html`과 `/index.html?v=1`은 같은 파일을 선택한다.
    - 쿼리는 파일명에 붙이지 않고, `%3F`로 인코딩된 파일명 문자와 구분한다.
- 쿼리 기반 기능은 필요할 때 확장한다.
- `/echo`도 query를 무시한다.

### 정적 MIME와 공개 허용 목록 (P1-21)

- **MIME 매핑과 파일 접근 허용 검사는 별도 책임이다.**
    - 정적 파일 정책을 `/echo` 바이너리 본문에 적용하지 않는다.
- 공개 허용 목록을 둔다는 인터뷰 방향은 유지한다.
    - 아래 목록을 ASCII 대소문자 구분 없이 적용한다. 요청한 파일명(디렉터리는 `index.html`)과 해석된 최종 파일명 모두 허용 목록에 들어야 하며 MIME은 최종 확장자로 선택한다.
        
        
        | 확장자 | MIME |
        | --- | --- |
        | `.html` | `text/html; charset=utf-8` |
        | `.css` | `text/css; charset=utf-8` |
        | `.js` | `text/javascript; charset=utf-8` |
        | `.png` | `image/png` |
        | `.jpg`, `.jpeg` | `image/jpeg` |
- 미등록·확장자 없는 파일은 403으로 포함한다.
- 단순히 application/octet-stream으로 제공하는 것은 접근 차단이 아니다.

### 존재 공개 정책 (P1-22)

- **존재하지 않거나 존재를 숨길 대상은 404, 접근 경계 위반이나 권한상 거부는 403이다.**
- 기본 문서 없는 디렉터리는 404이며 이전의 403 제안을 대체한다.
- 숨김 경로는 구성요소가 `.`으로 시작하는 파일·디렉터리를 뜻한다.
- 숨김 정책은 URL과 해석한 링크 대상 구성요소 모두에 적용한다. `.`·`..` URL 구성요소의 403과 숨김의 404를 구분한다.
- 외부 대상의 존재 여부를 확인해야만 경계 위반을 거부할 수 있는 구조를 피한다.

### 오류 응답 (P1-23)

| 코드 | 용도 |
| --- | --- |
| 400 | 문법·프레이밍 오류 |
| 403 | 경계·권한·특수 파일 등 접근 거부 |
| 404 | 없음·숨김·기본 문서 없음 |
| 405 | 자원별 메서드 불허, Allow 필수 |
| 408 | 수신 시간 초과 시 가능한 오류 응답 |
| 413 | 요청 본문 용량 초과 |
| 414 | 요청 라인 크기 초과 |
| 417 | 지원하지 않는 유효한 Expect 값 |
| 431 | 초기 헤더 또는 청크 부가 정보의 크기·개수 초과 |
| 500 | 통제된 내부 처리 실패 |
| 501 | 미구현 메서드 또는 지원하지 않는 유효한 전송 코딩 |
| 505 | HTTP/1.0 또는 다른 major의 미지원 버전 |
- **상태별 고정 text/plain 메시지로 응답하고 상세 원인은 내부 진단에 남긴다.**
    - 현재 고정 메시지는 상태 코드의 영어 사유 구문이며 끝 개행은 없다. Content-Length는 그 바이트 길이다.
    - 파싱·앱 오류 모두 같은 생성기와 최종 송신 경로를 사용한다. Date는 5xx에도 제공한다.
    - 실제 경로·입력 원문·스택·errno 설명 등을 응답에 넣지 않는다.
    - 동일한 404 정책의 응답은 원인별 문구·불필요한 헤더 차이를 만들지 않는다.
- Date 등 시간 의존 필드까지 동일하거나 응답 시간이 일정하다는 보장은 하지 않는다.
- **오류도 송신 제한을 지키며, 이미 응답을 시작했거나 연결이 끊겼다면 추가 최종 응답을 만들지 않는다.**

### Expect (P1-24)

- **`Expect: 100-continue`를 지원한다.**
    - 헤더만으로 거부 가능하면 바로 최종 오류를 보낸다.
    - 수신을 계속해야 하면 본문을 기다리기 전에 100을 보내고 최종 응답을 별도로 생성한다.
    - 클라이언트가 100을 기다리지 않고 본문을 보낸 경우도 처리한다.
- 알 수 없는 유효한 기대 조건은 417 후 종료, Expect 문법 오류는 400이다.
- 구현자 결정: 여러 필드/목록의 단순 100-continue 반복은 허용한다.
  빈 본문·이미 버퍼 안에서 완성된 본문에는 100을 생략한다.
  유효한 프레이밍에서 추가 입력이 필요하면 수신 전에 한 번 송신한다.
  문법이 유효한 매개변수/값이 붙은 기대 조건은 미지원 417, 잘못된 문법은 400이다.
  head/프레이밍·자원 오류와 308은 100보다 우선한다. 100의 송신 마감은 P1-12를 따른다.

### HEAD (P1-25)

- **성공·오류·리다이렉트를 포함한 모든 HEAD 최종 응답은 본문이 없다.**
    - 대응 GET의 표현 메타데이터를 사용하고 Content-Length를 보낸다면 GET 본문 길이로 한다.
    - Content-Length가 양수라도 실제 본문을 보내지 않는다.
- HEAD `/echo`는 405·Allow: POST이며 본문은 없다.
- 정상 요청 라인에서 HEAD를 확인한 시점부터 오류 응답에도 적용한다. 요청 라인 자체가 잘못되어 메서드를 확정하지 못하면 일반 오류 본문을 보낸다.

## 로그와 자원 정리

### 자원과 연결 실패 (P1-26)

- **부분 수신·송신, EINTR, EAGAIN/EWOULDBLOCK, EOF·RST를 구분한다.**
- 실패한 연결의 메모리·소켓·파일 FD를 회수하되 서버는 계속 실행한다.
- 소켓 송신에는 `MSG_NOSIGNAL`을 사용하며 접근·진단 로그 쓰기도 SIGPIPE로 서버 전체가 종료되지 않게 처리한다.
- recv=0은 송신 방향 종료일 수 있으므로 완성 요청에는 응답을 시도할 수 있다.
    - 미완성 요청을 성공 처리하지 않는다.
- 오류 응답·응답 후 정리도 무한 대기하지 않는다.

### 정상 종료 (P1-27)

**Phase 2 시작으로 이관. Phase 1의 구현·테스트·완료 게이트에서 제외한다.**
아래 계약은 삭제하지 않고 후속 구현 기준으로 유지한다.
Phase 1에는 커스텀 종료 핸들러·종료 플래그·종료 통지 대기를 넣지 않는다.

- **SIGINT·SIGTERM을 받으면 새 연결 수락을 중단한다.**
    - 현재 요청에 최대 30초 유예를 주되 기존 마감을 연장하지 않는다.
    - 완료 또는 먼저 도달한 마감 뒤 모든 자원을 회수하고 종료한다.
- 시그널 핸들러는 종료 의사만 안전하게 전달한다.
    - free·복잡한 로깅·일반적인 자원 정리를 핸들러에서 직접 하지 않는다.
- 유휴 accept/I/O 대기에서도 종료 요청을 놓치지 않아야 한다.

### 로그와 정보 노출 (P1-28)

- **내부 진단 로그와 요청별 JSONL 접근 로그를 분리한다.**
    - 접근 로그에는 메서드, 쿼리 제외 URL 경로, 최종 상태, 처리 시간, 송신 바이트 수를 남긴다.
    - 본문·인증정보·실제 파일 시스템 경로는 접근 로그에 기록하지 않는다.
- 사용자 문자열의 줄바꿈·제어문자·따옴표를 안전하게 인코딩한다.
- 진단 로그에도 본문·인증정보를 무조건 기록하지 않는다.
- `method`, `path`, `status`는 확정할 수 없으면 `null`이다. `duration_ms`는 단조 시계 기준 정수다. `bytes_sent`는 헤더를 포함하고 100을 제외한 최종 응답 중 커널이 받은 바이트 수다. `complete`는 최종 응답을 모두 커널에 넘겼는지를 뜻하며 클라이언트 수신 확인을 뜻하지 않는다.
- `READY` 뒤 stdout에는 연결당 JSONL 한 건을 기록하고 진단은 stderr로 분리한다. 긴 path는 `<truncated>`를 사용한다. 파이프 출력이 밀리면 연결을 계속 처리하고 기록은 버릴 수 있다.

## 테스트/구현 완료 기준

### 성능 기준선 (P1-30)

### 컨테이너 환경 증빙 (P1-31)

- **Linux Docker 컨테이너의 빌드·기능·보안·자원 검사 결과를 남긴다.**

- 호스트 경로가 컨테이너에 보인다는 사실만으로 POSIX 권한·링크 동작을 검증했다고 하지 않는다.

## 조합별 판정표

head 구문·한도 → 버전·대상·Host → CL/TE·Expect → 메서드 지원 →
경로·자원·자원별 메서드 → 필요한 본문과 최종 응답 순서다.

| 입력·상황 | 결과 |
| --- | --- |
| head 의미 오류와 잘못된 프레이밍 | 먼저 head의 400/505 |
| 프레이밍 오류·CL 초과·지원하지 않는 Expect와 자원 오류 | 자원 탐색 전에 400/413/417 등 프레이밍·Expect 결과 |
| 유효한 미지원 메서드와 경로 오류 | head·프레이밍이 유효한 경우 메서드 501 |
| POST로 존재하지 않거나 차단된 정적 자원 요청 | 404/403. 제공 가능한 정적 자원에만 405/Allow |
| HEAD `/echo` | 405, `Allow: POST`, 본문 없음 |
| 유효한 프레이밍 본문이 붙은 정적 GET/HEAD | 200이면 공통 한도로 수신·검증하고 버림. 308과 자원 오류는 본문·100 전에 응답 |
| CL/TE 없는 POST `/echo` | 빈 본문, 200, `Content-Length: 0`, 100 생략 |
| Content-Encoding이 있는 POST `/echo` | encoding을 해석하지 않고 전송 디코딩된 바이트를 돌려줌. 해당 요청 헤더는 복사하지 않음 |
