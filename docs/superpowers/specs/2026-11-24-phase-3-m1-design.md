# Phase 3 첫 마일스톤 — 단일 백엔드

기준은 `2785e06`이다. 이 문서는 착수 초안을 좁힌 작업 설계이며, 사용자가
프록시의 모든 최종 정책을 확정했다는 뜻은 아니다.

## 선택과 범위

별도 워커에 블로킹 송수신을 맡길 수도 있지만 큐·스레드·종료 정책을 새로
도입해야 한다. 기존 LT `epoll`에 백엔드 FD를 등록하는 쪽을 선택한다.
백엔드 응답이 지연되는 동안 기존의 정적 요청이 처리되는 것으로 검증한다.

- 기본 실행은 그대로다. `--route /api/=127.0.0.1:8001`을 주면 `/api/` 아래만
  숫자 IPv4 주소의 지정 포트로 보낸다. 첫 단계는 규칙 하나만 허용한다.
  URI의 호스트나 `Host`는 연결 대상을 결정하지 않는다.
- 기존 파서가 검증한 HTTP/1.1 GET·HEAD·POST를 쓴다. 원래의 경로와 쿼리를
  붙여 origin-form으로 전송하고, `Host`와 본문 길이는 다시 생성한다.
  `Expect`는 로컬에서 처리하고, 연결별 필드와 `Connection`이 가리키는
  필드는 양방향에서 제거한다. 요청에는 `Via: 1.1 week13`을 추가한다.
- 한 요청에 백엔드 연결 하나만 사용한다. 연결 제한 2초, 헤더 제한 5초,
  중계 제한 30초를 두고 정상 종료 유예보다 길게 기다리지 않는다.
  첫 단계에서는 길이가 확정된 응답과 본문 없는 응답만 처리한다.
  백엔드 헤더는 32 KiB, 첫 단계의 고정 길이 본문은 1 MiB로 제한한다.
- 응답을 검사하고 본문을 받은 뒤에만 클라이언트 응답을 시작한다. 연결 실패,
  지원하지 않는 프레이밍, 잘린 본문은 `502`, 기한 초과는 `504`로 처리한다.
  프록시 요청은 첫 단계에 한해 클라이언트 연결을 최종 응답 뒤 닫는다.
  프록시가 아닌 요청의 Phase 2 재사용 정책은 바꾸지 않는다.
- 본문 스트리밍과 backpressure, chunked/EOF 응답, 프록시 연결 재사용,
  두 번째 규칙·긴 프리픽스 우선순위는 후속 단위에서 다룬다. TLS, CONNECT,
  캐싱, 라운드 로빈은 첫 단계에서 구현하지 않는다.

## 합격 기준

실제 루프백 백엔드가 관찰한 메서드·경로·쿼리·바이너리 본문을 확인한다.
클라이언트는 백엔드의 상태와 본문을 받는다. 백엔드가 응답을 보내기
전에 다른 클라이언트의 `GET /`가 완료돼야 한다. 연결 거절·응답 지연 뒤
서버가 계속 동작해야 한다. 기존 기능과 메모리 검사를 Docker에서 재실행한다.
