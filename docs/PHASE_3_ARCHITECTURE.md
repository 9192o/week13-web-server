# Phase 3 설계 — 리버스 프록시

`webserver`는 기존 정적 파일·`/echo` 백엔드로, `reverse-proxy`는 독립된
앞단 프로세스로 실행한다. 두 프로그램은 HTTP 파서·LT `epoll`·세션 수명
관리 코드만 공유한다. `session_app.h`의 콜백 경계로 분리해 프록시에
`src/app/`·`src/static/`을, 백엔드에 `src/proxy/`를 링크하지 않는다.
이 문서는 현재 구현을 설명한다. 실행 결과는 [Phase 1–3 통합 검증](PHASE_3_TESTING.md),
설계 변경 전의 논의는 [착수 초안](PHASE_3_KICKOFF.md)을 참고한다.

## 라우팅과 설정

`webserver`는 `--port`와 `--root`가 필요하고 `--route`를 받지 않는다.
`reverse-proxy`는 `--port`와 `--route /prefix/=IPv4:PORT`가 필요하고
`--root`를 받지 않는다. `--route`는 총 32개까지 등록할 수 있다. 접두사는
`/`로 시작하고 `/`로 끝나야 한다. 같은 접두사에 서로 다른 IPv4:포트를
반복 등록하면 백엔드 풀이 되며, 같은 접두사에 같은 주소·포트를 중복
등록할 수 없다.

| 설정 또는 요청 | 처리 |
| --- | --- |
| `--route /api/=127.0.0.1:8001` | `/api/` 접두사를 8001에 등록 |
| `--route /api/admin/=127.0.0.1:8002` | `/api/admin/` 접두사를 8002에 등록 |
| `/api/admin/status?detail=1` | 최장 접두사인 8002로 원래 경로와 쿼리 전달 |
| `/api/echo` | 8001로 전달 |
| `/api`, `/apix/`, `/echo`, `/` | 위 설정과 불일치하므로 프록시가 `404` 반환 |
| `--route /=127.0.0.1:8001` | 더 구체적인 규칙과 매칭되지 않은 경로를 8001로 중계 |

origin-form 요청의 경로만 매칭하고 쿼리는 매칭에서 제외한다. 요청의 `Host`나
절대 URI로 접속 목적지를 선택하지 않는다. 기존 `webserver`에 직접 접속하면
정적 파일·`POST /echo`와 Phase 2 연결 재사용 정책을 그대로 쓸 수 있다.
두 실행 파일은 기본적으로 루프백에서 수신하며, 예제에서는 같은 컨테이너에서
실행한다. 프록시 기동에 백엔드가 필요하지 않고 백엔드 재기동 뒤에는
다음 요청에서 다시 접속한다.

최장 접두사를 먼저 고른 뒤, 그 접두사의 백엔드만 등록 순서대로 순환한다.
순번은 접두사별로 독립적이며 검증된 요청의 본문 수신이 끝나 백엔드를
선택할 때 한 번만 전진한다. 요청을 쓰기 전 TCP 접속 실패에만 같은 접두사의
다음 백엔드를 시도한다. 접속 단계의 2초 예산은 모든 시도가 공유한다.
쓰기 단계에 들어간 요청은 다시 보내지 않는다.

## 요청과 응답의 수명

1. [`proxy_routes.c`](../src/proxy/proxy_routes.c)가 검증된 요청의 목적지를 선택한다.
2. [`proxy_wire.c`](../src/proxy/proxy_wire.c)가 백엔드의 `Host`와 디코딩된
   본문의 길이에 맞춰 HTTP 요청을 재구성한다. 연결별 헤더와 `Connection`이
   지목한 필드를 제거하고 `Expect`는 로컬에서 처리한다. 백엔드 요청에
   `Via: 1.1 week13`을 넣으며 연결 정책은 HTTP/1.1 구간별로 결정한다.
3. [`proxy_exchange.c`](../src/proxy/proxy_exchange.c)가 백엔드 접속, 요청 쓰기,
   응답 헤더 읽기와 본문 중계를 논블로킹으로 처리한다. 기존 클라이언트 세션이
   교환의 수명을 관리하므로 응답이 느린 백엔드를 기다리는 동안에도 다른
   연결을 처리할 수 있다.
4. 최종 상태와 본문 바이트를 중계하되 응답 경계는 다시 구성한다.
   HTTP/1.0·1.1 백엔드의 고정 길이, chunked, EOF 구분을 지원한다.
   chunked·EOF 본문은 클라이언트 쪽에서 chunked로 보내며, 확장과
   트레일러는 복사하지 않는다. `HEAD` 및 본문 없는 상태에는 본문을 보내지
   않는다. 일반 1xx는 건너뛰고 프로토콜 전환(`101`)은 지원하지 않는다.

## 제한과 실패 처리

| 단계 | 상한 |
| --- | ---: |
| 백엔드 접속 | 2초 |
| 백엔드 요청 쓰기 | 5초 |
| 백엔드 응답 헤더 읽기 | 5초 |
| 최종 헤더 파싱 후 중계 | 30초 |

응답 헤더는 최대 32 KiB를 누적하고 본문은 8 KiB 단위로 중계한다.
클라이언트에 보낼 데이터가 남으면 백엔드 읽기를 멈춘다. 정상 종료 유예가
더 일찍 만료되면 그 시각을 적용한다.

클라이언트 응답을 시작하기 전 백엔드 접속 실패나 잘못된 응답에는 `502`,
기한 초과에는 `504`를 보낸다. 응답을 시작한 뒤 중계가 실패하면 두 번째
상태 줄을 쓰지 않고 연결을 닫는다. 고정 길이 응답을 끝까지 전달하면
클라이언트가 닫기를 요청하지 않은 경우 세션을 재사용한다. 업스트림은
HTTP/1.1 고정 길이 응답을 완전히 소비했고 종료 지시나 남은 바이트가 없을 때만
라우트의 백엔드 항목별 1개, 최대 5초 보관한다. HEAD는 업스트림 풀에 반환하지
않고, chunked·EOF 중계는 두 구간 모두 재사용하지 않는다.

백엔드는 숫자 IPv4의 평문 HTTP만 지원한다. DNS, TLS, CONNECT, 업그레이드,
캐싱, 별도 헬스 체크, 가중치, 경로 재작성은 구현하지 않았다.
