## Phase 3: 리버스 프록시

외부 요청을 받아 경로 규칙에 따라 여러 백엔드로 나눠 전달하는 **리버스 프록시**를 phase 1~2 웹서버에 붙였다.
외부 HTTP 라이브러리 없이 POSIX 소켓 API 만 쓰고, 백엔드는 같은 `./server` 를 포트만 바꿔 띄운 것이다.

```
client --> proxy :8080 --> rule matched  --> backend A :8001 / B :8002 (round-robin)
                       \-> no rule match --> static files / CGI served by the proxy itself
```

- 유저 시나리오 8개(P1~P8)를 먼저 쓰고, 한 단위씩 "결정 → 구현 → 테스트" 순서로 만들었다. 시나리오가 그대로 기능 테스트가 된다.
- 판단·변환 로직(`src/proxy.c`)과 실제 중계(`src/server.c` 의 `serve_proxy`)를 나눠서, 앞쪽은 소켓 없이 단위 테스트한다.
- **하지 않은 것:** 포워드 프록시, 캐싱, 프록시 부하 테스트 (맨 아래 "추후 작업").

### 과제 요구사항과 이번 선택

| 과제 요구 | 선택 | 구현·검증 |
| --- | --- | --- |
| Proxy 또는 Reverse Proxy 중 최소 하나 | **리버스 프록시.** 로드밸런싱, 502/504 처럼 다룰 거리가 많아서. 포워드 프록시는 하지 않음 | `src/proxy.c`, `serve_proxy` |
| 경로 또는 Host 헤더 기반 라우팅 | **경로 prefix.** 클라이언트는 늘 프록시의 포트로 오므로 포트는 근거가 될 수 없다. Host 이름 기반도 가능하지만 이번에는 경로만 구현 | `proxy_match`, P1 |
| 가능하면 단순 로드밸런싱 (Round-Robin) | 규칙마다 atomic 카운터로 라운드로빈 | `proxy_pick`, `test_pick_concurrent`, P2 |
| 정적 요청을 프록시가 직접 서빙할지 선택 | **규칙에 없는 경로는 프록시가 직접 서빙**, 규칙에 맞는 경로만 백엔드로 | P7 |
| 포트·루트·라우팅 규칙을 CLI 인자 또는 설정 파일로 | CLI 반복 옵션 `-R` | `config_parse` |
| 백엔드 응답 없음 / 타임아웃 | 꺼짐은 502, 늦음은 504, connect 실패는 다음 백엔드로 재시도 | P3, P4 |
| 클라이언트의 갑작스러운 연결 종료 | 중계 중단, fd 두 개 모두 정리 | P6 |
| 단위·기능·부하 테스트, 메모리 검사 | 단위·기능·ASan·valgrind 완료, 부하 테스트는 추후 | `make test` / `ftest` / `valgrind` |

### 사용법

```sh
# 백엔드 두 대 (같은 서버를 포트만 바꿔 실행. 응답 본문에 자기 포트를 넣어 누가 처리했는지 확인)
mkdir -p www-a/api www-b/api
echo 8001 > www-a/api/hello.txt
echo 8002 > www-b/api/hello.txt
./server -p 8001 -r ./www-a
./server -p 8002 -r ./www-b

# 프록시: /api/ 는 두 백엔드로 라운드로빈, 나머지 경로는 프록시가 직접 서빙
./server -p 8080 -R /api/=127.0.0.1:8001,127.0.0.1:8002

for i in 1 2 3 4; do curl -s localhost:8080/api/hello.txt; done   # 8001 8002 8001 8002
curl -s localhost:8080/index.html                                 # 규칙에 없음 → 프록시 자신의 ./www

# POST 전달 (백엔드의 CGI adder 가 본문을 받아야 3 이 나온다)
./server -p 8001 -r ./www
./server -p 8080 -R /cgi-bin/=127.0.0.1:8001
curl -X POST -d 'a=1&b=2' localhost:8080/cgi-bin/adder            # 3
```

- `-R prefix=host:port[,host:port...]` 를 여러 번 줄 수 있다 (규칙 최대 16개, 규칙마다 백엔드 최대 8개).
- 호스트는 이름도 되며 시작할 때 한 번 IPv4 로 해석한다. 같은 prefix 두 번, 프록시 자신을 가리키는 규칙은 시작할 때 거부한다.
- 접근 로그 끝에 어느 백엔드가 처리했는지 남는다: `"GET /api/x HTTP/1.1" 200 5 (proxy 127.0.0.1:8001)`.
  실패하면 이유가 붙고(`connect: Connection refused`, `backend timeout`, `backend closed early`, `client closed` ...),
  재시도는 `(proxy retry: ...)` 한 줄이 따로 남는다.

### 설계 결정과 이유

#### 구조와 라우팅

| 결정 | 선택 | 이유 | 대안 |
| --- | --- | --- | --- |
| 바이너리 | 같은 `./server` 에 `-R` 추가, 코드는 `proxy.c` 로 분리 | phase 2 의 스레드 풀·keep-alive·503·종료 처리·시간 제한을 그대로 받는다. 판단 로직은 소켓 없이 테스트된다 | 별도 `./proxy` (역할은 분명하지만 accept 루프·풀·종료 처리를 떼어내야 함) |
| 규칙 입력 | CLI 반복 옵션 `-R` | 기존 getopt 구조에 바로 붙고, 테스트 스크립트에서 쓰기 쉽다 | 설정 파일 (파서 모듈이 하나 더 필요) |
| 매칭 | 디코딩된 경로의 문자열 prefix, 여러 개면 **가장 긴 것**, `/cgi-bin` 보다 먼저 | `..`·점 파일 검사(`url_check_path`)를 먼저 거친 경로로 매칭해서 우회할 수 없다. `/api/` 규칙은 `/api`, `/apix` 에 걸리지 않는다 | 세그먼트 단위 매칭 |
| 백엔드 주소 | 호스트명 허용, 시작할 때 `getaddrinfo(AF_INET)` 로 한 번 | 요청마다 DNS 를 조회하지 않고, 숫자 IP 도 받는다 | 숫자 IPv4 만 (IPv6 는 listen·로그·CGI `REMOTE_ADDR` 까지 건드리므로 별도 단위로 미룸) |
| 백엔드로 보낼 경로 | 쿼리까지 **원문 그대로**, Host 도 클라이언트 값 그대로 | 재작성할 게 적어 경로 해석이 어긋날 위험이 작다. 프록시로 열리는 범위가 규칙의 prefix 로 좁다 | prefix 제거 (nginx 의 `proxy_pass .../`, 슬래시 하나로 의미가 바뀌는 함정), Host 를 백엔드 주소로 변경 |
| 규칙에 없는 경로 | 프록시가 직접 서빙 | 정적은 앞단, 동적만 백엔드로 보내는 nginx 식 구성. `-R` 없이 띄우면 phase 2 서버와 똑같다 | 전달만 하고 404 (순수 프록시) |
| 자기 자신을 가리키는 규칙 | 시작할 때 거부 (루프백·0.0.0.0 + `-p` 와 같은 포트) | 무한 루프로 워커가 모두 막히는 것을 미리 막는다 | 검사 안 함, `Via` 헤더로 루프 감지 |

#### 두 개의 연결: 클라이언트 ↔ 프록시, 프록시 ↔ 백엔드

프록시 워커는 연결을 두 개 쥔다 (`connfd`, `backendfd`). 두 연결은 서로 독립이라 keep-alive, HTTP 버전, 연결 관련 헤더를 구간마다 따로 정한다.
이번 설계의 상당 부분이 이 사실에서 나왔다.

| 결정 | 선택 | 이유 | 대안 |
| --- | --- | --- | --- |
| 백엔드로 보내는 요청 | **`HTTP/1.0` + `Connection: close`** | 1.0 요청에는 chunked 로 답할 수 없다. 응답의 끝이 "Content-Length" 아니면 "백엔드가 연결을 닫음" 둘뿐이라 해석할 것이 줄고, 1.0 으로 요청하는 클라이언트(`ab`)도 안전하다 (nginx 기본값과 같음) | 1.1 + chunked 해석 + 백엔드 연결 재사용 (별도 단위) |
| 클라이언트 keep-alive | 응답에 **Content-Length 가 있으면 유지**, 없으면 EOF 까지 흘리고 `Connection: close` | 길이를 알아야 다음 응답이 어디서 시작하는지 안다. 연결 재사용 덕에 요청마다 handshake 를 하지 않는다 | 항상 close (단순하지만 요청마다 새 연결) |
| 응답 상태 줄 | `HTTP/1.1` 로 바꿔서 전달 | 백엔드의 `HTTP/1.0` 을 그대로 주면 클라이언트가 keep-alive 를 끊는다 (중계자 규칙) | |
| hop-by-hop 헤더 | 요청·응답 양쪽에서 제거 (Connection, Keep-Alive, Proxy-Connection, TE, Upgrade, Connection 에 이름이 적힌 헤더) | 연결 하나에만 의미가 있는 헤더라 다음 홉으로 넘기면 안 된다 (RFC 9110 7.6.1) | |
| 응답 헤더를 믿는 정도 | 애매하면 **502** | 아래 참고 | 최대한 통과시키기 |

백엔드 응답에서 다음은 클라이언트에 아무것도 보내기 전에 502 로 거절한다: 상태 줄 형식 오류, 1xx, obs-fold, 이름이 잘못되었거나 콜론이 없는 헤더,
줄 안의 CR/NUL(응답 분할), 헤더 64개 초과, Content-Length 가 숫자가 아니거나 여러 개인데 값이 다름(RFC 9112 6.3),
**Transfer-Encoding 이 옴**, **Content-Length 와 Transfer-Encoding 이 같이 옴**. 1.0 으로 요청했으니 TE 가 오는 것 자체가 규격 위반이고,
길이를 두 가지로 읽을 수 있는 응답은 프록시와 클라이언트가 다르게 믿으면 다음 응답이 섞이는 request smuggling 의 출발점이기 때문이다.
(클라이언트가 보낸 요청의 TE, CL+TE 는 phase 1 파서가 프록시에 닿기 전에 501, 400 으로 막는다.)

#### 라운드로빈과 공유 카운터

- 백엔드는 `(카운터++) % 백엔드 수` 로 고른다. 카운터는 0 에서 시작하므로 첫 요청이 첫 번째 백엔드다.
- 카운터는 워커들이 함께 쓰는 공유 자원이다. 그냥 `++` 하면 읽기-더하기-쓰기 사이에 다른 스레드가 끼어들어 **lost update** (증가가 사라지고 같은 백엔드로 몰림)가 생긴다.
  보호할 것이 숫자 하나뿐이라 mutex 대신 **`atomic_fetch_add`** 로 겹치지 않는 번호표를 나눠 준다. 다른 메모리와 순서를 맞출 일이 없어 `memory_order_relaxed` 로 충분하다.
- 카운터는 **규칙마다 따로**, 64비트다. 다른 경로의 요청이 이 규칙의 순서를 흔들지 않고(시나리오 예측 가능), 32비트처럼 약 43억 요청 뒤에 한 바퀴 돌아 순서가 어긋나지 않는다.
- 분배는 **요청 단위**다. keep-alive 한 연결 안에서도 요청마다 다음 백엔드로 간다 (대안은 연결에 고정하는 sticky, 백엔드가 세션을 가질 때 필요).
- 같은 백엔드를 여러 번 적으면(`A,A,B`) 그만큼 더 받는다. 간단한 가중치로 쓸 수 있어서 막지 않았다.

#### 백엔드가 문제를 일으킬 때: 502, 504, 재시도

| 상황 | 결과 | 이유 |
| --- | --- | --- |
| connect 거절 (꺼짐) | 다음 백엔드로 재시도, 백엔드마다 한 번. 모두 실패하면 **502** | connect 가 실패했다면 백엔드는 요청을 한 바이트도 못 받았다. 메서드와 상관없이 안전하다 |
| connect 가 5초 안에 안 끝남 | 같은 방식으로 재시도. 마지막 시도가 시간 초과면 **504**, 거절이면 502 | "닿지 않음"과 "닿았는데 느림"을 구분 (nginx 도 마지막 오류 기준) |
| 응답 헤더 전체가 5초 안에 안 옴 | **504** | 한 바이트씩 질질 끄는 백엔드도 막으려고 헤더 전체 기준. 요청을 이미 보냈으므로 **재시도하지 않는다** |
| 백엔드가 헤더 전에 연결을 닫거나 응답이 깨짐 | **502** | |
| 헤더를 보낸 뒤 백엔드가 닫거나 5초 멈춤 | 로그만 남기고 클라이언트 연결을 끊음 | 이미 상태 줄이 나갔으므로 상태 코드를 바꿀 수 없다. 클라이언트는 Content-Length 보다 덜 받아 잘린 것을 안다 (curl exit 18) |
| 클라이언트가 중계 도중 끊음 | 중계 중단, 백엔드 연결 정리 | `send` 가 `EPIPE` 로 돌아온다 |

- **재시도 기준은 "요청이 이미 나갔는가"다.** 보낸 뒤의 실패는 백엔드가 이미 처리했을 수 있으므로(POST 는 멱등이 아님) 재시도하지 않는다.
- 재시도는 목록의 다음 칸으로 가고 라운드로빈 카운터는 건드리지 않는다. 한 대가 꺼져 있는 동안 다른 요청의 분배 순서까지 밀리지 않게 하려는 것이다.
- 시간 제한은 세 곳에 둔다 (`PROXY_CONNECT_TIMEOUT_MS`, `PROXY_TIMEOUT_MS`, 둘 다 5초, `-D` 로 변경 가능).
  connect 는 non-blocking + `poll(POLLOUT)` + `SO_ERROR` 로 건다. 응답 헤더는 전체 기준, 본문은 **조각 사이 무응답** 기준이라 크고 느려도 계속 오면 끊지 않는다.
- 408 은 클라이언트가 늦은 것, 504 는 백엔드가 늦은 것이다.

#### POST 전달

- 본문은 CGI 와 같은 규칙(Content-Length 없으면 411, 1MB 초과 413, 필요하면 100 Continue, 시간 안에 안 오면 408)으로 **다 받은 뒤** 백엔드를 골라 연결한다.
  느린 클라이언트가 본문을 보내는 동안 백엔드 연결을 붙잡지 않고, 연결 재시도도 "아직 아무것도 안 보냄" 상태에서 안전하다. 대안은 받는 대로 흘려보내는 스트리밍인데, 큰 업로드에는 유리하지만 도중에 실패하면 재시도할 수 없다.
- 요청을 다시 쓸 때 Content-Length 는 유지하고(백엔드가 본문 끝을 알아야 함), `Expect` 는 뺀다. 100-continue 는 프록시가 클라이언트와 이미 주고받았고, 백엔드가 100 으로 답하면 1xx → 502 규칙에 걸린다.
- 본문을 Content-Length 만큼만 소비하므로 그 뒤에 붙어 온 다음 요청(pipelining)도 처리한다. GET 에 붙은 본문은 정적 경로와 같이 전달하지 않고 응답 뒤 연결을 닫는다.

### 과제 중점 포인트와 이 구현

**Proxy 와 Reverse Proxy: 누구 입장에서 누구를 대신하나**

- 포워드 프록시는 **클라이언트를 대신**한다. 요청 URL 의 호스트를 보고 바깥 서버에 새 연결을 만들며, 바깥 서버는 실제로 누가 보냈는지 모른다. 캐싱과 접근 통제에 쓴다.
- 리버스 프록시는 **서버를 대신**한다. 클라이언트는 프록시만 알고, 백엔드가 몇 대인지·몇 번 포트인지·하나가 죽었는지는 보이지 않는다.
- 이 구현에서 얻는 것:
  - **보안:** 프록시로 열리는 범위가 규칙의 prefix 로 좁고, 경로 검사·헤더/본문 크기 제한·시간 제한(slowloris 포함)을 백엔드보다 앞단에서 먼저 적용하며, 응답도 엄격하게 검사한다.
    (이 서버는 `0.0.0.0` 으로 listen 하므로 백엔드를 실제로 숨기려면 방화벽이나 바인드 주소가 따로 필요하다.)
  - **로드밸런싱:** 라운드로빈, 꺼진 백엔드는 건너뜀.
  - **캐싱:** 구현하지 않았다.
- 포워드 프록시를 붙인다면 절대 URI 에서 호스트를 뽑고 `getaddrinfo` 를 요청 시점에 부르는 것이 추가분이고, `serve_proxy` 의 중계 코드는 재사용할 수 있다. 열린 프록시 악용 방지 같은 새 결정이 필요해서 이번에는 하지 않았다.

**HTTP 명세: 경계를 어떻게 식별하나**

- 응답의 끝을 아는 방법은 ① Content-Length ② 연결 닫힘 ③ chunked 세 가지다. 백엔드에 1.0 으로 요청해서 ③을 없앴고, ① 이 있을 때만 클라이언트 keep-alive 를 유지한다. 204/304 는 본문 없이 끝난 것으로 본다.
- 요청의 경계는 Content-Length 로 잡는다. POST 본문을 정확히 그만큼만 소비해야 같은 연결의 다음 요청이 어디서 시작하는지 안다.
- keep-alive 는 연결 하나의 속성이라 구간마다 따로 정하고, 그래서 Connection 류 헤더는 hop-by-hop 으로 지운다.

**동시성 모델의 트레이드오프**

- phase 2 의 스레드 풀을 그대로 쓴다. 프록시 요청 하나는 워커 하나가 `connfd` 와 `backendfd` 를 쥐고 끝까지 처리한다 (blocking I/O).
- 얻은 것: `serve_proxy` 가 위에서 아래로 읽히는 직선 코드이고, keep-alive·503·종료 처리·시간 제한을 그대로 받는다.
- 치른 것: 느린 백엔드가 워커를 시간 제한만큼 붙잡는다. 워커 수(`-w`)가 곧 동시 처리 상한이고, 가득 차면 큐(`-q`)에서 기다리다 503 을 받는다. 백엔드 시간 제한을 5초로 짧게 둔 이유이기도 하다.
- 이벤트 루프(`epoll`)는 느린 연결이 fd 하나로 끝나서 C10K 에 유리하지만, 읽기·쓰기·connect·CGI 를 전부 non-blocking 상태 머신으로 바꿔야 한다. 이번에는 phase 2 의 선택을 유지했다 (아래 "알려진 한계").

**메모리·자원 관리**

- fd 두 개: `backendfd` 는 `serve_proxy` 가 모든 종료 경로에서 닫고 `connfd` 는 워커 풀이 닫는다. 어느 쪽이 끊겨도 새지 않는다. 기능 테스트가 프록시 프로세스의 `/proc/<pid>/fd` 개수를 시나리오 전후로 비교한다.
- 백엔드 소켓은 `SOCK_CLOEXEC` 로 만든다. CGI 를 `fork`+`exec` 하는 자식이 백엔드 소켓을 물려받지 않게 하는 것이고, phase 2 에서 겪은 fd 상속 버그와 같은 문제다.
- POST 본문 버퍼는 모든 경로에서 `free` 한다. 규칙·백엔드는 고정 크기 배열이라 `malloc`/`free` 짝이 없다. 읽는 길이는 전부 상한이 있다 (헤더 16KB, URI 8KB, 헤더 64개, 본문 1MB).
- ASan·UBSan·LSan 빌드와 valgrind 로 기능 테스트 전체를 돌려 확인한다.

**시그널·종료**

- `SIGPIPE` 는 무시하고 `send` 에 `MSG_NOSIGNAL` 을 준다. 클라이언트가 중계 도중 끊어도 프로세스는 죽지 않고 `EPIPE` 로 돌아와 `client closed` 로 정리된다.
- `SIGINT`/`SIGTERM` 은 phase 2 의 정상 종료를 그대로 쓴다. 백엔드를 기다리는 워커는 시간 제한까지 깨어나지 않는 한계가 있다 (아래).

## 알려진 한계

### keep-alive 연결이 워커를 붙잡음 (스레드 풀 모델)

워커 스레드는 연결 단위로 일한다. keep-alive 연결은 다음 요청을 기다리는 동안(idle,
최대 `KEEPALIVE_TIMEOUT_MS` = 5초)에도 워커 하나를 차지한다. 그래서 워커 수(`-w`, 기본 8)만큼의
클라이언트가 가만히 연결만 열어 두어도 새 연결은 큐(`-q`)에서 기다리고, 큐까지 차면 503 을 받는다.

이벤트 루프(`poll`/`epoll`) 모델은 idle 연결을 fd 하나로만 들고 있어 이 문제가 없지만,
읽기·쓰기·CGI 를 전부 non-blocking 상태 머신으로 바꿔야 한다.
keep-alive 연결이 닫힐 때 남기는 로그 `(keep-alive closed: 이유, N requests, 초)` 로
연결이 워커를 얼마나 붙잡았는지 볼 수 있다.

### 강제 종료가 CGI 실행 중이면 늦어짐

종료 신호(SIGINT/SIGTERM) 뒤 처리 중인 연결을 최대 `SHUTDOWN_TIMEOUT_MS`(10초) 기다리고,
넘기거나 신호가 한 번 더 오면 연결 소켓을 `shutdown` 해서 강제로 끊는다 (종료 코드 2).
이때 워커가 소켓이 아니라 CGI 파이프를 기다리는 중이면 소켓을 끊어도 깨어나지 않아,
CGI 시간 제한(`CGI_TIMEOUT_MS`, 5초)까지 더 걸릴 수 있다 (최악 10 + 5초).
CGI 자식의 pid 를 워커마다 기록해 강제 종료 때 kill 하면 없앨 수 있지만, 구조가 커져서 감수했다.


### 리버스 프록시: 백엔드가 느릴 때

백엔드 시간 제한은 `PROXY_CONNECT_TIMEOUT_MS`(connect 한 번, 5초)와 `PROXY_TIMEOUT_MS`
(응답 헤더 전체, 그리고 본문 조각 사이 무응답, 5초)다. 그래서 다음은 남는다.

- connect 재시도는 백엔드마다 따로 시간을 잰다. 응답 없는 IP 가 여러 개면 최악 (백엔드 수 x 5초)
  뒤에 504 가 된다.
- 강제 종료(종료 신호 뒤 시간 초과, 두 번째 신호)는 클라이언트 소켓만 끊으므로, 백엔드를 기다리는
  워커는 위 시간 제한까지 깨어나지 않는다 (최대 5초 + 재시도분).
- 응답 전송 제한(`SEND_TIMEOUT_MS`, 30초)은 응답 하나 전체 기준이라, 백엔드가 조각마다 5초 안에
  꾸준히 보내더라도 전체가 30초를 넘으면 클라이언트 연결이 끊긴다.

자기 자신을 가리키는 규칙(루프백·0.0.0.0 이면서 포트가 `-p` 와 같음)은 시작할 때 거부하지만,
다른 로컬 IP 나 다른 프록시를 거쳐 돌아오는 루프는 막지 못한다.
