# Phase 1 아키텍처

기준: `5e3e68d`. CLI, 일반 정적 파일, 수신·송신 마감, 접근 로그를 포함한 Phase 1 기준선을 설명한다.
현재 `src/` 배치와 LT 이벤트 루프는 [HTTP 서버 코드 읽기](../public/http-server-guide.html)를 따른다.
동작 계약은 [요구사항](PHASE_1_REQUIREMENTS.md), 실행 증빙과 남은 검증은 [테스트](PHASE_1_TESTING.md)를 따른다.
아래 구현 선택은 인터뷰에서 확정한 요구와 구분하며, D-01~D-08의 Phase 1 이력은 [진행 원장](archive/PHASE_1_LEDGER.md)에 보관한다.

## A-01 설계 방향과 대안

관련 요구사항: P1-01, P1-03, P1-04.

Phase 1은 단일 프로세스가 한 번에 연결 하나의 요청 하나만 진행한다.
2026-11-20 사용자 결정으로 블로킹 I/O를 사용하고 정상 종료·시그널 처리는 Phase 2 시작으로 옮긴다.
스레드 풀·자식 프로세스별 요청 처리·N 연결 이벤트 루프는 만들지 않는다.
HTTP 처리와 소켓 I/O의 책임만 분리해 Phase 2에 재사용한다.

실행 환경은 Linux Docker 컨테이너로 확정했다. macOS 네이티브 구현은 필수 범위에서 제외한다.
CLI·실행 플랫폼은 요구사항 P1-02~04, 파일 시스템 지원 조건은 A-06을 따른다.
서버 시그널 전달과 정상 종료 설정은 Phase 2 시작의 D-07 하위 결정이다.
컨테이너의 격리만으로 정적 루트 경계나 자원 정리 요구를 충족했다고 간주하지 않는다.

| 대안 | 이점 | 한계 | 현재 판단 |
| --- | --- | --- | --- |
| 블로킹 I/O + 남은 마감에 맞춘 소켓 타임아웃 | 순차 처리 흐름을 유지함 | 호출마다 절대 마감에서 남은 시간을 다시 계산해야 함 | Phase 1 구현, A-04 |
| 활성 클라이언트 하나 + 논블로킹 I/O + poll 기반 대기 | 부분 I/O와 여러 마감을 한 제어 흐름에서 처리 | 초기 학습 코드의 복잡도가 커짐 | 이전 검토안. Phase 1에 적용하지 않음 |
| 처음부터 여러 연결의 이벤트 루프 | 높은 동시성으로 확장 가능 | Phase 1에 Phase 2의 상태·스케줄링이 유입됨 | Phase 2로 미룸 |

논블로킹 소켓을 쓴다고 반드시 여러 클라이언트를 동시에 처리하는 것은 아니다.
Phase 1은 현재 연결의 처리를 마친 뒤 다음 연결을 받으며, 종료 통지 대기는 구현하지 않는다.
큰 프레임워크나 다중 구현용 인터페이스를 미리 만들지 않는다.

## A-02 책임과 데이터 흐름

관련 요구사항: P1-03~08, P1-13~17, P1-21, P1-24~25.

| 파일 | 책임 |
| --- | --- |
| `app.c` | CLI 검사, 루트 FD 확보와 시작 검사, echo·정적 파일·오류 응답 준비 |
| `webserver.c` | 리스너·순차 accept, 요청 파싱과 응답의 연결, 스트리밍과 정리 |
| `http.c` | 요청 라인·헤더·head 의미 검증, 본문 프레이밍과 청크 상태, HTTP 응답 헤더 |
| `router.c` | 메서드 지원 확인, 경로 디코딩, echo·정적 파일·오류 분류. 파일 I/O 없음 |
| `static_response.c` | 정적 자원과 인덱스 선택, MIME·공개 판정, 308·405·오류 응답 준비 |
| `static_file.c` | 고정 루트 기준 파일 및 링크 해석, 확인한 파일 객체를 읽을 FD 반환 |
| `connection.c` | 단조 시계 마감, 부분 I/O, 입력 폐기, READY·JSONL·진단 출력 |

```text
CLI 검증 -> 루트 확보 -> socket/bind/listen
  -> accept
  -> 헤더 점진 파싱
  -> head 의미 검증 -> 프레이밍/Expect -> 라우팅/정적 자원 판정
  -> [오류/308이면 바로 최종 송신]
  -> [필요하면 100 Continue]
  -> [본문 수신 및 전송 디코딩]
  -> echo 응답 준비 또는 미리 연 정적 파일 사용
  -> 최종 헤더 + 본문 송신
  -> 제한된 연결 정리 + 접근 로그
  -> 다음 accept
```

세부 우선순위는 요구사항의 조합별 판정표를 따른다. 정적 자원의 403/404는 자원별 405보다 앞선다.

## A-03 연결과 파서 상태

관련 요구사항: P1-04~12, P1-14, P1-24, P1-26.

`http_parse_request_line(data, length)`는 요청 라인 시작부터의 누적 버퍼를 받는다.
NEED_MORE이면 호출자가 받은 바이트를 보존하고 추가 수신분을 붙여 다시 호출한다.
COMPLETE이면 CRLF를 포함한 소비 길이와 메서드·요청 대상의 포인터/길이,
major/minor 숫자를 반환한다. 참조 필드를 사용하는 동안 원본 버퍼를 유지해야 한다.
입력을 수정하거나 NUL 종료를 요구하지 않으며 CRLF 뒤의 헤더·본문 바이트는 소비하지 않는다.
NEED_MORE/ERROR에서는 소비 길이 0, 빈 요청 필드이며 오류 코드는 ERROR에서만 400/414다.
8,192바이트 한도 안에서 매번 다시 검사하는 단순한 구현이며 별도 수신 상태는 갖지 않는다.
요청 대상의 URI 유효성·지원 버전·라우팅 판정은 이 구문 분리 함수와 별개다.

`http_parse_headers(data, length, request_line_length)`는 요청 라인 뒤부터의 누적
바이트를 매번 처음부터 검사한다. 마지막 인자는 정상 요청 라인의 CRLF 포함 소비 길이로,
32,768바이트 총량에서 먼저 뺀다. 필드 줄은 CRLF 포함 8,192바이트, 필드 수는 100개다.
동적 할당 없이 `http_headers.fields`의 고정 배열에 이름·값 참조를 기록한다.
원래 이름 대소문자·중복·순서를 보존하고 값의 앞뒤 SP/HTAB만 제외한다.
필드별 의미 해석이나 이름별 병합은 하지 않는다. 이름 비교는 후속 단계에서
대소문자를 구분하지 않아야 한다. CL/TE 중복·충돌 검사는 본문 초기화에서 수행하며
Host의 필수/중복/값 검사는 별도 head 의미 검증에서 수행한다.
빈 줄에서 COMPLETE와 헤더 시작 기준 소비 길이를 반환하고 뒤의 본문은 검사하지 않는다.
NEED_MORE/ERROR는 소비 0·빈 목록, 문법 오류는 400, 자원 제한은 431이다.
이 참조 목록도 원본 버퍼 수명을 따른다.

현재 서버는 최대 32,768바이트의 head 버퍼에 한 번에 최대 1,024바이트씩 누적한다.
요청 라인 COMPLETE 뒤 헤더를 파싱하고 `http_validate_request_head()`를 호출한다.
버전 → 대상 구문 → Host 순서로 검사하고 실패 시 400/505 후 종료한다.
성공해야 `http_body_init()`로 프레이밍·Expect를 정하므로 의미 오류에서는 본문 할당·
추가 recv·100 송신이 없다. 같은 recv로 이미 받은 본문까지 소켓에서 안 읽었다고 주장하지 않는다.
이미 받은 본문 바이트부터 소비한 뒤 추가 recv 데이터만 `http_parse_body()`에 넣는다.
본문 함수는 누적 원문 재파싱이 아닌 상태 머신으로, 각 호출의 consumed는 NEED_MORE에서도 유효하다.
CL은 남은 길이, chunked는 크기 줄·데이터·CR·LF·trailer·완료 상태를 가진다.
디코딩 바이트만 필요에 따라 realloc으로 늘리며 용량은 1 MiB 이하다.
청크 원문 전체나 청크 개수에 비례하는 별도 메모리는 확보하지 않는다.
메타데이터 줄 버퍼는 8,192바이트이며 확장·trailer 카운터는 본문과 별개다.
`http_request { line, headers, target, body }`로 head/완료 본문을 표현한다.
정적 파일/오류는 body가 비어 있는 head 단계, echo는 본문 COMPLETE 뒤에 `app_handle_request()`를
한 번 호출한다. echo 응답이 본문 포인터를 빌리므로 콜백 반환 직후가 아니라 송신 완료/실패까지
head와 디코딩 본문을 유지한 뒤 해제한다.
앱은 본문 원문을 로그에 남기지 않는다.
미완성 EOF는 400, 파서 오류는 400/413/414/417/431/501, 할당 실패는 500이다.
추가 본문 수신이 필요한 100-continue는 한 번 송신하며 이미 완성된 본문에는 생략한다.
EINTR 재호출·부분 송신·MSG_NOSIGNAL은 100과 최종 응답에 동일하게 적용한다.
미소비 구간은 본문에 합치거나 두 번째 요청으로 실행하지 않는다.
마감은 A-04, 읽지 않은 입력의 정리는 A-08을 따른다.

```text
ACCEPTED -> READ_HEADERS -> VALIDATE_HEADERS
                         -> WRITE_INTERIM -> READ_BODY
                         -> READ_BODY
                         -> PREPARE_FINAL
READ_BODY -> PREPARE_FINAL -> WRITE_FINAL -> CLOSE
어느 단계에서든 복구 불가 연결 실패 -> CLOSE
유효한 오류 응답을 보낼 수 있는 실패 -> PREPARE_ERROR -> WRITE_FINAL -> CLOSE
```

- 파싱 성공과 메시지 완료는 다르다. COMPLETE는 정확한 경계가 확인됐을 때만 반환한다.
- 문자열 종료 NUL에 의존하지 않고 모든 입력에 길이를 붙인다.
- 수신 버퍼의 미소비 구간과 파서 상태를 보존한다. 한 recv에 여러 구간이 올 수 있다.
- CL 본문은 남은 길이, chunked는 크기 줄·데이터·CRLF·trailer 상태를 별도로 관리한다.
- 청크 크기·CL 변환 전에 범위를 검사한다. 누적 제한도 덧셈 전 남은 용량으로 확인한다.
- 구문이 유효한 길이가 남은 본문 한도보다 크면 413, 잘못된 숫자는 400으로 분리한다.
- TE 체인은 전체 문법·순서 검증 후 지원 여부를 판정한다.
- CL·TE 없는 요청은 헤더 종료로 완료한다. 수신 버퍼의 나머지를 echo 본문으로 돌리지 않는다.
- Phase 1은 남은 바이트를 다음 요청으로 실행하지 않는다.
- recv=0 전에 요청이 완성됐는지 확인한다. 송신 방향이 살아 있으면 응답할 수 있다.

서버는 라우팅/파일 오류와 308을 본문 전에 처리하고, 성공 가능한 GET/HEAD의 프레이밍된
본문은 공통 한도로 수신·검증 후 버린다. 100 생략·반복과 trailer 정책은 요구사항을 따른다.
처리 편의를 위해 지원하지 않는 입력을 정상 요청처럼 조용히 받아들이지 않는다.

## A-04 제한과 시간

관련 요구사항: P1-09~12, P1-24, P1-26~27.

숫자 제한의 단일 기준은 요구사항 P1-09~P1-12다.
본문·초기 헤더·청크 줄·확장 누적·trailer는 별도 카운터로 관리한다.
한 recv에 한도가 넘는 데이터가 와도 전체를 신규 메모리에 복사한 뒤 검사하지 않는다.

시간은 단조 시계의 절대 마감으로 표현한다.

```text
header_deadline = accepted_at + 10s
receive_deadline = accepted_at + 60s
body_idle_deadline = last_body_receive_at + 30s
final_send_deadline = final_send_started_at + 30s
```

`connection.c`는 `CLOCK_MONOTONIC`으로 남은 시간을 계산해 블로킹 호출에
`SO_RCVTIMEO` 또는 `SO_SNDTIMEO`를 건다. 본문 무진행 마감은 전체 수신 마감으로 제한한다.
100은 같은 본문 수신 마감 안에서 보내며, 408을 포함한 최종 응답에는 별도의 송신 예산을 한 번 준다.

- 현재 단계에 적용되는 수신·송신 마감 중 가장 이른 것으로 대기 시간을 계산한다.
- EINTR 후에는 남은 시간을 다시 계산한다. 원래 제한으로 다시 시작하지 않는다.
- EAGAIN/EWOULDBLOCK은 남은 시간을 다시 확인한 뒤 처리한다.
- 파서가 기존 버퍼를 소비하는 것만으로 무진행 타이머를 갱신하지 않는다.
- 본문 단계의 실제 `recv` 진행에는 청크 프레이밍 메타데이터도 포함한다.
- 소켓 I/O가 반환되어도 수신·송신 절대 마감을 다시 확인한다. 만료 경계에서는 만료를 우선한다.
- 408 송신을 위해 새 수신 기회를 주거나, 오류를 거듭 보내며 연결 수명을 연장하지 않는다.
- 소켓 타이머만으로 디스크·로그의 블로킹 시간까지 보장됐다고 주장하지 않는다.
  지원 파일 시스템과 로그 출력의 블로킹 제약은 D-02·D-06의 일부다.

서버의 `shutdown_deadline = shutdown_requested_at + 30s`와 기존 마감의 결합은
P1-27과 함께 Phase 2 시작에 구현한다.

## A-05 URI·라우팅·공개 정책

관련 요구사항: P1-06, P1-17, P1-19~23.

`app_match_request()`는 `app.c`의 정적 테이블(메서드·경로·함수 포인터)을
`router_match_request()`에 넘긴다. 라우터는 미구현 메서드를 먼저 거부하고,
origin/absolute-form 경로를 한 번 디코딩해 동적 라우트(`/echo`) 또는 정적 자원 후보를 선택한다.
query는 무시한다. 라우터는 I/O 없이 함수 포인터 또는 정적 경로와 상태·Allow를 전달한다.
서버는 프레이밍·Expect 초기화 뒤 앱에 경로 판정을 요청한다. 앱은 정적 응답과 오류를
본문 전에 준비하며, 본문 완료 후에만 선택된 동적 핸들러를 호출한다.
`handle_echo()`는 디코딩된 본문 바이트를 응답 송신이 끝날 때까지 빌린다.
`http_response`는 상태/Content-Type/Allow/Location/본문 slice/file_fd를 담는다.
file_fd >= 0이면 slice.length는 fstat 크기 스냅샷이며 서버가 FD를 소유한다.
서버는 HEAD에서 헤더만, echo에서 명시적 바이트 길이만, 파일에서 1,024바이트 버퍼로
스냅샷 길이까지만 송신한다. 실패 시 두 번째 최종 응답을 덧붙이지 않는다.
파일 증가분은 보내지 않고 조기 EOF·읽기 실패는 불완전 송신으로 종료한다.
성공/본문 오류/수신 실패/100 실패/최종 송신 실패에서 FD와 본문 메모리를 모두 정리한다.

head 검증은 원문을 `http_target`의 form/authority/path/query로 분리한다.
origin·HTTP(S) absolute·CONNECT authority·OPTIONS asterisk의 구문과 Host를 검사하며,
absolute authority가 Host보다 우선한다. 빈 absolute path는 정적 `/`를 참조한다.
나머지 구성요소는 head 버퍼 참조이며 callback 이후 보관하지 않는다.
path/query의 percent encoding은 그대로다. Router는 원문 target 전체나 Host를 다시
조합하지 않고, 아래 정책을 `target.path`에 적용한다.
현재 구문 성공은 메서드 지원·TLS·proxy·자원 권한을 승인하지 않는다.

```text
원래 request-target
  -> URI 구성요소 분리
  -> path 한 번 디코딩, 잘못된 %/NUL 거부
  -> 경계 위반과 dot segment 처리
  -> 숨김/공개 정책과 라우팅
  -> 안전한 파일 열기
  -> 실제 대상에도 경계/숨김/허용 종류 적용
```

- query를 파일명에 합치지 않는다. `%3F`를 구분자로 재해석하지 않는다.
- `+`를 무조건 공백으로 바꾸는 폼 디코더를 경로에 재사용하지 않는다.
- 단순 문자열 접두사 검사로 `/www2`를 `/www` 내부로 인정하지 않는다.
- root를 벗어나려는 `..`를 먼저 제거해서 정상 경로로 위장하지 않는다.
- 숨김 정책과 정상적인 `.`·`..` 경로 구성요소를 구분한다.
- URL 별칭·심볼릭 링크로 확장자나 숨김 정책이 우회되지 않는 기준이 필요하다.
- `Location`은 서버가 검증한 URL 구성요소로 생성한다.
  클라이언트가 준 Host나 원문을 그대로 연결해 외부 리다이렉트·헤더 삽입을 만들지 않는다.
- 존재 확인·권한·라우팅 순서가 403/404 구분과 충돌하지 않게 하나의 판정표를 사용한다.

구체적인 상태·MIME·308 정책은 요구사항 P1-17·P1-19~22에 둔다.

## A-06 파일 시스템 경계

관련 요구사항: P1-16~18, P1-21~22, P1-26, P1-31.

`app.c`는 운영자가 지정한 디렉터리(디렉터리를 가리키는 링크 포함)를 한 번 열고
`static_file_open()`으로 필요한 API를 검사한다. 요청마다 루트 경로 문자열을 다시 열지 않는다.

### 불변 조건

1. 시작 시 확보한 루트와 요청 경로를 기준으로 파일을 연다.
2. 권한·일반 파일 여부·크기는 실제 읽을 열린 FD에 대해 확인한다.
3. 링크·중간 디렉터리·상대/절대 대상이 루트 이탈을 만들지 못한다.
4. 검사 뒤 경로를 일반 open으로 다시 열어 검사 대상을 바꾸지 않는다.
5. 숨김·확장자 정책도 사용자 URL 이름만으로 우회되지 않아야 한다.
6. 실패한 탐색의 임시 FD와 메모리를 모두 회수한다.

`static_file.c`는 각 경로 확인을 루트 FD 기준 `openat2`와
`RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS | RESOLVE_NO_XDEV`로 수행한다.
링크는 열린 객체에서 대상을 읽어 정책을 적용하고, 경로를 루트에서 다시 해석한다.
중간 디렉터리 FD를 기준으로 나머지를 열지 않는다. 링크 해석은 최대 40회다.
절대 대상은 컨테이너에서 확인한 루트 경로 내부여야 한다. 실행 중 루트 자체를 이름 변경하는
배치와 별칭/대소문자 비구분 파일 시스템은 지원 검증 범위 밖이다.

`O_PATH` FD로 객체 종류를 먼저 확인하고 일반 파일만 `/proc/self/fd`로 읽기용 FD를 연다.
재확인한 읽기 FD가 같은 객체인지 검사하고 그 FD를 응답에 넘긴다.
인덱스도 같은 해석기를 사용한다. 시작 시 루트 디렉터리의 `openat2` 검사가
실패하면 종료한다. `/proc/self/fd`에 의존하는 실제 파일 열기가 실패하면 그 요청을
거부하며, 경계를 약화하는 대체 동작은 없다.
운영자가 직접 공개 루트에 배치한 일반 파일과 하드 링크의 내용은 신뢰한다.
파일 크기 스냅샷은 전송 길이를 고정할 뿐, 변경되는 파일 내용의 일관된 스냅샷을 보장하지 않는다.
링크·디렉터리·파일 변경의 전체 제어 테스트는 아직 미실행이다(T-18).

## A-07 응답·echo·HEAD

관련 요구사항: P1-13~15, P1-23~25.

헤더 작성과 본문 소스를 분리하고 송신 오프셋을 유지한다.
메모리 echo, 고정 오류, 파일 스트림에 같은 부분 송신 원칙을 적용한다.
청크 형식과 초기 헤더·trailer는 echo 데이터에 포함하지 않는다.

현재 구현은 파싱/프레이밍 오류와 앱 오류 모두 `http_response`로 준비해 같은
헤더 생성·부분 송신 경로를 사용한다. 오류 본문은 상태별 영어 사유 구문의
고정 바이트이며 요청 원문·실제 경로·errno 설명을 포함하지 않는다.
정상 요청 라인을 파싱한 직후 HEAD를 기억하므로 헤더·head 의미·본문 오류에서도
표현 길이는 유지하고 본문 송신만 생략한다. 요청 라인 자체의 실패에는 HEAD를 추정하지 않는다.
100 Continue만 별도 고정 중간 응답이며 본문과 Content-Length가 없다.
수신 시간 초과가 408로 이어지는 흐름과 최종 송신 예산은 A-04, 닫기 예산은 A-08을 따른다.

echo는 최대 1 MiB의 본문을 모은 뒤 확정된 길이로 최종 응답을 작성한다.
대용량 파일처럼 임시 파일로 저장하지 않는다.
수신 Content-Type·Content-Encoding을 응답에 복사하지 않는다.
고정 echo는 Content-Encoding을 해석하지 않으므로 해당 바이트도 그대로 반환한다.
자동 압축 해제를 추가하지 않으며, 응답에는 Content-Encoding을 복사하지 않는다.

응답 작성자는 다음을 관리한다.

- final response started 여부: 최종 오류를 두 번 생성하지 않음.
- HEAD 여부: 성공·오류·리다이렉트의 본문을 모두 억제.
- 계산한 표현 길이와 실제 송신한 본문 길이의 구분.
- 최종 응답과 100 중간 응답의 분리.
- Date·Content-Type·Content-Length·Allow·Location 등 상태별 필수 헤더.
- echo의 octet-stream·nosniff와 모든 최종 응답의 Connection: close.
- 고정 오류 본문: 코드별 본문 바이트와 길이가 일치하며 내부 원인을 넣지 않음.

큰 숫자 출력은 size_t·off_t 등을 잘못 축소하지 않는다.
파일 본문이 크다고 헤더 Content-Length를 작은 정수로 잘라서는 안 된다.

## A-08 정리·시그널·서버 수명

관련 요구사항: P1-04, P1-12, P1-26~27.

| 자원 | 소유자 | 해제 시점 |
| --- | --- | --- |
| 루트 FD | `app.c` | 시작 검사 실패 또는 `webserver_run()` 반환 |
| listener·접근 로그 FD | `webserver.c` | 시작 실패 또는 서버 루프 반환 |
| 클라이언트 FD·수신 버퍼·파서·echo 메모리 | 현재 연결 | 성공·오류·중단 모두 |
| 탐색 중 디렉터리/링크 핸들 | 파일 접근 코드 | 다음 단계 또는 탐색 실패 |
| 정적 파일 FD·송신 버퍼 | 응답/현재 연결 | 송신 완료·실패·시간 초과 |
| 테스트 프로세스·임시 루트 | 테스트 하네스 | 테스트 성공·실패·시간 초과 |

각 자원은 한 소유자만 닫는다. 오류 경로마다 흩어진 중복 close/free를 만들지 않는다.
부분 초기화 실패도 같은 소유권 규칙으로 되돌린다.

SIGPIPE에 대한 송신 실패 안전성 정책은 P1-26대로 Phase 1에 유지한다.
SIGINT·SIGTERM에 의한 서버 정상 종료는 P1-27과 함께 Phase 2 시작으로 이관한다.
Phase 1에는 핸들러·종료 플래그·self-pipe·pselect 기반 종료 통지를 넣지 않는다.

Phase 2 시작에는 핸들러가 안전한 플래그·통지만 전달하도록 구현하고,
종료 통지가 유실되지 않는 대기 방식과 통지 FD 소유권을 D-07에서 정한다.
종료 인지 뒤 새 accept를 중단하며 현재 요청과 가장 이른 마감만 진행한다.
반복 시그널이 30초 유예를 다시 시작하지 않는지도 그때 검증한다.

완전 송신 후 `shutdown(SHUT_WR)`을 호출하고, 일시적으로 `O_NONBLOCK`을 설정해 `read()`로 읽을 수 있는
입력을 최대 32 KiB 폐기한 뒤 소켓을 닫는다. 불완전 송신은 닫기 경로로 간다.
추가 요청은 실행하지 않는다.

Phase 1은 느린 현재 연결이 다음 연결을 지연시키는 가용성 한계가 있다.
현재 계약의 전체 수신 상한은 accept부터 60초이므로 헤더 10초를 다시 더하지 않는다.
그 뒤 최종 송신 30초가 붙을 수 있다. 파일 I/O와 일반 파일·터미널 로그 쓰기는
소켓 시간 제한으로 제어하지 않으므로 연결 수명 전체의 90초 상한을 보장하지 않는다.
이 한계는 Phase 2의 동시성 도입 이유이지 Phase 1에서 N 연결 처리를 몰래 추가할 이유가 아니다.

## A-09 로그 계약

관련 요구사항: P1-23, P1-28, P1-30.

| 필드 | 의미 |
| --- | --- |
| `method` | 파싱한 메서드, 알 수 없으면 null |
| `path` | query 분리 후 디코딩 전 URL 경로, 알 수 없으면 null |
| `status` | 선택한 최종 HTTP 상태, 선택하지 못했으면 null |
| `duration_ms` | accept부터 연결 처리 완료까지 단조 시계 기반 시간 |
| `bytes_sent` | 커널이 인수한 최종 응답 바이트 수. 헤더 포함, 100 제외 |
| `complete` | 최종 응답 전체를 커널에 넘겼는지 여부. 클라이언트 수신 확인은 아님 |

HEAD도 헤더 송신분을 `bytes_sent`에 포함한다. 실패로 선택한 상태와 실제 전달이 다를 수 있다.
`READY <port>` 뒤 stdout에는 처리한 연결당 JSONL 한 건을 시도하고, 진단은 stderr에 쓴다.
문자열은 JSON 이스케이프하고, 긴 경로는 `<truncated>`로 대체한다.
본문·인증정보·실제 파일 경로는 접근 로그에 넣지 않는다.
stdout이 파이프이면 비대기 쓰기를 사용하며 출력이 정체되면 해당 레코드를 버린다.
파일과 터미널에 직접 쓰는 배치는 출력 장치가 정상 진행하는 것을 전제로 한다.

## A-10 검증을 위한 경계와 구현 순서

관련 요구사항: P1-02~03, P1-29~32.

테스트를 위해 실제 동작을 우회하는 생산용 백도어·관리 HTTP 경로를 만들지 않는다.
필요한 제한 시계·오류 주입·준비 신호는 테스트 빌드나 내부 함수 경계에서 제공한다.
HTTP 응답을 해석할 테스트 코드는 서버의 파서를 그대로 재사용하지 않는다.

구현 이력과 후속 순서:

1. D-07의 이미지·도구·빌드 하위 계약을 DECIDED로 정하고, 실제 컨테이너 빌드 전에 Docker CLI·데몬 접근을 확보한다.
2. Docker 빌드 환경·Makefile과 실제 CLI의 C/Python 테스트를 만든다. 준비 통지는 관련 하위 결정 뒤에 결합하고 서버 정상 종료는 Phase 2 시작으로 분리한다.
3. I/O 없는 HTTP·URI·길이·청크·MIME 단위 테스트와 구현을 진행한다.
4. 블로킹 순차 소켓·마감·부분 I/O를 결합한다.
5. echo·Expect·HEAD·오류 응답을 실제 소켓에서 검증한다.
6. Linux 컨테이너의 파일 경계 설계에 따라 정적 파일을 통합하고 실제 경계 테스트로 증명을 보완한다.
7. 정리·로그·보안·메모리/FD를 검증하고 성능 기준선을 남긴다.
8. Phase 2 시작에 정상 종료·시그널 처리(P1-27/T-27)를 구현한 뒤 다중 연결 동시 처리로 확장한다.

실제 빌드 타깃과 실행 증빙은 테스트 문서에 있다.
아키텍처의 존재를 코드 구현이나 컨테이너 실행 검증 통과의 증거로 삼지 않는다.

### 첫 구현 단위의 범위 (이력)

첫 단위는 Docker 빌드 환경과 도구 체인의 실행 확인이다.
`Dockerfile`·`.dockerignore`·`dev.sh`·`Makefile`과 `tests/environment`의 환경 검사를 작성했다.
`sh dev.sh build`는 이미지를 빌드하고 `sh dev.sh check`는 컨테이너 안의 `make dev-check`를 실행한다.
베이스 이미지·도구·비특권 실행 계약은 D-07의 개발환경 하위 결정과 README를 따른다.
구성 파일 작성과 실제 빌드·실행 통과는 구분하며, 실행 상태는 진행 원장에서 확인한다.

이 단계의 성공은 서버나 T-02 전체의 성공이 아니다.
빈 응답 서버·항상 성공하는 테스트를 기능 구현 대신 두지 않으며,
CLI부터는 실제 동작과 실패 사례를 함께 구현한다.
프로덕션 기능은 HTTP 처리에 필요해지는 순서대로 추가한다.
