# Phase 3 착수 초안 — 리버스 프록시

초안 작성 당시의 기준은 `68133c4`였다. 실제 구현 브랜치
`feat/phase3/woong`은 소스 재배치와 데모를 포함하고 Docker 기능·메모리
검증을 마친 `2785e06`에서 분기했다. 아래는 착수 당시의 제안이며,
현재 작업 범위에는 두 백엔드 라우팅과 응답 스트리밍이 포함된다.
현재 동작은 [구현 계약](PHASE_3_ARCHITECTURE.md), 실행 증빙은
[Phase 1–3 통합 검증](PHASE_3_TESTING.md)을 참고한다. 현재는 앞단 프록시와
정적·echo 백엔드를 별도 실행 파일로 분리했으며, 프록시는 미일치 경로에
`404`를 반환하고 응답 뒤 클라이언트 연결을 닫는다.

## 범위 제안

- 정적 파일과 `/echo`는 현재처럼 로컬 처리한다. 처음에는 `/api/`만 설정된
  HTTP 백엔드로 보낸다. 클라이언트의 `Host`나 absolute URI로 접속 대상을
  선택하지 않는다.
- 라우팅은 반복 가능한 CLI 설정으로 두고 경로 구간 경계로 매칭한다.
  긴 프리픽스가 우선이며 접두사 중복 설정은 거부한다. 미일치 요청은 기존
  로컬 라우터로 넘긴다. 백엔드로 전달할 때 프리픽스와 쿼리를 보존한다.
- 예: `/api/`는 A, `/api/admin/`은 B. 한 곳은 첫 마일스톤, 두 곳의 응답을
  실제로 구분해 라우팅해야 완료다. TLS, CONNECT, 풀링, 캐싱, 라운드로빈은
  첫 범위에서 제외한다.

## 작업 순서와 검증 기준

| 단위 | 작업 | Linux Docker 합격 기준 |
| --- | --- | --- |
| 1. 단일 백엔드 | 기존 LT `epoll`에서 백엔드 fd도 논블로킹으로 처리한다. 고정 길이 응답부터 연결한다. | GET과 바이너리 POST에서 상태 코드·본문을 보존한다. 백엔드 응답을 의도적으로 보류한 동안 별도 클라이언트의 로컬 `GET /`가 먼저 완료된다. |
| 2. HTTP 경계와 정리 | 양쪽 연결의 HTTP 경계, 부분 송수신 및 마감을 독립적으로 관리한다. 응답은 제한된 버퍼로 중계하고, 클라이언트가 느리면 백엔드 읽기도 늦춘다. | 큰 응답, 연결 거절·무응답, 중계 중 연결 종료를 검증한다. 반복 후 소켓 FD 수가 유휴 기준으로 돌아온다. |
| 3. 라우팅과 회귀 | 두 번째 목적지와 경로 우선순위·미일치 정책을 검증한다. | 실제 백엔드 두 곳의 응답이 구분되고, 기존 정적·echo·keep-alive·정상 종료 검사가 통과한다. |

## 구현 전에 닫을 HTTP 계약

- 백엔드 요청은 origin-form과 설정으로 만든 `Host`를 사용한다. 연결별
  헤더(`Connection`이 지목하는 필드 포함)는 다음 연결에 그대로 복사하지
  않는다. `Via` 정책과 보존할 종단 간 헤더는
  [RFC 9110 §7.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.6)에 맞춰 정한다.
- [RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)의
  길이 규칙으로 `HEAD`·본문 없는 상태, 고정 길이, chunked, EOF 종료 응답을
  구분한다. 첫 단위에서 지원하지 않는 응답 형태는 중계를 시작하기 전에
  오류로 처리하며, 이를 Phase 3 완료로 간주하지 않는다.
- 최종 응답을 보내기 전 연결 실패·잘못된 응답에는 `502`, 기한 초과에는
  `504`를 제안한다. 최종 응답을 보내기 시작한 뒤 중계가 실패하면 두 번째
  응답을 쓰지 않고 클라이언트 연결을 닫는다. 백엔드 연결 종료 자체가
  클라이언트 연결 종료를 의미하지는 않는다. 재사용 여부는 클라이언트 쪽
  메시지를 완결했는지와 기존 Phase 2 정책으로 판단한다.
- 연결·응답 헤더·중계 단계의 구체적인 마감과 버퍼 상한은 구현 전에 정한다.
  세션이 양쪽 fd를 정리하고, 한쪽이 닫힌 뒤 같은 epoll 배치의 남은 이벤트가
  해제된 세션을 참조하지 않도록 기존 세션 정리 흐름에 맞춘다.
