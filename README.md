**C17 · Linux 소켓 API로 구현한 HTTP/1.1 웹 서버와 리버스 프록시**

## 🌐 1. 소개와 구조

```text
클라이언트 → reverse-proxy → webserver A / B
                              ├─ 정적 GET / HEAD
                              ├─ 바이너리 POST /echo
                              └─ 선택적 CGI
```

- `webserver`와 `reverse-proxy`는 HTTP 파서·이벤트 루프를 공유하는 **독립 실행 파일**입니다.
- HTTP 기본 처리 → 동시 연결·재사용 → 리버스 프록시 순서로 확장했습니다.

## ⚙️ 2. 구현 핵심

```text
socket → bind → listen → epoll → accept4
                                  └─ 연결별 세션 → 요청 파싱 → 처리 → 응답
```

| 구성 | 핵심 구현 |
| --- | --- |
| 소켓 | 논블로킹 리스너와 연결 소켓, `SO_REUSEADDR` 설정 |
| HTTP | TCP 요청 경계가 없으므로 연결별 버퍼·파서 상태 유지, 부분 수신·전송 처리 |
| 응답 | 정적 파일은 나눠 전송, HEAD 본문 생략, `/echo`는 널 바이트까지 그대로 반환 |
| 동시 처리 | 단일 스레드의 LT `epoll`, 느린 연결은 상태를 저장하고 다음 연결 처리 |
| 프록시 | 요청 경로와 가장 많이 겹치는 규칙으로 백엔드 선택, 같은 경로는 라운드 로빈, 경로·쿼리 보존과 Host 재작성,<br/> 접속 실패 시 다음 백엔드 시도, 응답 전 실패는 502·기한 초과는 504|
| 연결·종료 | keep-alive·순차 파이프라이닝, 프록시는 백엔드 연결도 5초간 재사용, 종료 신호 시 새 연결 수락 중단 후 유예 종료 |

- **재시도는 요청을 쓰기 전 접속 단계에서만 합니다.**
- 이미 쓰기 시작한 요청은 중복 처리를 막기 위해 재전송하지 않습니다.

## 🎬 3. 라이브 데모

### 준비

기준 환경은 **Linux/amd64 Docker**입니다. 빌드 후 같은 컨테이너의 터미널 4개를 사용합니다.
8001·8002·8080 포트를 비워 둡니다.

```sh
# 호스트
sh dev.sh build
sh dev.sh shell
# 컨테이너
make
```

### ① 웹 서버 A/B와 프록시 실행

```sh
# 터미널 1
./webserver --port 8001 --root examples/round-robin/a
# 터미널 2
./webserver --port 8002 --root examples/round-robin/b
# 터미널 3
./reverse-proxy --port 8080 --route /=127.0.0.1:8001 --route /=127.0.0.1:8002
```

### ② 직접 접속과 라운드 로빈 확인

터미널 4에서 실행합니다.

```sh
# 직접 접속: 200, Backend A
curl --noproxy '*' --max-time 5 -i http://127.0.0.1:8001/

# 프록시 경유: Backend A → B → A → B
for i in 1 2 3 4; do
  curl --noproxy '*' --max-time 5 -fsS http://127.0.0.1:8080/ \
    | grep -o 'Backend .' | head -n 1
done
```

### ③ 장애 전환과 종료

| 동작 | 확인할 결과 |
| --- | --- |
| 터미널 1에서 A를 `Ctrl+C`로 종료 → 위 반복 명령 재실행 | **Backend B만 응답** |
| 터미널 2에서 B도 `Ctrl+C`로 종료 → 아래 요청 실행 | **502 Bad Gateway** |
| 터미널 3에서 프록시를 `Ctrl+C`로 종료 | 새 연결 수락 중단 후 종료 |

```sh
curl --noproxy '*' --max-time 5 -i http://127.0.0.1:8080/
```

- 접속 실패는 다른 백엔드로 전환하고, 모두 접속할 수 없으면 502를 반환합니다.
- 기한 초과는 504이며, 이미 클라이언트 응답을 시작한 뒤 실패하면 연결을 닫습니다.

## 🧪 4. 검증 결과

**Linux/amd64 Docker 환경에서 검증하였습니다**. 

| 검사 | 대상 | 결과 |
| --- | --- | --- |
| 단위 | 파서·세션·라우터·정적 파일·연결 I/O·프록시 | **C 실행 파일 8개 통과** |
| 기능 | 실제 소켓의 응답·동시 연결·재사용·종료·장애·CGI | **회귀 명령 종료 코드 0** |
| 메모리 | ASan·UBSan·LSan, Valgrind와 FD 추적 | **검사 범위에서 오류·누수 미보고** |
| 변이 | Mull로 코드 변형 후 C 단위 테스트 실행 | **3,982건 중 1,351건 검출 · 33.9%** |
| 퍼징 | libFuzzer + ASan·UBSan, 시드 16개 | **61초 · 4,174,818회 · 크래시·타임아웃 산출물 0개** |

### 🔬 생존 변이가 드러낸 단위 테스트의 빈틈

생존 기록 **2,631건 → 중복 제거 1,101개 → 다른 단위 테스트의 검출분 480개 제외 → 621개**를 추렸습니다.
33.9%는 실행 파일별 집계이며, 전체 코드 커버리지가 아닙니다.

| 놓친 검증 | 원인 | 변이를 넣었을 때 응답 |
| --- | --- | --- |
| 정적 POST·HEAD 최종 응답 | 라우트 선택과 GET 파일 응답까지만 검사 | POST `405 → 200`, HEAD `200 → 405` |
| 접두사와 길이가 같은 경로 | 같은 길이 입력을 absolute-form 거부 검사로만 사용 | `/api/`의 `200 → 404` |
| 400 오류 본문 | 라우트 상태만 검사하고 본문 생성은 미검사 | 상태 400 유지, 본문 `11 B → 0 B` |

- **세 변이는 C 단위 테스트를 통과했지만 기존 기능 테스트는 모두 검출했습니다.**
- 퍼징은 **HTTP 파서·프록시 요청 재구성·응답 헤더 파싱** 범위에서 실패가 관측되지 않았습니다.

```sh
make test-unit test-proxy-unit
make -B test test-shutdown test-epoll test-keepalive test-proxy test-cgi
sh tests/verify_phase3.sh
```

## 📊 5. 부하 측정과 한계

**CPU 2개 · 메모리 1 GiB · 응답 1 KiB · 요청마다 새 연결** 조건에서 2,000건씩 3회 측정했습니다.

아래는 처리량의 중앙값이며, 측정 요청은 모두 성공했습니다.

| 경로 | 동시성 1 | 동시성 8 | 동시성 32 |
| --- | ---: | ---: | ---: |
| 직접 정적 GET | 2,514 req/s | 1,607 req/s | 1,605 req/s |
| 프록시 경유 GET | 1,810 req/s | 1,040 req/s | 998 req/s |
| 기준 Python 백엔드 직접 GET | 1,475 req/s | 1,196 req/s | 943 req/s |

- 직접·프록시 경로의 백엔드 구현이 다르고 부하 생성기도 같은 컨테이너에 있습니다.
- 로컬 환경 한정이라는 점에서 한계가 있습니다.
