# week13-web-server

C17과 Linux 소켓 API로 HTTP/1.1 웹 서버와 리버스 프록시를 구현한 크래프톤 정글 13주차 프로젝트입니다.

**목차:** [개요](#overview) · [웹 서버 핵심 구현](#server) · [리버스 프록시 핵심 구현](#proxy) · [품질](#quality)

<a name="overview"></a>

## 개요

```text
클라이언트 ── HTTP ── reverse-proxy ── HTTP ── webserver A/B
                                                  ├─ 정적 파일
                                                  ├─ POST /echo
                                                  └─ /cgi-bin/이름 (선택)
```

`webserver`는 정적 파일과 동적 응답을 제공합니다. `reverse-proxy`는 요청 경로로 백엔드를 선택하고 응답을 중계합니다. 두 프로그램은 HTTP 파서와 이벤트 루프를 공유하지만 독립적으로 실행합니다. 프록시 없이 웹 서버에 직접 접속할 수도 있습니다.

### 요구 사항

| 단계 | 구현 범위 |
| --- | --- |
| [Phase 1](docs/PHASE_1_REQUIREMENTS.md) | TCP 연결 수락, HTTP/1.1 파싱과 응답, 정적 `GET`/`HEAD`, 바이너리 `POST /echo`를 구현합니다. |
| [Phase 2](docs/PHASE_2_REQUIREMENTS.md) | 논블로킹 I/O로 여러 연결을 처리하고, 연결 재사용·순차 파이프라이닝·정상 종료를 지원합니다. |
| [Phase 3](docs/PHASE_3_ARCHITECTURE.md) | 경로 기반 중계, 백엔드 풀, 접속 실패와 타임아웃 처리를 구현합니다. |

전체 범위는 [과제 요구 사항](docs/REQUIREMENTS.md)에서 확인할 수 있습니다.

### 빌드 및 실행

기준 환경은 **Linux/amd64 Docker**입니다. 호스트에서 개발 이미지를 빌드하고 셸을 엽니다. WSL에서는 `dev.sh`가 `docker.exe`를 사용합니다.

```sh
sh dev.sh build
sh dev.sh shell
```

개발 셸에서 두 프로그램을 빌드하고 웹 서버를 시작합니다.

```sh
make
./webserver --port 8080 --root public
```

같은 컨테이너의 다른 셸에서 `curl -i http://127.0.0.1:8080/`으로 시작 페이지를 확인합니다. 다른 셸이 필요하면 호스트에서 `docker exec -it <컨테이너-ID> bash`를 실행합니다. WSL에서는 `docker.exe`를 사용합니다. 브라우저 실행 방법은 [브라우저 라우팅 실습](docs/ROUTING_DEMO.md)에 정리했습니다.

## 웹 서버 핵심 구현

### TCP 소켓 서버

`socket()`으로 IPv4 TCP 논블로킹 소켓을 만들고 `SO_REUSEADDR`를 설정합니다. `bind()`로 주소와 포트를 지정한 뒤 `listen()`으로 연결을 받습니다.

리스너의 `EPOLLIN`은 **HTTP 요청이 아니라 수락할 TCP 연결이 준비됐다는 뜻**입니다. `accept4()`로 연결 전용 FD를 얻고, 각 FD에 `client_session`을 만들어 `epoll`에 등록합니다. 이후 `recv()`와 `send()`는 리스너가 아니라 연결 전용 FD에서 수행합니다.

### HTTP 요청 파싱/응답 생성

TCP는 HTTP 요청 경계를 보존하지 않습니다. [클라이언트 세션](src/server/client_session.c)은 연결별로 버퍼와 파서 상태를 유지합니다.

1. **요청을 읽습니다.** 요청 줄과 헤더를 파싱하고, 요청 대상과 헤더 규칙을 검증합니다. 데이터가 부족하면 다음 읽기까지 기다리고, 잘못된 입력이면 HTTP 오류 응답을 준비합니다.
2. **본문을 읽습니다.** [HTTP 파서](src/http/http.c)는 `Content-Length` 또는 chunked 형식에 맞춰 본문을 읽습니다.
3. **응답을 보냅니다.** 상태 줄과 헤더를 먼저 보내고 본문을 이어 보냅니다. 한 번에 다 쓰지 못하면 전송 위치를 저장합니다. `HEAD`에는 본문을 보내지 않습니다.

### 정적 파일 서빙/동적 요청 처리

| 요청 | 처리 방식 |
| --- | --- |
| 정적 `GET`/`HEAD` | [정적 파일 처리기](src/static/static_response.c)는 정적 루트 아래에서 일반 파일 또는 `index.html`을 찾고, 파일 FD·MIME·크기를 응답에 넘깁니다. 파일 전체를 메모리에 올리지 않고 나눠 보냅니다. |
| `POST /echo` | [라우트 테이블](src/app/app.c)이 에코 처리기를 선택합니다. 널 바이트를 포함한 본문을 `application/octet-stream`으로 그대로 돌려줍니다. |
| `/cgi-bin/이름` | `--cgi-root`를 지정할 때만 켭니다. [CGI 실행기](src/app/cgi.c)는 워커 2개와 대기열 8칸을 사용합니다. 대기열이 차면 `503`, 실행 한도 5초를 넘기면 자식을 정리하고 `504`로 응답합니다. 출력 한도는 1 MiB입니다. |

[파일 열기](src/static/static_file.c)는 `openat2` 제약으로 정적 루트 밖이나 다른 마운트로 넘어가지 않도록 합니다. CGI는 샌드박스가 아니므로 공개 정적 루트나 업로드 경로와 분리하고 신뢰하는 실행 파일만 둡니다.

### 동시 요청 처리

[이벤트 루프](src/server/epoll_loop.c)는 단일 스레드에서 LT(Level-Triggered) `epoll`로 준비된 FD를 처리합니다. 한 연결이 아직 읽거나 쓸 수 없으면 그 세션의 상태를 저장하고 다른 연결을 처리합니다. 프록시의 백엔드 소켓도 같은 이벤트 루프에서 감시합니다.

웹 서버는 연결을 재사용하고 파이프라인 요청에는 수신 순서대로 응답합니다. `SIGINT`나 `SIGTERM`을 받으면 새 연결을 받지 않고, 진행 중인 요청은 유예 시간 안에서 마무리합니다. [LT/ET 비교 실습](examples/README.md)에서 두 알림 방식의 차이를 확인할 수 있습니다.

## 리버스 프록시 핵심 구현

### 경로 기반 라우팅과 요청 중계

1. [라우터](src/proxy/proxy_routes.c)는 쿼리를 제외한 경로에서 **가장 긴 접두사**를 선택합니다. 같은 접두사의 백엔드는 등록 순서대로 번갈아 선택하며, 일치하는 규칙이 없으면 `404`를 반환합니다.
2. [요청 재구성 코드](src/proxy/proxy_wire.c)는 경로와 쿼리를 보존하고 `Host`를 설정된 백엔드 주소로 바꿉니다. 연결 단위 헤더를 제거하고 디코딩한 본문 길이로 `Content-Length`를 설정합니다.
3. [중계 코드](src/proxy/proxy_exchange.c)는 백엔드 접속부터 응답 전송까지 논블로킹으로 처리합니다. 클라이언트 쪽 전송이 밀리면 백엔드 읽기를 잠시 멈춥니다. chunked 응답과 EOF로 끝나는 응답은 클라이언트에 chunked로 보냅니다.

### 장애 처리와 연결 재사용

**재시도는 요청을 쓰기 전 접속 단계에서만 합니다.** TCP 접속에 실패하면 같은 접두사의 다음 백엔드를 시도하며, 모든 접속 시도는 2초 기한을 공유합니다. 쓰기를 시작한 요청은 중복 처리를 막기 위해 다시 보내지 않습니다. 클라이언트에 응답을 쓰기 전에는 실패 유형에 따라 `502` 또는 `504`를 반환하고, 쓰기 시작한 뒤 중계가 실패하면 연결을 닫습니다.

클라이언트와 백엔드 연결의 재사용 여부는 따로 판단합니다. HTTP/1.1 고정 길이 응답을 끝까지 읽었고 종료 신호나 남은 데이터가 없으면, 백엔드 항목마다 유휴 소켓을 최대 1개씩 최대 5초 동안 보관합니다. chunked·EOF 응답은 중계하지만 해당 백엔드 연결은 재사용하지 않습니다.

### A/B 라운드 로빈과 장애 전환 예시

8080 포트를 사용 중인 단독 서버가 있다면 먼저 종료합니다. 같은 컨테이너의 별도 셸에서 각 명령을 실행합니다.

```sh
./webserver --port 8001 --root examples/round-robin/a
./webserver --port 8002 --root examples/round-robin/b
./reverse-proxy --port 8080 --route /=127.0.0.1:8001 --route /=127.0.0.1:8002
```

`curl -fsS http://127.0.0.1:8080/`을 반복하면 A → B → A 순서로 응답합니다. A를 종료하면 이후 요청에는 B가 응답합니다.

### 메모리 누수 검사

```sh
sh tests/verify_phase3.sh
```

스크립트는 일반 빌드와 ASan/UBSan/LSan 빌드의 회귀 테스트를 실행하고, Valgrind로 C 단위 테스트 8개와 FD를 검사합니다. **2026-11-25 Linux/amd64 Docker(GCC 14.2.0) 재검증은 종료 코드 `0`**으로 끝났습니다.

별도의 **기존 실행 프로세스 계측**에서는 웹 서버와 프록시 모두 Valgrind 오류가 0건이었습니다. 웹 서버는 FD 8개를 유지했고, 프록시는 유휴 연결을 보관한 뒤 7개에서 8개로 늘어난 상태를 유지했습니다. CGI를 켠 웹 서버도 오류 0건이었고 종료 시 표준 FD 3개만 남았습니다. 외부 CGI 실행 파일 자체는 계측하지 않았습니다. 로컬 Docker 결과는 GitHub Actions의 실행 결과와 별개입니다.

### 고려한 엣지 케이스

| 상황 | 처리 |
| --- | --- |
| 요청 줄·헤더·본문이 나뉘어 도착합니다. | 연결별 버퍼와 파서 상태를 유지하고 이어 읽습니다. |
| 본문 길이 헤더가 충돌하거나 입력이 너무 큽니다. | 잘못된 프레이밍을 거부하고 요청 줄·헤더·본문에 각각 크기 제한을 적용합니다. |
| 클라이언트가 천천히 보내거나 읽습니다. | 부분 전송 상태와 기한을 관리하면서 다른 연결도 처리합니다. |
| 요청 경로가 정적 루트 밖을 가리키거나 확장자가 허용되지 않습니다. | 루트 경계를 지키고 허용된 확장자의 일반 파일만 제공합니다. |
