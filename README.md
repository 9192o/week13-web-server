## 알려진 한계

### keep-alive 연결이 워커를 붙잡음 (스레드 풀 모델)

워커 스레드는 연결 단위로 일한다. keep-alive 연결은 다음 요청을 기다리는 동안(idle,
최대 `KEEPALIVE_TIMEOUT_MS` = 5초)에도 워커 하나를 차지한다. 그래서 워커 수(`-w`, 기본 8)만큼의
클라이언트가 가만히 연결만 열어 두어도 새 연결은 큐(`-q`)에서 기다리고, 큐까지 차면 503 을 받는다.

이벤트 루프(`poll`/`epoll`) 모델은 idle 연결을 fd 하나로만 들고 있어 이 문제가 없지만,
읽기·쓰기·CGI 를 전부 non-blocking 상태 머신으로 바꿔야 한다.
keep-alive 연결이 닫힐 때 남기는 로그 `(keep-alive closed: 이유, N requests, 초)` 로
연결이 워커를 얼마나 붙잡았는지 볼 수 있다.

### 강제 종료가 CGI 실행 중이면 늦어짐

종료 신호(SIGINT/SIGTERM) 뒤 처리 중인 연결을 최대 `SHUTDOWN_TIMEOUT_MS`(10초) 기다리고,
넘기거나 신호가 한 번 더 오면 연결 소켓을 `shutdown` 해서 강제로 끊는다 (종료 코드 2).
이때 워커가 소켓이 아니라 CGI 파이프를 기다리는 중이면 소켓을 끊어도 깨어나지 않아,
CGI 시간 제한(`CGI_TIMEOUT_MS`, 5초)까지 더 걸릴 수 있다 (최악 10 + 5초).
CGI 자식의 pid 를 워커마다 기록해 강제 종료 때 kill 하면 없앨 수 있지만, 구조가 커져서 감수했다.


### 리버스 프록시: 백엔드 시간 제한이 아직 없음 (P1, P4 에서 해결 예정)

`-R prefix=host:port` 규칙으로 백엔드에 넘기는 요청은 지금 백엔드 쪽 시간 제한이 없다.

- 응답하지 않는 IP 로 `connect` 하면 커널 기본값(1~2분)까지 막힌다.
- 연결은 됐는데 백엔드가 응답하지 않으면 워커가 계속 기다린다. 이때는 종료 신호의 강제 종료도
  클라이언트 소켓만 끊으므로 그 워커가 깨어나지 않아 종료가 끝나지 않을 수 있다.
- 응답 전송 제한(`SEND_TIMEOUT_MS`, 30초)에 백엔드가 느리게 보내는 시간까지 포함된다.

자기 자신을 가리키는 규칙(루프백·0.0.0.0 이면서 포트가 `-p` 와 같음)은 시작할 때 거부하지만,
다른 로컬 IP 나 다른 프록시를 거쳐 돌아오는 루프는 막지 못한다.
