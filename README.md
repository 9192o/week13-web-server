# 🌐 week13-web-server

C17과 Linux 소켓 API로 HTTP/1.1 웹 서버와 리버스 프록시를 구현한 크래프톤 정글 13주차 프로젝트입니다.

**목차:** [📌 개요](#overview) · [🖥️ 웹 서버 핵심 구현](#server) · [🔀 리버스 프록시 핵심 구현](#proxy) · [🧪 품질](#quality)

<a name="overview"></a>

## 📌 개요

```text
클라이언트 ── HTTP ── reverse-proxy ── HTTP ── webserver A/B
                                                  ├─ 정적 파일
                                                  ├─ POST /echo
                                                  └─ /cgi-bin/이름 (선택)
```

- `webserver`는 정적 파일과 동적 응답을 제공합니다. 프록시 없이 직접 접속할 수도 있습니다.
- `reverse-proxy`는 요청 경로로 백엔드를 선택하고 응답을 중계합니다.
- 두 프로그램은 HTTP 파서와 이벤트 루프를 공유하지만 독립적으로 실행합니다.

<a name="server"></a>

## 🖥️ 웹 서버 핵심 구현

```text
TCP 연결 수락 → HTTP 요청 파싱 → 정적·동적 처리 → HTTP 응답 전송
전체 연결 상태는 epoll 이벤트 루프에서 관리합니다.
```

### TCP 소켓 서버

```text
리스너 준비: socket() → setsockopt() → bind() → listen() → epoll 등록
연결 수락:   리스너 EPOLLIN → accept4() → client_session 생성 → 연결 FD 등록
데이터 처리: 연결 FD의 읽기·쓰기 이벤트 → recv() / send()
```

- `socket() -> bind() -> listen()` 흐름으로 재사용 가능한 IPv4 TCP 논블로킹 리스너 소켓을 만듭니다.
- `bind()`로 루프백 주소와 포트를 지정하고 `listen()`으로 연결을 받을 준비를 합니다.
- 이벤트 루프 내에서 `epoll`로 준비된 연결만 `accept4()`로 꺼냅니다. 각 연결마다 세션을 만들어 요청 버퍼와 송수신 상태를 따로 관리합니다.

### HTTP 요청 파싱/응답 생성

```text
recv() → 요청 줄·헤더 파싱 → 요청 대상·헤더 검증
  ├─ 입력 부족: 다음 읽기에서 이어서 파싱
  ├─ 잘못된 입력: 오류 응답 준비
  └─ 검증 통과: 본문 상태 초기화 → 라우트 준비 → 필요하면 본문 파싱

최종 응답 준비 → 상태 줄·헤더 전송 → 본문 전송(HEAD 제외)
```

- **요청을 읽습니다.** TCP는 요청 단위를 보장하지 않으므로 [클라이언트 세션](src/server/client_session.c)당 요청 줄과 헤더, 본문 파서 상태를 유지하며 파싱합니다.
- **본문을 읽습니다.** [HTTP 파서](src/http/http.c)는 `Content-Length` 또는 chunked 형식에 맞춰 읽습니다. 헤더나 라우트 단계에서 요청을 거부하면 본문을 읽기 전에 오류 응답을 준비할 수 있습니다.
- **응답을 보냅니다.** 상태 줄과 헤더를 먼저 보내고, 한 번에 다 쓰지 못하면 전송 위치를 저장합니다. `HEAD`에는 본문을 보내지 않습니다.

### 정적 파일 서빙/동적 요청 처리

```text
요청 → 라우트 선택
       ├─ 정적 GET / HEAD → 정적 루트 아래 파일 또는 index.html
       ├─ POST /echo      → 입력 본문을 바이트 그대로 반환
       └─ /cgi-bin/이름   → CGI가 활성화된 경우 워커에서 실행
```

| 요청 | 처리 방식 |
| --- | --- |
| 정적 `GET`/`HEAD` | [정적 파일 처리기](src/static/static_response.c)는 정적 루트 아래에서 일반 파일 또는 `index.html`을 찾고, 파일 FD·MIME·크기를 응답에 넘깁니다. 파일 전체를 메모리에 올리지 않고 나눠 보냅니다. |
| `POST /echo` | [라우트 테이블](src/app/app.c)이 에코 처리기를 선택합니다. 널 바이트를 포함한 본문을 `application/octet-stream`으로 그대로 돌려줍니다. |
| `/cgi-bin/이름` | `--cgi-root`를 지정할 때만 켭니다. [CGI 실행기](src/app/cgi.c)는 워커 2개와 대기열 8칸을 사용합니다. 대기열이 차면 `503`, 실행 한도 5초를 넘기면 자식을 정리하고 `504`로 응답합니다. 출력 한도는 1 MiB입니다. |

## 🔀 리버스 프록시 핵심 구현

```text
클라이언트 → 프록시에서 경로 선택 → 백엔드 A 또는 B
클라이언트 ← 프록시에서 응답 중계 ← 선택된 백엔드
```

### 경로 기반 라우팅과 요청 중계

```text
요청 → 가장 긴 경로 접두사 확인
       ├─ 일치 없음 → 404
       └─ 일치함 → 백엔드 선택 → 요청 재구성 → 백엔드로 전송
                   클라이언트 ← 응답 중계 ← 백엔드 응답 읽기
```

1. [라우터](src/proxy/proxy_routes.c)는 쿼리를 제외한 경로에서 **가장 긴 접두사**를 선택합니다. 같은 접두사의 백엔드는 등록 순서대로 번갈아 선택하며, 일치하는 규칙이 없으면 `404`를 반환합니다.
2. [요청 재구성 코드](src/proxy/proxy_wire.c)는 경로와 쿼리를 보존하고 `Host`를 설정된 백엔드 주소로 바꿉니다. 연결 단위 헤더를 제거하고 디코딩한 본문 길이로 `Content-Length`를 설정합니다.
3. [중계 코드](src/proxy/proxy_exchange.c)는 백엔드 접속부터 응답 전송까지 논블로킹으로 처리합니다. 클라이언트 쪽 전송이 밀리면 백엔드 읽기를 잠시 멈춥니다. chunked 응답과 EOF로 끝나는 응답은 클라이언트에 chunked로 보냅니다.

### 장애 처리와 연결 재사용

```text
백엔드 연결
  ├─ 접속 실패 → 같은 접두사의 다음 백엔드 시도
  └─ 접속 성공 → 요청 전송 → 응답 중계 → 재사용 조건 확인
                                         ├─ 충족 → 유휴 풀에 보관
                                         └─ 미충족 → 백엔드 연결 종료
```

- **재시도는 요청을 쓰기 전 접속 단계에서만 합니다.** 같은 접두사의 다음 백엔드를 시도하며, 모든 접속 시도는 2초 기한을 공유합니다. 쓰기를 시작한 요청은 다시 보내지 않습니다.
- 클라이언트에 응답을 쓰기 전 중계가 실패하면 `502` 또는 `504`를 반환합니다. 응답을 쓰기 시작한 뒤 실패하면 연결을 닫습니다.
- 클라이언트와 백엔드 연결의 재사용 여부는 따로 판단합니다. 종료 신호나 남은 데이터 없이 HTTP/1.1 고정 길이 응답을 끝까지 읽으면, 백엔드 항목마다 유휴 소켓을 최대 1개씩 최대 5초 동안 보관합니다.
- chunked·EOF 응답은 중계하지만 해당 백엔드 연결은 재사용하지 않습니다.

### A/B 라운드 로빈과 장애 전환 예시

```text
두 백엔드가 정상 → 요청 1: A → 요청 2: B → 요청 3: A
A를 종료한 뒤  → A 접속 실패 시 같은 경로의 B로 전환
```

- 8080 포트를 사용 중인 단독 서버가 있다면 먼저 종료합니다. 같은 컨테이너의 별도 셸에서 각 명령을 실행합니다.

```sh
./webserver --port 8001 --root examples/round-robin/a
./webserver --port 8002 --root examples/round-robin/b
./reverse-proxy --port 8080 --route /=127.0.0.1:8001 --route /=127.0.0.1:8002
```

- `curl -fsS http://127.0.0.1:8080/`을 반복해 응답 순서를 확인합니다. A를 종료한 뒤에는 B가 응답하는지 확인합니다.

### 부하 테스트 결과

```text
동시성 1·8·32 → 100건 워밍업 → 2,000건 측정 × 3회 → 중앙값 집계
```

- [공통 런북](docs/TEAM_COMMON_TEST_RUNBOOK.md)에 따라 GCC `-O2`, CPU 2개, 메모리 1 GiB로 실행했습니다. 응답은 1 KiB이며 요청마다 새 연결을 열었습니다.
- 직접·프록시 36,000건, 기준 백엔드 18,000건, 워밍업 2,700건이 모두 성공했습니다. 표에는 회차별 처리량(req/s)과 p95 지연(ms)의 중앙값을 표시합니다.

| 경로 | 동시성 1 | 동시성 8 | 동시성 32 |
| --- | ---: | ---: | ---: |
| 직접 정적 GET | 2,514 · 0.57 ms | 1,607 · 7.95 ms | 1,605 · 31.46 ms |
| 프록시 경유 GET | 1,810 · 0.73 ms | 1,040 · 38.24 ms | 998 · 67.19 ms |
| 기준 Python 백엔드 직접 GET | 1,475 · 0.89 ms | 1,196 · 21.72 ms | 943 · 61.07 ms |

- 부하 생성기와 백엔드를 같은 컨테이너에 두었으며, 직접 정적 GET과 프록시 경유 GET의 백엔드 구현은 서로 다릅니다. 이 결과를 프록시만의 비용, 운영 처리 한도 또는 keep-alive 개선 폭으로 해석하지 않습니다.
- 단계별 측정은 [Phase 1 검증](docs/PHASE_1_TESTING.md), [Phase 2 검증](docs/PHASE_2_TESTING.md), [Phase 3 검증](docs/PHASE_3_TESTING.md)에 정리했습니다.

### 퍼징

```text
시드 16개 → libFuzzer가 입력 생성 → HTTP·프록시 코드 실행 → 실패 기록
```

- [퍼징 하네스](tests/fuzz_http.c)는 16개 [시드](tests/fuzz_corpus)에서 시작해 HTTP 요청 줄·헤더·본문 파싱, 프록시 요청 재구성, 프록시 응답 헤더 파싱을 libFuzzer·ASan·UBSan으로 검사합니다.

```sh
sh dev.sh build
sh dev.sh shell
make fuzz FUZZ_SECONDS=60
```

- **재실행 결과:** Clang 19.1.7에서 61초간 **4,174,818회** 실행했습니다. 종료 코드는 `0`이며 크래시·타임아웃 산출물은 0개였습니다.
- 입력과 실패 산출물은 `fuzz_work/`에 저장하며 커밋하지 않습니다.
- 네트워크 이벤트 루프, 연결 재사용 상태, CGI, 파일 시스템은 검사 범위에 포함하지 않습니다. 10분 실행 방법과 이전 기록은 [퍼징 문서](docs/FUZZING.md)에 정리했습니다.

### 고려한 엣지 케이스

```text
경계 상황 감지 → 세션 상태 확인 → 이어 처리 / 오류 응답 / 연결 정리
```

| 상황 | 처리 |
| --- | --- |
| 요청 줄·헤더·본문이 나뉘어 도착합니다. | 연결별 버퍼와 파서 상태를 유지하고 이어 읽습니다. |
| 본문 길이 헤더가 충돌하거나 입력이 너무 큽니다. | 잘못된 프레이밍을 거부하고 요청 줄·헤더·본문에 각각 크기 제한을 적용합니다. |
| 클라이언트가 천천히 보내거나 읽습니다. | 부분 전송 상태와 기한을 관리하면서 다른 연결도 처리합니다. |
| 요청 경로가 정적 루트 밖을 가리키거나 확장자가 허용되지 않습니다. | 루트 경계를 지키고 허용된 확장자의 일반 파일만 제공합니다. |
| 인덱스가 있는 디렉터리 URL에 끝 슬래시가 없습니다. | `308`과 `Location`으로 슬래시가 붙은 URL을 안내합니다. |
| 백엔드가 응답을 끝내기 전에 끊깁니다. | 이미 시작한 응답을 새 상태 줄로 덮지 않고 연결을 닫습니다. |
| 종료 신호를 받거나 연결 한도에 도달합니다. | 새 연결 수락을 제어하고, 종료 유예가 끝나면 남은 연결과 FD를 정리합니다. |

### 요구 사항

```text
Phase 1: HTTP 기본 → Phase 2: 동시 연결과 재사용 → Phase 3: 리버스 프록시
```

| 단계 | 구현 범위 |
| --- | --- |
| [Phase 1](docs/PHASE_1_REQUIREMENTS.md) | TCP 연결 수락, HTTP/1.1 파싱과 응답, 정적 `GET`/`HEAD`, 바이너리 `POST /echo`를 구현합니다. |
| [Phase 2](docs/PHASE_2_REQUIREMENTS.md) | 논블로킹 I/O로 여러 연결을 처리하고, 연결 재사용·순차 파이프라이닝·정상 종료를 지원합니다. |
| [Phase 3](docs/PHASE_3_ARCHITECTURE.md) | 경로 기반 중계, 백엔드 풀, 접속 실패와 타임아웃 처리를 구현합니다. |

전체 범위는 [과제 요구 사항](docs/REQUIREMENTS.md)에서 확인할 수 있습니다.

### 빌드 및 실행

```text
개발 이미지 빌드 → 컨테이너 셸 → make → 웹 서버 시작 → curl로 응답 확인
```

- 기준 환경은 **Linux/amd64 Docker**입니다. 호스트에서 개발 이미지를 빌드하고 셸을 엽니다. WSL에서는 `dev.sh`가 `docker.exe`를 사용합니다.

```sh
sh dev.sh build
sh dev.sh shell
```

- 개발 셸에서 두 프로그램을 빌드하고 웹 서버를 시작합니다.

```sh
make
./webserver --port 8080 --root public
```

- 같은 컨테이너의 다른 셸에서 `curl -i http://127.0.0.1:8080/`으로 시작 페이지를 확인합니다.
- 다른 셸이 필요하면 호스트에서 `docker exec -it <컨테이너-ID> bash`를 실행합니다. WSL에서는 `docker.exe`를 사용합니다.
- 브라우저 실행 방법은 [브라우저 라우팅 실습](docs/ROUTING_DEMO.md)에 정리했습니다.
