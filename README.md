# week13-web-server
크래프톤 정글 13주차. "C로 동작하는 웹서버" 구현 레포지터리입니다.

## 리버스 프록시 (phase 3)

### 사용법

```sh
# 백엔드 두 대 (같은 서버를 포트만 바꿔 실행)
./server -p 8001 -r ./www-a
./server -p 8002 -r ./www-b

# 프록시: /api/ 는 두 백엔드로 라운드로빈, /cgi-bin/ 은 8001 로, 나머지는 프록시가 직접 서빙
./server -p 8080 -r ./www -R /api/=127.0.0.1:8001,127.0.0.1:8002 -R /cgi-bin/=localhost:8001
```

- `-R prefix=host:port[,host:port...]` 를 여러 번 줄 수 있다 (규칙 최대 16개, 규칙마다 백엔드 최대 8개).
- prefix 는 '/' 로 시작하고, 디코딩된 경로의 앞부분이 문자열 그대로 같으면 매칭된다.
  여러 규칙이 맞으면 가장 긴 prefix. 규칙은 `/cgi-bin` 보다 먼저 확인한다.
- 호스트는 이름도 되며 시작할 때 한 번 IPv4 로 해석한다.
- 같은 prefix 두 번, 프록시 자신(루프백·0.0.0.0 + `-p` 와 같은 포트)을 가리키는 규칙은 시작할 때 거부한다.

### 동작

| 상황 | 결과 |
| --- | --- |
| 규칙에 맞는 경로 | 백엔드로 전달. 경로·쿼리는 원문 그대로, Host 는 클라이언트 값 그대로 (P1) |
| 규칙에 없는 경로 | 프록시가 직접 정적 파일·CGI 로 처리 (P7) |
| 백엔드 여러 대 | 규칙마다 atomic 카운터로 라운드로빈, 첫 요청은 첫 번째 백엔드 (P2) |
| connect 실패 (꺼짐) | 목록의 다음 백엔드로 재시도, 백엔드마다 한 번. 다 실패하면 502 (P3) |
| connect 시간 초과 / 응답 헤더 5초 안에 안 옴 | 504 (P4) |
| 본문 전송 도중 백엔드가 닫거나 5초 멈춤 | 이미 헤더를 보냈으므로 클라이언트 연결을 끊음 (P5, P4) |
| 전송 도중 클라이언트가 끊음 | 중계 중단, 두 fd 모두 정리 (P6) |
| POST | 본문을 CGI 와 같은 규칙(411/413/100-continue/408)으로 다 받은 뒤 전달 (P8) |

- 백엔드에는 `HTTP/1.0` + `Connection: close` 로 보낸다. chunked 응답이 오지 않고,
  응답 끝은 Content-Length 또는 백엔드가 닫는 것으로 안다.
- 응답에 Content-Length 가 있으면 클라이언트 keep-alive 를 유지하고, 없으면 끝까지 흘린 뒤 닫는다.
- hop-by-hop 헤더(Connection, Keep-Alive, Proxy-Connection, TE, Upgrade, Connection 에 적힌 헤더)는
  양쪽 다 빼고, 응답 상태 줄은 `HTTP/1.1` 로 바꾼다.
- 깨지거나 애매한 응답 헤더(상태 줄 형식, 1xx, Content-Length 오류·충돌, Transfer-Encoding)는 502.
- 접근 로그 끝에 `(proxy host:port[, 이유])`, 재시도는 `(proxy retry: ...)` 한 줄이 따로 남는다.

### 구조

- `src/proxy.c` — 규칙 해석, 경로 매칭, 라운드로빈 선택, 요청·응답 헤더 재작성,
  시간 제한 있는 connect. 네트워크 중계를 하지 않아 단위 테스트(`tests/test_proxy.c`)로 검증한다.
- `src/server.c` 의 `serve_proxy` — 요청 하나의 흐름: (POST 본문 받기) → 백엔드 고르기 →
  connect(재시도) → 전송 → 응답 헤더 검사 → 본문 중계. 워커 스레드가 connfd 와 backendfd 를 함께 든다.
- 기능 테스트는 `tests/functional.sh` 의 "리버스 프록시" 구역 (P1~P8, 504 는 `--timing`).

### 추후 작업

## 알려진 한계

### keep-alive 연결이 워커를 붙잡음 (스레드 풀 모델)

워커 스레드는 연결 단위로 일한다. keep-alive 연결은 다음 요청을 기다리는 동안(idle,
최대 `KEEPALIVE_TIMEOUT_MS` = 5초)에도 워커 하나를 차지한다. 그래서 워커 수(`-w`, 기본 8)만큼의
클라이언트가 가만히 연결만 열어 두어도 새 연결은 큐(`-q`)에서 기다리고, 큐까지 차면 503 을 받는다.

이벤트 루프(`poll`/`epoll`) 모델은 idle 연결을 fd 하나로만 들고 있어 이 문제가 없지만,
읽기·쓰기·CGI 를 전부 non-blocking 상태 머신으로 바꿔야 한다.
keep-alive 연결이 닫힐 때 남기는 로그 `(keep-alive closed: 이유, N requests, 초)` 로
연결이 워커를 얼마나 붙잡았는지 볼 수 있다.

### 강제 종료가 CGI 실행 중이면 늦어짐

종료 신호(SIGINT/SIGTERM) 뒤 처리 중인 연결을 최대 `SHUTDOWN_TIMEOUT_MS`(10초) 기다리고,
넘기거나 신호가 한 번 더 오면 연결 소켓을 `shutdown` 해서 강제로 끊는다 (종료 코드 2).
이때 워커가 소켓이 아니라 CGI 파이프를 기다리는 중이면 소켓을 끊어도 깨어나지 않아,
CGI 시간 제한(`CGI_TIMEOUT_MS`, 5초)까지 더 걸릴 수 있다 (최악 10 + 5초).
CGI 자식의 pid 를 워커마다 기록해 강제 종료 때 kill 하면 없앨 수 있지만, 구조가 커져서 감수했다.


### 리버스 프록시: 백엔드가 느릴 때

백엔드 시간 제한은 `PROXY_CONNECT_TIMEOUT_MS`(connect 한 번, 5초)와 `PROXY_TIMEOUT_MS`
(응답 헤더 전체, 그리고 본문 조각 사이 무응답, 5초)다. 그래서 다음은 남는다.

- connect 재시도는 백엔드마다 따로 시간을 잰다. 응답 없는 IP 가 여러 개면 최악 (백엔드 수 x 5초)
  뒤에 504 가 된다.
- 강제 종료(종료 신호 뒤 시간 초과, 두 번째 신호)는 클라이언트 소켓만 끊으므로, 백엔드를 기다리는
  워커는 위 시간 제한까지 깨어나지 않는다 (최대 5초 + 재시도분).
- 응답 전송 제한(`SEND_TIMEOUT_MS`, 30초)은 응답 하나 전체 기준이라, 백엔드가 조각마다 5초 안에
  꾸준히 보내더라도 전체가 30초를 넘으면 클라이언트 연결이 끊긴다.

자기 자신을 가리키는 규칙(루프백·0.0.0.0 이면서 포트가 `-p` 와 같음)은 시작할 때 거부하지만,
다른 로컬 IP 나 다른 프록시를 거쳐 돌아오는 루프는 막지 못한다.
